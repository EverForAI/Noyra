## A01：Windows站点图密钥文件的ACL未被加载器校验

**类型与归因：** 本轮新增跨平台安全合同遗漏，来自`c15259f`引入的专用密钥加载器。复用的通用凭证helper原有行为没有变化，问题是新keyring将其视为完整私有文件验证。

**代码证据：** `src/noyra/interaction/sitemap_tokens.py:45`调用`read_secret_file`；`src/noyra/core/credentials.py:53`在非POSIX平台直接跳过权限验证。`sitemap_tokens.py:61`调用的`validate_private_root`默认`create=False`，验证目录、链接和设备边界，不执行Windows ACL审计或加固。参考既有`src/noyra/core/at_rest.py:1326`、`:1770`的keyring验证在Windows调用ACL审计。

**根因：** 路径完整性与文件访问权限是两类边界。当前加载器具有绝对路径、reparse/symlink拒绝、普通单链接文件、打开前后文件身份一致和4096字节上限，但Windows下没有核验访问该文件的主体范围。Windows的`chmod(0600)`也不能替代DACL验证。

**有界复现：** 对临时合成keyring用`icacls`增加Everyone读取权限，现有`SitemapTokens.from_file`仍接受，既有keyring参考验证器拒绝：

```json
{"probe":"windows_everyone_readable_sitemap_keyring","sitemap_accepted":true,"reference_validator_error":"BackupKeyUnavailableError"}
```

该诊断证明加载器接受不安全文件，不是实际登录另一个账号读取生产密钥的测试；有效访问还受祖先目录ACL等条件影响。

**影响：** 若另一个本机账号可到达并读取该文件，可解密或生成站点图路由描述符，获知其subject/kind/slot范围并破坏该路由材料的保密目标。该密钥不是操作令牌或归档正文密钥；分片仍校验当前主体、公开资格和hash，不能据此推断能够登录后台、解密私密正文或绕过撤回。具备写入权限时还可能篡改配置造成启动失败或旧路由失效。

**触发条件与概率：** Windows配置外部keyring，或默认secret目录/文件出现宽松ACL。加载器接受上述文件可重复复现；实际未经授权读取/修改的概率取决于本机账号、文件及祖先权限，未测。正确加固的data-root可能另有AtRest总检查保护，不能推定所有Windows部署都已泄露，更不能据此认定Linux生产受同一问题影响。

**修复风险：中。** 全局改变`read_secret_file`可能影响其他凭证、systemd文件与启动时延；直接替换成某个路径validator又可能丢失有界读取、稳定文件身份或POSIX服务组合同。应局部完善sitemap keyring加载，沿既有Windows ACL合同拒绝不合格文件，保留POSIX root/service-group 0640和服务账号私有文件支持。

**建议及验收：** Windows使用前优先修复，发布前闭合。覆盖Everyone/Users读写、继承ACL、意外owner、ACL探测不可用、正确私有ACL，以及POSIX owner/group、symlink/reparse/hardlink、文件替换、超大/损坏、双owner初始化与轮换。不得静默再生密钥来掩盖不安全文件。前份复审“权限不合格均拒绝”的结论需按本报告限定为当前真正实现的平台范围。

## A02：钱包只读列表的SQLite锁等待未受短期限约束

**类型与归因：** 既有数据库等待合同遗漏。本轮`f280fb1`正确统一同步高分辨率时钟并组合父请求期限，没有引入付款或跨时钟原点错误；但新的剩余预算目标没有覆盖busy等待。

**代码证据：** `src/noyra/wallet/admin_projection.py:90`创建不超过3秒及父剩余时间的期限，`:93`进入`Database.read_transaction`，`:94`安装SQL progress handler，`:142`在投影后检查期限。`src/noyra/core/database.py:7151`仍为连接设置30000ms busy timeout，`:7215`的读事务未覆盖它。HTTP在`src/noyra/service.py:2675`把`WalletListLimit`映射为503及`wallet_list_budget_exceeded`。

**根因：** progress handler在SQLite虚拟机执行期间检查期限，不能中断等待锁的busy handler。同步HTTP的期限上下文也不是会抢占线程的外部定时器。短请求可在第一次SQL返回/报错后才知道已经超时。

**有界复现：** 临时合成库切换DELETE journal，另一连接持有`BEGIN EXCLUSIVE`，1.2秒后自动释放；在50ms父期限内调用当前钱包列表：

```json
{"probe":"wallet_busy_wait","journal_mode":"delete","parent_budget_seconds":0.05,"lock_seconds":1.2,"elapsed_seconds":1.224,"error_type":"WalletListLimit"}
```

这是排他锁/非正常日常WAL写者的复现。不能将它扩大成“普通WAL写事务都会阻塞读取”或“每个钱包请求都会等待30秒”。

**影响：** 超预算后仍正确拒绝，没有返回成功伪装、资金side effect或记录修改；问题是请求线程在拒绝前占用资源过久。维护、恢复、排他访问或实际锁模式异常时，并发等待可增加管理台延迟和HTTP容量占用。单次busy等待可能沿用30秒上限，确切总时间受语句与锁行为影响。

**触发条件与概率：** 读取需要等待锁，且busy等待大于父请求剩余预算/列表3秒上限。本次1.2秒锁和50ms预算下已复现；正常WAL无排他读取阻塞时较低，维护/竞争时上升，生产频率未统计。

**修复风险：中。** 全局降低`Database`超时会影响写事务、升级、记账和恢复，不适合作为局部只读列表修复。应在该投影的专用连接上组合剩余期限与busy等待，必要时采用有界重试和检查点，并审查连接建立/首次查询的边界。

**建议及验收：** 优先修复该短预算路径，发布前闭合锁竞争场景。覆盖正常WAL读写、合成排他锁、父期限已耗尽/仅余毫秒、默认3秒、锁释放后下一请求恢复；保留SQL progress、主体/游标范围、hash和现有503错误合同。验证所有余额、订单、执行状态未改变，不修改资金或签名流程。

## A03：合法多行JSON keyring被拒绝

**类型与归因：** 本轮专用加载器新增的配置兼容性问题，与A01共用入口但根因及影响不同。

**代码证据：** `sitemap_tokens.py:46`未显式指定`single_line=False`；`core/credentials.py:83`默认`single_line=True`，`:128`拒绝内部换行/制表控制字符。之后的`json.loads`原本能够处理JSON语法允许的换行。公开合同`docs/api/public-contract-v2.md:59`指定JSON结构，没有声明只能单行序列化。`service.py:1440`在构造时加载外部文件。

**根因：** 结构化JSON配置复用了“一行令牌”内容规则。文件末尾换行经strip移除不构成本问题；问题是对象/数组内常见的格式化换行。

**有界复现：** 同一份合成材料，文件权限设为0600；`json.dumps(..., indent=2)`被拒绝，压缩单行版本接受：

```json
{"probe":"multiline_sitemap_keyring","error_type":"CredentialError"}
{"probe":"compact_sitemap_keyring","persistent":true}
```

**影响：** 管理员用常规JSON编辑器制作/轮换密钥文件，可能使服务构造或启动失败。拒绝发生在读取配置阶段，未确认密钥泄露、数据变化或轮换被静默接受；默认自动生成的压缩文件不受此情形影响。

**触发条件与概率：** 指定包含内部换行的外部JSON文件，或手工把managed文件改为格式化JSON。该输入下必现；自动生成和持续单行管理时较低，实际管理员使用频率未知。

**修复风险：低中。** 局部接受JSON允许的空白，继续保持4096字节、编码、稳定文件身份、权限、结构、key长度和重复key验证。不得放宽一行操作令牌/供应商凭证的通用规则或吞掉错误自动换key。

**建议及验收：** 可暂缓，但计划文件轮换或多主机分发前应完善。优先支持受控的多行JSON；如暂时仅支持单行，必须明确操作合同。验收pretty/compact/CRLF、合法缩进、空文件、非JSON、超大文件、损坏key和旧URL轮换兼容。

## A04：原短批次返回时可能多显示记录

**类型与归因：** 既有阅读数量合同遗漏。本轮补齐了极短/空页下的“欠恢复可继续”，但没有闭合首请求“超恢复”；起点`bb250b9`也在首请求后计算wanted，不能归因为此次新增数据丢失。

**代码证据：** `src/noyra/web/app.js:740`恢复直接使用旧`restore.path`，通常保留`limit=20`；`:749`先执行首请求，`:750`才计算原批次目标；只有`:756`后的补读按剩余条数设置limit。`:794`在显示数量达到目标后清除恢复状态。

**根因：** 第一页限制采用旧请求limit，而不是本次要恢复的原可见条数。原批次受过滤/冷段边界影响只有13条时，如果现在同一合法请求能返回20条，首请求就会超过原目标。

**有界复现：** 调用当前源码的loadView/refresh，使用既有前端harness，原目标13、保存路径limit20、当前API按该limit返回20条：

```json
{"probe":"restore_short_batch","target":13,"visible":20,"cursor":"220","reads":1,"restoring":null}
```

**影响：** “回到原批次”的条数和阅读位置恢复不精确，状态显示20条并清除恢复目标。此次复现没有跳项、重复、服务器写入、私有数据混入或撤回正文缓存；下一游标仍位于实际读取之后。

**触发条件与概率：** 原批次条数小于保存路径limit，且当前同一路径的合法首批返回数变多。满足该组合时可复现；增长、撤回/过滤和冷段粒度决定实际频率，未统计。原目标200的常规补读不证明13→20边界已覆盖。

**修复风险：低中。** 在第一次请求前以剩余目标限制读取。不能在读取20条后简单slice成13条同时保留推进到220的游标，否则会新引入跳过7条的问题。保留有界补读、去重、撤回重查、异步代次及草稿隔离。

**建议及验收：** 可暂缓体验修复。覆盖13→20、1→20、上一批恢复、空页/短页、目标200、部分恢复继续、历史结束、撤回与迟到响应；对照记录ID和游标证明没有跳项，并使状态准确反映当前恢复目标。

## C01：增量slot解决了全源扫描，长期容量运维仍未完整

**类型与归因：** 已公开的工程容量边界，不是确认的索引丢失或新隐蔽安全漏洞。`3a572a0`引入持久slot，改善旧全扫描；相应增加了必须保留slot的运维合同。

**代码/证据：** `core/public_sitemap_schema.py:36`建表并禁止UPDATE/DELETE，后续回填/源触发器仅追加。`interaction/public_archive.py:683`只读各类别高水位，`:687`限制单类别5百万slot，`:689`每100slot生成范围，`:697`限制总描述符5万；`service.py:9812`限制完整XML为2,000,000字节。`tests/test_public_sitemap_capacity.py:58`及既有运行证据覆盖25000有效日记/250分片、增长、撤回、重演和主体隔离。

**根因/未完整部分：** 撤回保留tombstone，源记录清理也不重排slot。根索引按历史高水位生成全部范围，空范围仍占描述符。没有完整的多层索引、永久slot增长容量看板、容量预警与大规模迁移/保留策略。根查询避免了历史正文全扫描，但响应序列化/加密仍与范围数线性增长。

**影响：** 历史增长到预算边界时，整个站点图索引可能返回503或413；即使当前公开正文已减少，旧slot高水位也不一定下降。源公开分页/单条阅读有自己的预算，不能据此说所有公开页面都不可用。slot表及其索引也产生持久存储和源写入成本。

**触发条件与概率：** 大量历史记录或撤回、长URL/主体描述符、慢硬件和并发使时间/响应预算先到达。超过硬上限时会拒绝；本次未制造百万级生产数据或给出统一失效阈值。5万描述符、5百万slot只是各自上限，不能称为实际保证容量；XML或时间预算可能更早触发。小规模较低，长期增长后风险增加，发生时间未知。

**修复风险：中高。** 修改层次索引、分区/重建或保留策略涉及schema、旧路由、迁移、备份与当前公开资格。删除/重编号live slot会破坏稳定URL；改成成功空图、静默截断或取消hash/预算不可接受。

**建议及优化：** 可暂缓完整大规模索引工程；先给出目标规模、各类别slot/空分片数、根XML字节、生成时延和存储趋势，建立达到上限前的提示及维护runbook。需要更大规模时设计有界多层索引及版本化恢复策略。验收应含大量tombstone、多个公开类别、实际HTTP根XML而非只测内部token列表、schema71→94/93→94、源事务回滚、重演和key+slot完整恢复。现有文档关于“丢失slot只能换key并重抓索引”已明确，不再重复记成缺文档。

## C02：冷读进程隔离已实现，完整运行容量仍缺真实验证

**类型与归因：** 完成度与部署验收边界。`7fdfaa2`有效降低主进程冷段对象膨胀及不可取消解码风险；没有确认本轮引入越权、无限创建worker或不安全云恢复。

**代码/已有实测：** `interaction/public_cold_reader.py:29`、`:104`、`:141`对worker设置512MiB限制；`:238`启动spawn；`:271`有界IPC；`:319`终止/回收；实际退出前保留准入slot。`public_archive.py:84`全进程两槽准入；父快照传namespace/manifest/公开事件ID，子进程不打开live DB且只返回from/to/hash。`.runtime/remediation-systemd-rss.json`为应用SHA `f280fb1`：8请求/4并发，2次200（1.986/1.991秒）、6次准入503（0.059–0.110秒），最多2worker；父RSS111780KiB、child RSS151952KiB、child VMS165104KiB。后续单请求正常，保存路由重启后仍可读。

**根因/未完整部分：** 512MiB是Windows进程提交内存或POSIX地址空间，两者不同；它不是整个NoyraService的RSS上限。两槽是资源准入保护，不保证并发访客都成功。完整服务的认知/保留/完整性任务、实际磁盘与目标硬件、文件keyring初始化路径和长时间请求分布尚未给出完整验收。

worker通过`EventPayloadArchive`加载`ArchiveKeyring.from_env`；实际文件模式会走`core/archive.py:125`的路径/ACL检查，Windows还会调用`core/at_rest.py:1853`的PowerShell审计。现有大冷段专项常用合成inline key，不能据其延迟推定真实文件模式相同。本次未复现文件模式超时或辅助进程失控，因此不将该调用链报成确认漏洞。

**影响：** 访客冷历史请求可能因准入或期限拒绝；现有成功请求靠近2秒，目标环境余量须测量。完整服务的总内存/可用性不能从单worker限制和合成RSS数字外推。进程启动、主进程热SQL/JSON及OS调度仍有检查点/系统边界；文件系统不可中断工作可能暂时保留槽，相关风险已经文档化。

**触发条件与概率：** 多个并发冷请求、较大段、真实文件keyring加载、慢IO或其他服务任务同时运行。该合成负载里6/8准入拒绝是当次配置结果，不是生产75%失败率。正常环境的超时、RSS和拒绝率均未测，不能给出生产概率或宣称已OOM。

**修复/验收风险：中高。** 任意提高期限、并发或memory cap可能重新造成主机资源压力；减少验证/让冷读云恢复也会破坏安全边界。先测再决定是否优化worker初始化、隔离生命周期或容量，不进行没有数据依据的全局参数调整。

**建议及优化：** 发布前在最终安装SHA、完整服务、真实受保护文件keyring和目标硬件上验证p50/p95/p99、峰值内存（含父/子/辅助进程）、两槽拒绝/恢复、WAL和磁盘余量。覆盖损坏/缺key、轮换、慢IO、并发、超时后的回收和后续请求。明确可支持的段大小与访客并发；长期遥测应只输出状态/计数，不输出密钥或私密正文。完整服务总资源验收属于E01的一部分，本条列出其具体完成度要求，不另计为已发生的资源安全事故。
