## 3. C01：更新 certifi，保留 TLS 验证

### 根因、影响及触发条件

runtime 与 dev 锁文件仍固定 `certifi==2026.7.22`。GitHub 公告 `GHSA-6q48-6c7w-9gw2` 与 OSV 编号 `PYSEC-2026-4320` 指向同一信任库事件，不是两个独立漏洞。恶意利用需要相应泄露的 CA 私钥及在途流量控制条件；不是只要安装旧版本就证明已遭入侵。

### 实际修改

- `requirements.lock`、`requirements-dev.lock` 同步固定为 `2026.10.19`，仅更新该包及两项发布文件哈希，不整体漂移依赖。
- 两个发布文件均从 PyPI 元数据指定的发布站点下载，并验证内容 SHA-256；元数据保存在证据中。
- `pyproject.toml` 增加 `certifi>=2026.10.19`，避免不使用项目锁文件的 wheel 安装再次选择更旧版本。
- 新增锁文件同步及最低版本回归；不改动没有该依赖条目的 cloud 扩展锁文件。

### 验证与剩余风险

- Windows 3.11/3.12 和 Linux 3.12 验证环境安装更新后锁依赖，`pip check` 均通过。
- runtime、runtime + cloud、dev 三组在线 `pip_audit` 均返回无已知漏洞。
- 新构建 wheel 的 METADATA 包含最低版本约束，且包含 `maintenance_evidence.py`。
- 没有降低证书校验要求。信任库变更可能使此前依赖被移除证书链的上游不可用，这是兼容性风险，应由合法证书链解决。
- 已运行的环境、已有容器镜像和系统自身的证书库不会因 Git 提交自动更新；部署时必须重建/更新相应环境。本轮没有启动生产部署。

## 4. C02：让服务 UID 真正能够读取测试包

### 根因、影响及触发条件

原 root 集成测试先加载 `at_rest`，再切换 UID 65534；后续权限检查才延迟导入 `maintenance_evidence`。当 checkout 的任一级父目录对服务 UID 不可穿越时，导入失败表现为 `ModuleNotFoundError`，容易误判为安装包遗漏模块。

本轮构建 wheel 已确认该模块存在。错误发生在 Python root 集成测试，不是 shell 安装器已证明损坏。

### 实际修改

- 在本测试既有的可穿越临时根中，复制 `src/noyra` 到独立代码夹具。
- 只对这份临时代码副本设置目录 0755、文件 0644；不改变 checkout、用户 HOME、私有数据、密钥和维护证据的权限。
- 子进程先清空附加组、降 GID/UID、设置 umask，再首次导入 Noyra，并断言实际导入路径位于代码夹具中。
- 保留原有 GC、权限加固、加密备份、恢复及 root 证据归属断言；增加子进程 120 秒总超时。

### 验证与剩余风险

源码快照父目录保持 **0700** 时，修复后的真实 UID 65534 GC/备份/恢复测试通过。说明不是依赖放宽源码快照权限或预加载模块才通过。

随后普通组合测试在可读的 0755 快照运行，避免让其他未修改的 runuser 测试也失去源码访问。首次故意使用私有快照运行时，另一个既有 retention 夹具因找不到 `noyra` 失败，该日志仍保留；不能将其混入最终通过结果或当作产品回归。

## 5. C03：正文读失败在分发前关闭

### 根因、影响及触发条件

`do_POST()` 的通用 `except Exception` 把正文读取的 `TimeoutError` 当成内部业务错误，尝试返回 500。在 Windows 中，socket 超时可能早于绝对预算耗尽少许，500 仍可写出，因此该行为不能依赖另一个 deadline 偶然阻止回复。

基线/修复对照探针对超时和重置分别证明：基线尝试返回 500；修复后关闭连接且不回复；两者探针的业务分发次数均为 0。没有由此推断资金被盗或已经发生签名。

### 实际修改

只在 `self.rfile.read(length)` 周围捕获 `OSError`（包括超时及断连），设置 `close_connection=True` 并返回。短正文/非法 JSON 的原有校验和业务异常处理保持原语义，不能用外层统一吞掉所有 I/O 错误。

### 验证

- 保留真实 socket 半包超时测试和签名请求账本零新增断言。
- 新增不依赖时钟先后的正文超时/连接重置注入测试：不分发、不调用回复函数、连接关闭、账本仍为空。
- 将业务分发中的内部错误回归扩展到 RuntimeError、TimeoutError、ConnectionResetError：这些错误仍走脱敏诊断 500，证明正文读取的特殊处理没有蔓延到业务阶段。
- Windows 3.11、Windows 3.12、Linux 3.12 的签名服务及相关边界组合回归通过。

## 6. C04：验证清理完成，不要求清理瞬时完成

### 根因、影响及触发条件

旧测试要求：父命令在 0.25 秒超时后，后代绝不能在启动 1 秒后写标记。可是实现先调用 Windows `taskkill` 清理进程树，该命令自身存在启动/执行延迟。标记存在并不足以证明清理返回后仍有孤儿进程。

本次没有证据支持为了这一条时序断言立即引入高风险的生产 Job Object 改造，也没有把 `taskkill` 的一般失败情况宣布为已经解决。

### 实际修改及防止弱化测试

- 后代通过真实回环 socket 发送 ready；测试先确认后代确实启动。
- 等待 `SubprocessRunner.run()` 以 `COMMAND_TIMEOUT` 返回，随后才通过 socket 允许后代写标记。
- 要求连接已关闭且标记不存在，验证清理完成后不能继续产生该副作用。
- Windows 增加人为延迟 `taskkill` 启动 1.1 秒的分支；正常与慢清理分支均通过，不靠盲目增大标记睡眠时间。
- 外置负向控制故意把清理换成“只杀父进程”。新测试在标记断言上按预期失败，证明它仍能识别真正存活的后代；这个失败是有效性验证，不是最终产品测试失败。
- `src/noyra/deployment_setup.py` 本轮未修改。测试契约是清理返回后停止后代，而不是承诺超时瞬间所有进程已经原子停止；不能将测试通过解释成更强保证。
