## 1. 结论与发布建议

本轮确认 12 项问题：5 项 P1 代码或功能问题、1 项 P1 外部验收证据缺口、5 项 P2、1 项 P3。没有确认 P0。这不是逐行形式化验证，也不是“未列出的路径必定安全”的证明。

最重要的结论是：**当前仍存在确定的迁移代码缺陷，不能把全部剩余风险解释为缺少真实环境测试。** 标准 HTTP 迁移链中，真实配置数据库的快照、agent 到 root 激活协议、归档数据搬运和自主提案流程存在问题。网络回复丢失后的来源回滚还有单活安全缺口。完成真机测试之前，先修复这些代码问题；真机测试不能代替代码补全。

目前的质量状态是：当前 SHA 的专项回归及静态检查通过，但跨模块故障复现失败。可以继续开发和受控测试，不宜据此解除迁移保护或宣称全功能生产验收完成。迁移默认关闭、启用后默认人工审批仍应保留；“管理员明确开启”与“出厂默认开启”是不同决定。

## 5. 详细发现

### B01：回滚没有确认目标停用就恢复来源权限

- **风险等级：P1。** 可破坏主体单活，造成两端认知、消息及付款工作同时执行；实际双活风险在目标成功激活后才成立。
- **修复风险：高。** 需处理回复丢失、进程重启、目标不可达和幂等回滚，不能用简单的“异常即解除 fence”实现。
- **根因与代码证据：** `migration/http_executor.py:420` 发出 `/v1/activate`，在回复验证完成后的 `:453` 才保存 `_active`。`migration/cutover.py:223`、`:230` 的异常处理只在已经拿到 receipt 时尝试 executor rollback。显式 `CutoverCoordinator.rollback()`（`:256`）没有调用目标停用或验证目标已停用，却在 `:286` 撤销来源数据库 epoch，再在 `:293` 清除内存隔离。
- **关键区别：** `service.py:1614` 的 `source_unfence` 是保守空操作，单独发生 executor 异常时来源仍被隔离。这不是问题所在；问题是随后显式回滚把该保护解除，而且目标端数据库已是独立副本，不会因来源数据库修改自动停机。
- **影响范围：** 已进入 validating/cutover 的 HTTP 迁移任务，尤其目标已执行成功但回复丢失、或来源随后持久提交失败且目标回滚失败的情况。
- **触发条件：** 目标完成激活；来源收不到有效回执或持久提交失败；管理员/恢复流程调用来源 rollback，目标仍运行。
- **触发概率：** 健康完成流程不触发；网络/进程故障属于条件性、中等概率，无法从现有数据估计真实事故率。模拟中只要满足该状态，来源解除隔离即确定发生。
- **复现：** 在临时完整数据库创建合法任务及 epoch，模拟 executor 激活目标后抛出 `activation_reply_lost`，随后调用真实 coordinator rollback。结果为 `source_fenced_after_commit_error=true`、`executor_rollback_calls=0`、`target_still_active_simulation=true`、`source_admission_reopened=true`、epoch `revoked`。
- **建议：立即修复。** 持久记录激活请求与歧义状态；重新联系同一目标，取得与任务/epoch 绑定的停用证据后才能撤销来源权限隔离。目标不可达时保持隔离，提供明确的恢复所需状态，不能把本地 `rolled_back` 当作全局回滚完成。
- **修复验收：** 覆盖目标激活回复丢失、来源重启、目标停用回复丢失、停用失败、持久审计失败和重复回滚。核心断言必须是任意时刻最多一个端点获得有效写入/外部动作权限，而不只是数据库 task 字段变化。

### B02：真实配置记录触发不可变约束，使迁移快照失败

- **风险等级：P1。** 标准已配置实例无法迁移；来源在执行前已经建立隔离，失败后还需要可靠恢复，和 B01 形成依赖。
- **修复风险：高。** 快照脱敏涉及配置引用、永久审计、外键、secret intent 和目标重新绑定，不能直接移除主库触发器或无差别删除历史。
- **根因与代码证据：** `migration/http_executor.py:67` 的 `SQLiteArtifactProvider` 备份真实 SQLite 后，在 `:100` 至 `:110` 删除 `search_provider_configs`、`cognitive_resource_keys`、`interaction_transports`、`embedding_resources`、`secret_file_intents`。`PRAGMA foreign_keys=OFF` 不会关闭触发器。`core/database.py:1460` 禁止删除搜索配置，`:7802` 禁止删除 secret intent。
- **影响范围：** 配置过搜索 API、模型密钥或其他通过 secret intent 写入的资源的主体，包括已撤销但仍保留必要历史的配置。
- **触发条件：** 上述表存在记录，通过实际服务接线的 SQLiteArtifactProvider 生成迁移 bundle。
- **触发概率：** 满足记录条件即确定触发。用于全功能运行的部署通常需要这些配置，所以实践相关性高；空数据库/简化测试表不触发。
- **复现：** 使用真实 `Database` schema 和 `SearchProviderStore.configure()`，执行快照得到 `MigrationExecutionError: artifact_snapshot_failed`，原因为 `search provider configs cannot be deleted`。只配置真实 CognitiveResourceStore 也失败，原因为 `secret file intents are append-only`。
- **测试缺口：** `tests/test_migration_http_executor.py:92` 的快照测试使用自行创建的简单表，没有完整 schema 的不可变触发器和依赖记录，因而不能证明实际服务数据库可迁移。
- **建议：立即修复。** 定义明确的“安全元数据保留、密钥不复制、目标重新绑定”合同。保留历史记录身份与引用，只有真实 secret bytes 不进入主体迁移数据；若确需重建配置，必须一致迁移依赖图及目标不可用状态，不能只删几个表。
- **修复验收：** 使用完整 schema，包含模型池及历史路由、搜索资源及研究结果、embedding、通讯与待投递消息、撤销资源、secret intent；恢复后外键和完整性检查通过，旧因果引用可读，未重新绑定密钥时禁止外部调用。

### B03：激活请求、回执字段和摘要的两端合同不一致

- **风险等级：P1。** 即使绕过 B02、完成加密传输，也会被真实 root 激活流程确定性拒绝。
- **修复风险：高。** 激活是 root 与服务权限之间的信任边界，字段不能随意放宽，所有摘要和 binding 必须保留验证。
- **根因与代码证据：** `MigrationAgent.activate()`（`migration/agent.py:1376`）要求 15 个字段，包含 recipient、卷、凭据、signer、钱包证明；在 `:1523` 把该请求交给 activation controller。CLI 实际使用 `TargetActivationBridge`。但 root 的 `_validate_activation_request()`（`migration/activation.py:869`）只接受旧的 9 个字段并检查集合严格相等。
- **第二个独立阻断：** `SQLiteArtifactProvider` 在 `http_executor.py:142` 把 `artifact_sha256` 设为密文摘要，executor `:431` 原样发送；root activator `activation.py:203` 却把这个值与恢复后的明文 SQLite 摘要比较，语义不同。
- **回执也有缺口：** `_ACTIVATION_RECEIPT_KEYS`（`activation.py:852`）仍是旧字段集合，不返回 agent `:1524` 之后验证所需的新增 binding 字段。仅接受请求字段仍不足以让流程成功。
- **影响范围：** 标准加密 bundle → agent → 文件桥接 → root target activator 的接线，不是部署者少填一个配置项。
- **触发条件：** 将标准 agent 的请求交给真实 root 校验器；修复字段问题后，还会遇到密文/明文摘要及回执字段问题。
- **触发概率：** 当前标准接线满足条件即确定触发。各层使用不同 mock/旧格式数据的测试可能分别通过。
- **复现：** 同一份合法基础请求，9 字段校验成功；加入 agent 合同要求的 6 个字段后返回 `TargetActivationError: activation_request_invalid`。使用真实加密 bundle 的密文摘要调用 root activator，则返回 `restored_artifact_digest_mismatch`，模拟 systemd 尚未被调用。
- **建议：立即修复。** 用共享版本化 schema 描述请求和回执，分别定义传输密文摘要、认证明文摘要与激活后数据库摘要。root 暂存副本必须核对被认证的明文摘要；不得通过忽略字段或跳过 hash 校验来“修通”。
- **修复验收：** 完整 executor、真实 agent、真实文件桥接、root activator 和正式回执解析串联测试。可以模拟 systemd/卷探测，但不能把协议接口本身都替换成宽松 mock；再覆盖未知字段、字段缺失、摘要错绑和回执重放。

### B04：主体本地归档和工作区没有进入标准迁移产物

- **风险等级：P1。** 长期主体已归档的记忆/事件可能在迁移后不可读取；工作区产品和文件也不会随主体移动。不是纯粹页面体验问题。
- **修复风险：高。** 文件清单、相对路径、密钥重绑定、对象 hash、空间预算及一致快照必须一起设计，避免迁移“成功”却缺历史。
- **根因与代码证据：** 实际服务 `service.py:1515` 接线的 `SQLiteArtifactProvider` 只快照 SQLite，输出一个加密文件。它不打包 `subject/cold`、工作区或其他引用的主体文件。`EventPayloadArchive`（`core/event_archive.py:101`）将冷 payload 搬到磁盘，只在数据库保留元数据；`EventStore` 在 `core/events.py:390` 根据目标本地目录加载该对象。
- **影响范围：** 开启归档并产生本地冷事件/观测对象的主体、带工作区成果或文件依赖的主体。云对象和归档密钥另有目标可用性要求，不能假设 SQLite 复制会自动满足。
- **触发条件：** 来源存在已从热库移出的本地归档或工作区状态，使用默认迁移 provider 恢复到空目标数据目录。
- **触发概率：** 纯热库、无工作区实例不触发；有本地归档而目标无副本/云恢复证据时确定触发。越长期运行越相关，实际发生频率尚无样本。
- **复现：** 在临时主体通过真实 EventPayloadArchive 归档一个事件，来源 EventStore 可读原 payload；用默认 provider 加密、解密到新目录，保留相同测试归档密钥，目标读取同一 event 得到 `IntegrityError: verified cloud archive metadata is missing`。排除了“只是目标没有密钥”的解释。
- **现有校验局限：** agent 的 restore/health 主要验证 SQLite `quick_check`、主体身份和 artifact，见 `agent.py:1644`、`:1680`、`:1359`；它们不能证明所有数据库外引用对象完整存在。
- **建议：立即修复。** 建立完整迁移清单，包含所有需要保留的本地对象及工作区，或具有可验证目标读取能力的远端对象引用。目标验证所有对象及可解密性后才能 activation；控制面密钥和机器身份按重绑定合同处理，不直接打包所有 `/etc`。
- **修复验收：** 使用有冷事件、冷观测、真实工作区产物和多个旧 key generation 的主体；恢复后验证事件链、归档读取、文件 hash、项目引用及缺一个对象时的拒绝行为。不能把仅 SQLite quick_check 作为完整主体迁移成功标准。

### B05：自主资源发现与迁移提案流程未接入运行时

- **风险等级：P1，重要功能缺口。** 不是已发现的未授权迁移漏洞，而是开启后仍不能实现“Noyra 自己评估可信设备并提出申请”的主要需求。

### B06：发现结果与提案构造器的安全字段不兼容

- **风险等级：P2。** 当前因 B05 尚未接线而不是现成公网攻击入口；一旦直接组合这些库，会将未验证资源当成满足迁移条件。

- **建议：在 B05 接线前立即修复。** 定义统一、严格的已验证候选类型；从注册与观察分别取得卷、资源、成本、时延及验证状态，所有必要字段缺失均拒绝。只能通过可信状态变换生成该类型。
- **修复验收：** 将发现库失败输出直接输入构造器，验证无效签名、过期观察、不可用资源、缺卷证据、成本超限和容量不足都不能提案，而不是仅测试 SimpleNamespace 形式的理想候选。

### B07：拒绝辅助库写入的提案不能被统一管理器校验

- **风险等级：P2。** 可导致提案列表返回完整性错误，并污染迁移控制数据；当前主要是未接线辅助库的兼容问题。
- **修复风险：中。** 必须确定规范哈希、兼容已有记录及拒绝冷却身份，不能为了恢复列表而跳过完整性核查。
- **根因与代码证据：** `MigrationProposalStore.record_rejection()`（`proposals.py:229`）直接插入一条 rejected proposal，其 `state_hash` 只包含部分身份/状态字段；`MigrationManager._proposal_hash()`（`manager.py:585`）还覆盖 evidence、scores、expires_at 和决定字段，`:678` 按此规范验证。两者不一致。
- **影响范围：** 使用辅助 rejection store 的主体；该记录进入 manager 的列表、详情或完整性消费路径。
- **触发条件：** 调用 record_rejection 写入后，用实际服务接线的 MigrationManager 读取提案列表。
- **触发概率：** 满足条件即确定发生；当前正常管理台拒绝使用 manager 自己的路径，因此不要泛称“管理台所有拒绝都会坏”。
- **复现：** 完整 schema、合法登记目标和启用策略中调用 record_rejection；随后 `MigrationManager.list_proposals()` 返回 `ValueError: migration proposal integrity check failed`。
- **建议：在 B05 接线前修复。** 提案/拒绝写入统一到一个状态机及规范序列化；辅助类只调用统一合同。已有这种格式的数据如需兼容，应采用显式可审核转换，保留原始证据。
- **修复验收：** 所有提案和拒绝写入入口产出的记录均可被同一管理器及完整性检查读取；拒绝后改提案文字/幂等键不能绕过冷却。

### B08：容量已满时阻断待发送消息

- **风险等级：P2。** 可能出现“消息已接受或回复已决定，但一直发不出去”，包括首次发送和失败重试。

### B09：证据容量并没有覆盖 embedding 和心跳的增长

### B10：容量检查的成本随历史规模线性增长

- **风险等级：P2，性能和可用性。** 不构成已证明的访问权限绕过；大库或高频工作会增加运行延迟和 SQLite 写锁占用。
