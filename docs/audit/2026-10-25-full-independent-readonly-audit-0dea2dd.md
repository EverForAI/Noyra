**触发条件**

- 登录入口可达；未登录请求在一分钟内耗尽 `admin_login_rate_limit_per_minute` 后再发送一次。默认 5 次预算，即第 6 次触发；本轮把临时实例阈值设为 2，以第 3 次复现同一分支。
- 或管理员正常进行表中维护操作；或启动时恢复既有隐私意图。

### A02：申请撤回没有贯穿主动社交的来源选择及提交复核

**问题风险：P2。修复风险：中。置信度：高。归因：原生/存量，不是上轮新引入。**

**位置**：[撤回业务](<E:/我的项目/Noyra/开发版/src/noyra/interaction/collaboration.py:548>)、[共享撤回判定](<E:/我的项目/Noyra/开发版/src/noyra/core/private_sources.py:18>)、[社交消息查询](<E:/我的项目/Noyra/开发版/src/noyra/cognition/social.py:258>)、[路由验证](<E:/我的项目/Noyra/开发版/src/noyra/cognition/social.py:462>)、[提交前复核](<E:/我的项目/Noyra/开发版/src/noyra/cognition/social.py:565>)。

**根因**

直接邀请认知使用 `WITHDRAWN_PARTICIPANT_INVITATION` 和 invitation scope 阻止撤回后继续处理。主动社交采用另一条历史消息/冻结路由链，仅检查身份、会话删除、transport 和 binding；没有检查该邀请所属申请是否已经 withdrawn。提交前再次调用 `_route()` 也重复同一遗漏。仅复核路由可达不能代表原业务邀请仍有效。

**触发条件**

账户发出协作申请，由此产生 incoming 邀请，形成已知关系；申请撤回时这条消息仍是最近可用来源。社交审阅到期并选择该关系。撤回可发生在模型调用前，也可发生在调用中。

**影响**

直接调度器正确忽略原邀请，但主动社交仍生成一条以原邀请为 `related_interaction_id` 的 outgoing，并呈现给参与者。产生不必要模型开销和撤回后继续回应。复现只生成本地消息，没有执行外部投递。

**独立证据**

两个独立临时实例分别在调用前和 FakeProvider 响应中撤回；两者均得到：

```json
{"application_status":"withdrawn","direct_scheduler_has_invitation":false,
 "result":"relationship_social_contact","provider_calls":1,
 "outgoing_related_to_withdrawn_source":true,"external_delivery":false}
```

全部申请、关系、消息和撤回通过实际业务接口形成，无伪造 source 或 idempotency key。

**归因**

共享撤回保护与社交链的分离在基线已存在；路由验证主体来自较早 `24aa46b`。上轮 `324870b` 扩大候选可见范围，但没有创建“withdrawn 不检查”的规则。应标记原生缺口；新覆盖会让原先被排序遮挡的联系人进入此旧路径，但不是根因新增。

**修复建议与边界**

候选来源过滤和提交前使用同一邀请有效性判断；如已发送则依现有结算保留调用/费用，不自动新建请求身份重试。撤回某次申请不等于撤销整个账户所有交流：存在独立、仍有效的新邀请时，应允许按那个真实来源处理，不能把联系人永久设为 no_contact，也不能静默改投其他房间。

**验收**

调用前、await 期间、提交前撤回都不再关联原邀请生成回复；独立新消息正常；旧状态与新消息身份不混合；未知费用和审计不删除。

### A03：有界返回不等于有界执行，新候选查询放大历史扫描

**问题风险：P2。修复风险：中。置信度：高。归因：上一轮修复引入的次生性能问题，提交 `324870b`。**

**位置**：[候选 keyset 页](<E:/我的项目/Noyra/开发版/src/noyra/cognition/social.py:185>)、[每个候选的 interaction 查询](<E:/我的项目/Noyra/开发版/src/noyra/cognition/social.py:258>)、[社交进入认知调度](<E:/我的项目/Noyra/开发版/src/noyra/cognition/cycle.py:577>)、[现有 interaction 索引](<E:/我的项目/Noyra/开发版/src/noyra/core/database.py:1256>)。

**根因**

最多 64 个关系，每个执行一次 `interactions LEFT JOIN participant_message_links`，再用 `m.entity_id=? OR (m.interaction_id IS NULL AND i.counterparty=?)` 筛选。现有主扫描索引仅以 subject/time 排列。对无历史或很久未联系的对象，SQLite 仍须从全局 interaction 历史逐条查 link 后才能确认找不到目标；`LIMIT 48` 约束返回条数，不约束扫描条数。

单次还会为每个候选创建/关闭数据库连接。没有 SQL 步数/时间中断预算。该同步方法在 async 认知路径中执行，期间不能让出事件循环。

**触发条件**

较多高优先级联系人缺少路由，主体累计大量无关 interaction；社交策略进入审阅。并非声称它必然每个 tick 执行；实际频率受调度和社交策略影响。

**影响**

耗时随联系人候选数乘以全局历史增长；长期小内存实例可能出现明显 tick 延迟、HTTP/维护竞争和 CPU 成本。没有发现额外付费模型请求：无可用上下文时仍为零次。

**独立真实业务比较**

用真实业务写入 10,001 条 interaction、64 个高优先级无路由关系及一个较低优先级合法关系；只监测数据库连接和 VM progress，不改查询。将 `6a742e5` 的原类从 Git 读到临时文件后，在同一库比较：

| 实现 | 实测耗时 | 连接数 | 约 SQLite VM 指令数 | 模型请求 |
| --- | ---: | ---: | ---: | ---: |
| 上轮之前 6a742e5 | 0.076 秒 | 3 | 34,000 | 0 |
| 当前 0dea2dd | 2.754 秒 | 66 | 12,824,000 | 0 |

两者该轮均返回无上下文：当前是在推进续页，旧版则会持续遮挡后项。**比较说明当前计算成本明显增加，不主张恢复旧版的候选饥饿错误。** 时间受本机并发测试和硬件影响，不能外推为所有服务器固定耗时。

另用相同 SQL/索引的隔离微基准测 64 个无匹配候选：1,000/10,000/100,000 行约执行 121.7 万/1,216.1 万/12,160.1 万条 VM 指令。EXPLAIN 使用 subject/time 索引后再查 link，没有以目标 entity 作为主检索入口。

**修复建议与风险边界**

保留续页与来源隔离。拆分已归属参与者查询与未归属 legacy 查询，设计支持 entity/legacy counterparty 加时间排序的索引；避免 OR 把两路都退化成全局扫描。增加执行预算及可恢复续查，而非仅限制结果数。索引/schema 改动需验证迁移与 DDL 契约；不能为了提速按昵称合并身份或取回全局私密消息给模型。

**验收**

13/80+ 联系人行为不退化；相同未命中联系人在扩大全局历史时，查询计划和 VM 计数不按全局行数线性放大；有固定预算；撤销、重启与路由冻结回归仍通过。

### A04：内生目标来源标签可以改变而不触发心智完整性告警

**问题风险：P2。修复风险：中至高。置信度：高。归因：原生/存量。**

**位置**：[GoalStore 读取与状态哈希](<E:/我的项目/Noyra/开发版/src/noyra/mind/goal.py:405>)、[哈希字段](<E:/我的项目/Noyra/开发版/src/noyra/mind/goal.py:454>)、[目标修订核验](<E:/我的项目/Noyra/开发版/src/noyra/mind/engine.py:415>)、[治理 origin 门禁](<E:/我的项目/Noyra/开发版/src/noyra/cognition/governance.py:182>)、[研究 origin 门禁](<E:/我的项目/Noyra/开发版/src/noyra/cognition/research.py:473>)。

**根因**

目标哈希包含标题、描述、状态、优先级、承诺、进度、情感压力，却不包含 origin。goal_revisions 也没有 origin 历史字段，MindEngine 只比较这套哈希与修订号。数据库 CHECK 仅保证 origin 属于合法枚举，不能证明它与创建来源相同。

origin 又实质决定目标能否进入治理、研究、行动、项目、自我模型等模块，不是无关展示字段。

**触发条件与攻击面界限**

持久化目标的 origin 被误改、导入/修复/恢复路径写错，或具备直接数据库写权限的主体修改其合法枚举值。**没有确认普通 HTTP 用户能直接写该字段**；本项是已承诺的耐久状态完整性覆盖缺口，不是远程 SQL 注入。

**影响**

**复现**

`git blame` 显示哈希遗漏早于上一轮修复（可见历史根 `13a3cb7`），不是 `197c6b6` 等新引入。

**建议与修复风险**

把不可变创建来源绑定到可核验的持久证据：可用版本化哈希及创建/来源记录，或独立不可变 origin 见证，并与所有读取者一致校验。历史迁移不能简单对当前值重新计算哈希并宣称“已验证历史来源”；无法证明的旧状态应明确标识可信边界。避免把新增保护变成可由管理员直接强制改写目的的入口。

**验收**

单字段合法枚举变化必须被发现；正常创建/接受/激活/修订/迁移通过；原有同主体因果与来源约束不退化；历史兼容不造成全库误停。

### A05：Windows 新恢复记录失败后不能完成安全、可重试的安装

**问题风险：P2。修复风险：中。置信度：高。归因：次生异常恢复路径，兼有既有发布流程缺口。**

**位置**：[已存在版本直接拒绝](<E:/我的项目/Noyra/开发版/deploy/windows/noyra-lifecycle.ps1:444>)、[恢复记录写入](<E:/我的项目/Noyra/开发版/deploy/windows/noyra-lifecycle.ps1:119>)、[先搬入 target 再保存记录/信任/指针](<E:/我的项目/Noyra/开发版/deploy/windows/noyra-lifecycle.ps1:469>)、[失败只清 staging](<E:/我的项目/Noyra/开发版/deploy/windows/noyra-lifecycle.ps1:481>)。

**根因**

先把 staging 移入 `versions/<version>`，再写新增恢复记录。记录写入失败，finally 只尝试清理已不存在的 staging，未撤销刚提升的 target，也没有可恢复安装 intent。再次执行同版本 install 时，代码看到 target 存在就返回 `Version already installed`，不区分已激活版本和未完成安装遗留。

**触发条件**

新恢复记录路径不可用（例如残留同名目录）、权限失败、磁盘写入或原子改名失败，发生在 target 已提升后。第一次全新安装及后续升级都可能遇到；旧当前版本在这条失败路径中仍保留，不是已验证的数据丢失或运行版本被覆盖。

**原生/次生区分**

旧流程在保存发布者策略等后置操作失败时也可能遗留 target；这是已有的非原子发布弱点。但本轮具体复现的 `verification-policy.<version>.json` 新写入步骤由 `3f930ba` 增加，`004f7c2` 调整顺序后只保护信任策略，没有解决目录遗留。故标为“上一轮新增异常路径的次生恢复问题”，不声称所有 target 遗留都是上一轮才产生。

**本轮 Windows 原生证据**

复用当前回归中的合法内存 CMS 包和恢复记录路径被空目录占用的失败场景；保留外部 A 策略、尝试安装 B。测试首先证明原信任策略未变化且 current 未发布。随后仅删除已核对位于临时目录中的空阻塞目录，再用正确许可名单重试：

```json
{"target_remains_after_failed_install":true,"pointer_published":false,
 "blocking_receipt_directory_repaired":true,
 "retry":"Version already installed: signed-b3"}
```

没有递归删除安装目录，没有修改系统证书库，没有执行 launcher。

**建议与风险边界**

给提升/记录/策略/指针加入明确的恢复协议，或在确认只有本次操作创建且未发布时安全撤销遗留 target。恢复采用已有目录时必须重新验证精确清单、签名、版本与安装意图，不能只因名称相同就信任，也不能删除已经被 current/previous 或运行进程引用的版本。

**验收**

注入恢复记录、信任文件及指针发布阶段失败；原当前版本和信任策略按约定保留；修复外部故障后同版本可安全重试；实际被引用旧版本不被清除；证书撤信与路径保护继续拒绝非法包。
