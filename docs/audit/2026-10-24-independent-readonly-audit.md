## 5. 逐项发现

### A01：合法长消息能够持续阻塞认知队列

**风险：P1。修复风险：中。**

**代码证据：**

- `src/noyra/interaction/collaboration.py:256-276`：私信允许最多 10,000 字符并以 offered 入库。协作意向允许 20,000 字符，也会形成 incoming interaction。
- `src/noyra/interaction/store.py:351-355`：底层允许最高 100,000 字符。
- `src/noyra/cognition/interaction.py:69-86`：选中消息后先执行 `_messages`，只专门捕获 `PermissionError`。
- 同文件 `:224-237`：按优先级及时间持续选择 offered/deferred 消息。
- 同文件 `:277-297`：把完整消息交给记忆检索，即使稍后会清空检索结果。
- `src/noyra/mind/memory.py:272-274`：检索查询超过 4,000 字符直接抛出 `ValueError`。

**根因：** 入库长度与认知消费长度没有统一契约；单条数据的确定性异常也没有从队列中隔离。异常发生在模型调用和消息决策之前，消息仍为 offered。

**触发条件：** 认知已启用，收到超过 4,000 字符的合法私信、渠道消息或意向；该消息成为当前调度候选。4,001 字符即可触发，无需超大请求或管理权限。

**影响：** 同一消息可被反复选中并再次异常，后面的普通消息无法正常获得处理机会；本轮认知流程在该阶段之后的工作也可能无法执行。不能据此声称所有认知模块必然完全停止，因为部分模块在此前运行。

**复现：** 临时库通过真实 `ParticipantCollaboration.write` 写入 4,001 个字符，令此前消息正常结束，确认 `_due_interaction()` 选中该消息；两次调用真实 `run_due()` 均得到：

```text
ValueError: memory recall query must be nonblank and bounded
interaction.status = offered
normal follow-up status = offered
same interaction selected again = true
```

复现没有调用模型。Git 归属显示完整文本传入 recall 的语句是存量代码，新增账户接口扩大了其暴露面，不能将整个问题都归咎于本轮新增代码。

**根因修复方向：** 明确传输、存储、检索查询与模型上下文各自的长度契约；允许长正文存在时，用有界检索查询或直接跳过不需要的检索。对已经入库的异常消息设置可审计的隔离/调度恢复机制，不能只限制新表单或笼统吞掉异常后继续选择同一行。

**回归要求：** 4,000/4,001/10,000 字符、多字节文本、较长意向前缀、已有长记录；异常记录在前、正常记录在后的队列推进；不把隔离记作 Noyra 的自主拒绝，不产生重复正式调用。

### A02：账户回复会让外部渠道发送队列停滞

**风险：P1。修复风险：中。**

**代码证据：**

- `src/noyra/interaction/collaboration.py:267-275`：账户私信采用内部 `participant` 渠道。
- `src/noyra/cognition/interaction.py:141-150`、`src/noyra/interaction/store.py:106-145`：回复沿用该渠道，记录为 outgoing/sent。
- `src/noyra/interaction/transport.py:1224-1231`：先取没有 delivery 的 outgoing 记录并 LIMIT；只排除特定 web 记录，没有排除内部 participant 消息。
- 同文件 `:1272-1279`：找不到外部 transport 后直接 continue，不创建终态标记或推进候选游标。
- 同文件 `:1382-1388`：实际后台默认批次为 10，入队也使用这个限制。
- `src/noyra/service.py:11630`：服务按默认限制调用 `deliver_pending`。

**根因：** 候选 LIMIT 发生在“是否需要且能够走外部渠道”判断之前。账户回复本来已通过页面供接收者读取，却不断成为外部待发送候选。它们永远没有 transport，也永远不会退出该候选集合。

**触发条件：** 同一实例积累 10 条排在其他消息之前的账户回复。使用 `enqueue_pending` 默认 50 时阈值是 50；实际服务默认是 10。类似的停用/无可用 transport 积压也需要一起考虑。

**影响：** 后续 Telegram、邮件或 webhook 等消息可能没有任何 delivery 记录，不会进入后续发送和重试步骤。服务仍运行，页面回复也存在，所以单看“sent”或进程健康难以识别这一阻断。

**复现：** 合成账户写入 10 条内部回复，配置一个有效的合成 webhook transport，再创建一个更晚的 webhook outgoing。连续两次运行 `enqueue_pending(subject, limit=10)`：

```json
{"queued":[0,0],"native_delivery_count":0,"participant_outgoing":10}
```

作为正向对照，把同一次扫描的 limit 临时设为 11，立即创建 1 条外部 delivery，排除了 transport 本身不可用的解释。增大 limit 仅用于诊断；积累更多内部回复后仍会再次堵塞，不能作为根因修复。只执行入队，没有触发网络发送。

**根因修复方向：** 在数据/调度契约上区分内部页面交付与外部渠道交付；批次限制应约束符合交付条件的消息，而不是先让不具备交付目标的记录占满窗口。对于暂时不可投递的记录保留正确状态并允许扫描继续，不能冒充 delivered，也不能为了绕开积压而改用另一个机器人账户。

**回归要求：** 10 条内部回复后仍可入队一个原渠道回复；不可用渠道在前、可用渠道在后；多个 bot/app 的来源绑定；内部消息不创建外部 delivery、不访问任何 provider；有界扫描与旧记录兼容。

### A03：撤回意向与认知邀请没有形成状态闭环

**风险：P2。修复风险：中至高。**

**代码证据：**

- `src/noyra/interaction/collaboration.py:341-377`：同一事务创建申请和 offered 邀请，但申请没有保存明确的 interaction 关联字段。
- 同文件 `:413-423`：撤回只更新 `participant_applications.status`。
- `src/noyra/cognition/interaction.py:224-237`：候选查询不检查申请是否已撤回。
- `src/noyra/core/participant_schema.py:64-70`：申请状态仅 submitted/withdrawn，无邀请的明确外键。

**根因：** 写入时创建了两个业务对象，撤回时只改变其中一个；调度器无法从自己的候选规则判断原邀请是否仍然有效。

**触发条件：** 用户提交意向，在 Noyra 处理前撤回；或撤回与模型处理并发。

**影响：** 页面显示已撤回，但原意向仍可能消耗认知机会、调用预算并收到后续回应。该路径本身不会自动创建付款订单，不能夸大为已经发生支付。

**复现：** 真实 apply → withdraw → `_due_interaction()`：

```text
application.status = withdrawn
selected interaction.status = offered
selected content = Collaboration interest [bounty_...]: I can help
```

**根因修复方向：** 建立申请与邀请的稳定关联，并在同一事务处理撤回与可调度性；消费前及结果提交前复核撤回状态，清楚定义正在处理时的行为。用户撤回不能被伪造成“主体自主 rejected”；已经接受的成果和付款仍必须由原钱包状态机决定。

**修复风险来源：** 现有记录需关联回填；还涉及模型已发送、结果尚未提交的竞争窗口。单纯补一个 UPDATE，可能把处理中的邀请和账务证据改坏。

**回归要求：** 提交前后重复撤回、跨账户撤回、撤回后不再调度、处理中撤回、历史关联回填；原子提交与失败回滚；不会通过意向撤回取消已接受成果或既有支付。

### A04：未读通知会被较新的普通记录挤掉

**风险：P2。修复风险：中。**

**代码证据：**

- `src/noyra/interaction/collaboration.py:106-159`：各 owned 视图按记录创建时间倒序返回首批最多 50 条。
- 同文件 `:186-221`：通知只读取这些视图的第一页，然后过滤 pending 或 incoming。
- 同文件 `:438-442`：标记已读也只接受当前这个窗口内的通知。

**根因：** “最近创建的业务对象”被当成“应展示的通知”。先 LIMIT 再筛选，因此已读状态、后续审阅或付款变化都不能保证通知仍可见。

**触发条件：** 一个未读回复之后有 50 条较新 incoming 消息；或者一个旧成果后来付款，而已有 50 个更晚创建的成果/留言。

**影响：** 通知无须被读过就会消失；旧成果的新的审阅或支付进展可能从来不出现在通知区。底层业务记录仍在，不能说它已被删除。

**复现：** 先创建一个账户私信和对应回复，通知数为 1；随后创建 50 条 incoming 消息。通知数变为 0，旧回复状态仍为 sent，没有任何 notification-read 记录。

**根因修复方向：** 以通知事件或业务状态变更为查询对象，先按接收者和通知条件筛选，再排序和分页；采用稳定事件标识，保证旧对象的新变化可以成为新通知。不要通过无上限扫描整个消息历史解决。

**回归要求：** 51 条以上混合方向消息、旧成果新付款、仅 pending 对象占满首页、超过 100 条通知的分页、跨账户隔离、已读幂等与状态变化生成新通知。

### A05：成功请求的幂等重试会受后续业务状态影响

**风险：P2。修复风险：中。**

**代码证据：**

- `src/noyra/interaction/collaboration.py:315-340`：先要求 bounty 仍 published/open，再查询申请幂等键。
- 同文件 `:322-327`：总容量先于已有申请的查询。
- 同文件 `:258-266`：私信也先检查容量再进入底层已有记录查找。
- `src/noyra/wallet/economy.py:379-398`：底层成果提交也先检查开放状态，再查已有提交。

**根因：** “创建新记录的准入规则”与“确认已经完成的相同请求”混在一起，导致已有收据的返回依赖于重试时的状态。

**触发条件：** 首次请求已经提交，但响应未被客户端确认；随后悬赏关闭/过期，或容量达到上限；客户端以同一幂等键、同一内容重试。

**影响：** 服务端记录真实存在，客户端却收到失败，容易出现结果误判和换新幂等键重试。没有复现重复支付，不应将该问题描述为支付幂等已经失守。

**复现：** 首次 apply 成功，记录 application_id；关闭 bounty，再发送完全相同的 payload：

```text
ValueError: collaboration_not_open
existing application still present
```

容量路径的顺序由代码确认，未为达到上限而在复现库灌入 10,000 条记录。

**根因修复方向：** 在验证当前身份、归属及输入指纹后，先处理已有幂等收据；只有确实需要新建时才执行开放状态和容量准入。不同内容重用同一键仍须拒绝，不能返回别人的记录，也不能因一次幂等重试重新触发工作流或付款。

**回归要求：** 创建后关闭/过期、达到容量后重试、撤回后重试、修改内容重用键、并发同键、跨账户同键；验证只返回原结果且无第二条业务副作用。

### A06：不会进入模型上下文的记忆仍被计为已使用

**风险：P2。修复风险：低至中。**

**代码证据：**

- `src/noyra/cognition/interaction.py:277-297`：先执行 recall 并构造结果，随后对有 participant 归属的消息清空结果。
- `src/noyra/mind/memory.py:261-270,376-384`：recall 默认 `record_access=True`，会持久化所选记忆的访问。
- 同文件 `:333-346`：访问计数参与后续检索评分。
- `src/noyra/mind/retrieval.py:188-199`：当该 store 配置 embedding_index 时，召回还可能进行 query embedding。

**根因：** 隐私筛选只作用于最后的 Python 列表，没有阻止前面的查询和访问副作用。准备上下文与使用记忆的语义也没有区分。

**触发条件：** 有明确 participant 归属的消息，库中存在可召回记忆。即使最终没有模型预算，`_messages()` 仍先运行。

**影响：** 未实际用于回应的记忆被记录为已访问，后续相关性、使用记录和写入负担失真。复现确认的是数据库副作用；当前默认 `InteractionCognition` 构造的 MemoryStore 没有自动配置 embedding_index，因此不把付费 embedding 消耗写成现网已确认事实。也未发现被清空的他人记忆实际进入该消息的模型上下文。

**复现：** 为临时主体创建一条可召回记忆；执行账户消息的 `_messages()`：

```json
{"access_before":0,"access_after":1,"context_has_memory":false}
```

**根因修复方向：** 在决定可使用的来源/记忆集合之后才执行检索；无需检索的明确分支直接跳过。若未来允许归属内记忆，应先过滤候选，再计算和记录实际使用，不要先全局召回再清空。

**回归要求：** 有归属账户不召回被排除记忆、不创建访问记录、不调用 embedding；保留已经授权的会话历史；无主体归属的旧入口按明确兼容策略工作；预算耗尽时不反复伪造访问。

### A07：协作机会缺少字节预算与可继续读取的分页

**风险：P2。修复风险：中。**

**代码证据：**

- `src/noyra/interaction/collaboration.py:30-54`：一次取最多 50 个 published bounty，返回完整 description/criteria。
- `src/noyra/wallet/economy_types.py:49-81`：description 最多 20,000 字符，criteria 最多 32 项、每项最多 2,000 字符，属于合法业务数据。
- `src/noyra/interaction/participant_http.py:20-24`：整包超过 2,000,000 字节，替换为 HTTP 413。
- 同文件 `:145-146` 与 `src/noyra/web/participant.js:215-226`：机会接口及页面没有 next_cursor 继续读取机制。

**根因：** 只有条数上限，没有对 UTF-8 结果包施加列表字节预算；通用响应兜底会把整个列表替换为错误，而不是生成仍可浏览的页面。

**触发条件：** 若干个较详细的合法悬赏，尤其中文或其他多字节文本。超过 50 个开放项目时，较旧项目本身也没有这个页面的分页入口。

**影响：** 协作入口整页无法展示，合法用户只能得到通用失败；重试无效，因为读取的数据没有改变。

**复现：** 创建并发布 34 个完全符合 BountyInput 约束的合成悬赏，每项 description 为 20,000 个汉字，criteria 只有一个短字符串；单条创建 payload 按 UTF-8 JSON 序列化小于默认 100,000 字节请求限制。测试用 GoalStore 正常生成合成目标及修订，没有靠破坏目标哈希或关闭数据库约束构造输入。真实本地 HTTP 请求结果：

```json
{"published":34,"serialized_bytes":2057817,"http":413,"body":{"error":"participant_response_too_large"}}
```

**根因修复方向：** 机会列表采用明确的条数和 UTF-8 字节预算，返回稳定游标；前端支持继续阅读。也可设计受限摘要与单条详情，但不能静默截掉验收条件导致参与者误解约定。一般单项大小仍可单独限制，保留整包兜底。

**回归要求：** 多字节大条目、超过 50 条、同时间戳、翻页期间状态变化、单项超限、分页无遗漏/重复、金额和验收条件完整性。

### A08：账户发帖没有保留验证码错误的恢复契约

**风险：P3。修复风险：低。**

**代码证据：**

- `src/noyra/interaction/posts.py:27-32`：PublicPostCaptchaError 是 ValueError 的子类。
- `src/noyra/interaction/collaboration.py:280-313`：正确提交失败尝试计数后重新抛出该异常。
- `src/noyra/interaction/participant_http.py:243-260`：未单独转换该异常，最终变为 invalid_participant_request。
- `src/noyra/service.py:5952-5953`：匿名发帖保留 invalid_captcha 专用错误。
- `src/noyra/web/app.js:1549-1558`：只有 invalid_captcha 会自动刷新验证码。

**根因：** 新适配层没有保留原公开发帖接口的错误类型契约。

**触发条件：** 已登录账户提交错误、过期或失效验证码。

**影响：** 用户看到一般填写错误，无法得到专用解释，前端也不会执行既有自动刷新分支；手动刷新仍可恢复。验证码校验和失败计数本身仍有效，没有绕过验证码。

**复现：** 真实账户登录后，从本地接口取得 challenge，再以 WRONG 发帖：HTTP 400，`{"error":"invalid_participant_request"}`。

**修复方向与回归：** 在通用 ValueError 之前保持专用错误映射，统一两条发帖路径；验证错误、过期、重放、正确重试与计数持久化，不因调整错误响应而回滚已经记录的失败尝试。

### A09：KDF 并发限流被解释成凭据错误

**风险：P3。修复风险：低。**

**代码证据：**

- `src/noyra/interaction/accounts.py:23-28`：AccountRateLimited → AccountError → ValueError。
- 同文件 `:35-39`：KDF 槽位满时抛 AccountRateLimited(authentication_busy)。
- 同文件 `:50-55`：password_matches 的 `except (ValueError, TypeError)` 把它捕获并返回 False。
- 同文件 `:133-135,293-294`：login 和修改密码把 False 转成 invalid_credentials。
- `src/noyra/interaction/participant_http.py:247-250`：若异常正常传播，本来会得到 429；实际被转换成 401。

**根因：** 密码编码错误与基础设施繁忙共用 ValueError 继承链，宽泛捕获掩盖了限流语义。

**触发条件：** 同时有两次 KDF 计算占用全局槽位，第三次登录/当前密码校验进入 password_matches。

**影响：** 正确密码被显示成错误，容易造成无效重试或不必要恢复；本次没有发现因此接受错误密码或泄漏凭据。

**复现：** 正常计算正确密码的合法 digest，暂时占用两个槽位，再调用 `password_matches(正确密码, 合法 digest)`，结果 False。不是用一个错误 digest 冒充正确密码测试。

**修复方向与回归：** 显式让限流异常在校验错误处理前传播，保持 HTTP 429 和相应解释；同时确认错误密码仍返回 False、注册/恢复的 KDF 限制仍生效，并发上限没有扩大。

### A10：付款状态显示未对齐后端状态机

**风险：P3。修复风险：低。**

**代码证据：**

- `src/noyra/wallet/economy_types.py:17-30`：真实状态包含 awaiting_confirmation、signing、expired、refunded。
- `src/noyra/web/participant.js:132-153`：定义的是并不存在于该枚举的 pending_confirmation；缺少另外几个实际状态，直接回显内部英文。
- 同文件 `:260`：通知也使用同一状态函数。

**根因：** 页面手写枚举没有与后台 PaymentOrderStatus 保持一致，提交审核和付款状态还共用部分词语。

**触发条件：** 付款订单进入等待确认、签名中、过期或退款等状态，并出现在“成果与报酬”或通知中。

**影响：** 中文页面出现 awaiting_confirmation 等内部值，参与者无法从页面清楚理解是否还需确认、正在发送还是已终止。属于解释能力问题，不改变后台支付策略。

**复现：** 使用 Node VM 执行当前脚本的真实 status 函数，在 zh-CN 下，awaiting_confirmation、signing、expired、refunded 均原样返回；pending_policy、reserved、confirmed 等已有映射正常。

**修复方向与回归：** 根据真实付款枚举补齐中英文解释；必要时按业务类型区分“投稿未采纳”和“付款被拒绝”。以完整状态枚举验证所有状态，而不只检查几条页面文案，不把 awaiting_confirmation 误呈现为已支付。

## 7. 建议的根因修复顺序与安全边界

1. **先处理 A01 与 A06（消息消费和记忆使用）。** 统一长度契约并确保异常记录不会永久占据队首；在检索前完成来源判断。不能通过减少用户可写正文长度掩盖已有记录问题，也不能把技术隔离伪造成主体自主拒绝。

4. **处理 A04、A07（通知和公开列表）。** 使用有界查询、稳定游标和字节预算。只返回原来允许公开或本人拥有的字段，不能为分页便利读取其他参与者的私信。
