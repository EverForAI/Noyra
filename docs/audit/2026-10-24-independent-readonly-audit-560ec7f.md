## 4. 逐项发现

### B01：密码恢复完成后，旧会话仍可在并发窗口生成新凭据

**风险 P1；修复风险中。**

**代码证据：**

- `src/noyra/interaction/participant_http.py:130-132`：解析请求前读取身份。
- 同文件 `:219-223`：Cookie/CSRF 的第二次校验完成后，执行限流，再进入具体操作。
- 同文件 `:236-243`：创建凭据只把此前取得的 Participant 传给 AccountStore.api_key，没有把当前 session 或授权代次传入写事务。
- `src/noyra/interaction/accounts.py:229-255`：恢复事务更新密码并删除全部会话和程序凭据。
- 同文件 `:257-285`：api_key 的写事务只根据 entity_id 找账户，不再检查调用它的会话是否仍有效。

**根因：** 校验会话和生成新凭据使用不同事务，Participant 对象变成一个可在撤销之后继续使用的授权快照。恢复事务删除已有行，但不能识别尚未提交的新凭据操作。

**触发条件：** 一个拥有有效会话和 CSRF 的请求通过检查后尚未进入凭据写事务；另一个请求在此期间完成恢复或撤销，再由旧请求继续生成凭据。复现针对密码恢复；不需要猜测密码或绕过 CSRF。攻击场景需要攻击者已取得一个会话，风险在于恢复动作未能可靠切断其持久访问。

**影响：** 用户恢复密码后看到所有旧会话和凭据已删除，但旧会话对应的在途操作又创建一个可用的新 bearer，继续读取该账户私信/成果或代表该账户提交内容。该凭据仍是 participant 权限，没有取得管理员或付款权限。

**本地复现：**

1. 正常注册 Alice 并通过 HTTP 登录。
2. 发起真实 `/api/participants/credential` 请求，在原限流操作完成后用 Event 暂停该线程，保持身份与 CSRF 检查已完成。
3. 从另一线程调用同一真实账户恢复逻辑，确认会话行数和凭据行数均为 0。
4. 恢复原请求，读取它返回的新凭据，再用它访问本人消息接口。

```json
{
  "http_status": 200,
  "sessions_after_reset": 0,
  "keys_after_reset_before_release": 0,
  "key_created_after_reset": true,
  "created_key_authenticates": true,
  "new_key_login_status": 200
}
```

Event 只控制线程调度，不替换鉴权结果、会话内容或数据库检查；没有输出原始凭据。

**根因修复方向：** 在生成/轮换凭据的同一个写事务内，复核发起操作的 session、CSRF 及有效授权代次。恢复、修改密码、退出和凭据操作必须共享明确的撤销线性化边界。可以使用事务内会话检查或账户授权代次，不能只在 HTTP 入口增加一次无事务检查，也不能依赖客户端主动清 Cookie。

**修复边界：** 不要跨 KDF、请求体读取或网络 I/O 持有长数据库写锁；已有 API key 的正常轮换和失效语义需要保留；旧 Participant 对象不能直接充当无限期授权。

**回归要求：** 恢复/修改密码/退出与凭据创建竞争；授权先提交与撤销先提交两种顺序；账号禁用；不同账户隔离；被撤销的在途 API 写请求是否还允许提交，需要明确统一语义。断言撤销先提交时不能产生恢复后仍可使用的凭据。

### B02：社交回复目的地在生成之后被另一条消息改变

**风险 P1；修复风险中至高。**

**代码证据：**

- `src/noyra/cognition/social.py:149-200`：从当时的消息快照建立联系人和渠道。
- 同文件 `:237-285`：模型上下文只保留 relationship 和 channel；_SocialContext 没有冻结具体的入站 source、interaction、conversation 和目的地址。
- 同文件 `:90-116`：在模型 await 前后，分别构造上下文和提交。
- 同文件 `:367-380`：提交时重新查询该联系人的最新 incoming，只有 channel 相同就采用它的 counterparty 和 interaction_id。
- 同文件 `:383-395`：以重新选择的地址和关联消息写入 outgoing。
- `src/noyra/interaction/store.py:330-347`：回复归属继承重新选择的关联消息。
- `src/noyra/interaction/transport.py:1255-1275`：外部交付再依该关联消息选择原 transport；因此 transport 正确不能保证 conversation 仍是模型面对的原会话。

**根因：** 稳定联系人身份与具体交付会话被混为同一层路由。模型生成期间的新入站消息可改变最终地址，而提交校验只比较渠道名称，没有比较原会话和来源版本。

**触发条件：** 同一个已识别联系人在同一渠道的多个会话联系实例；主动社交模型调用尚未结束时，另一个会话的新消息到达。私聊转群聊、一个群转另一个群都可能满足；即使仍是同一个机器人，也不能把两处会话视为同一保密范围。

**影响：** 为原会话准备的内容被记录并排队到新会话；原私聊的内容若被生成进回复，可能被发送到更多接收者可见的群组。可以确认的是错误会话入队，不把它夸大为生产环境已经外发。

**本地复现：** 配置一个合成 webhook transport，明确绑定同一账户和发送者，使用真实 InboundStore.ingest 在 `original-conversation` 接收首条消息。合成 provider 记录它收到的上下文，随后在返回模型结果前通过同一真实入站链路接收 `new-conversation` 的消息。返回合法 contact 结果，再只执行 enqueue_pending：

```json
{
  "model_context_original_conversation": true,
  "model_context_new_conversation": false,
  "result": "relationship_social_contact",
  "actual_outgoing_destination": "new-conversation",
  "deliveries_queued": 1,
  "queued_transport_is_original_bot": true,
  "queued_destination": "new-conversation"
}
```

关联的 interaction_id 也变成模型上下文里不存在的新消息。没有调用任何外部发送接口。正向对照中不插入新会话消息，其他路径保持相同，结果正确入队 original-conversation，排除了原 transport 不可用或基础配置错误的解释。

**根因修复方向：** 把实际交付来源、会话和关联入站消息作为社交决策的冻结路由上下文。提交时按冻结标识检查归属、权限和可用性；有新消息时不能自动重定向已有内容。原来源撤销时应取消/重新评估，不能改投另一个地址或机器人。

**修复边界：** 同一联系人可以具有多个来源，这不代表其所有会话都获准共享内容；应保留原 transport 绑定和既有回复选择器。历史无 participant 归属的记录也需要兼容，不能以强行合并历史身份解决。

**回归要求：** 模型等待期间从私聊切换群聊、同渠道不同会话、同人不同 bot、多来源绑定、来源撤销、原会话不可用、新消息仅更新时间；断言关联消息与目的地仍对应原模型上下文，或明确停止发送。

### B03：未知调用隔离没有从调度上让出队首

**风险 P1；修复风险高。**

**代码证据：**

- `src/noyra/cognition/interaction.py:216-245`：按优先级和创建时间选择首条 offered/deferred 消息，没有排除本轮处于 unknown 或等待隔离的候选。
- 同文件 `:97-132`：网关返回 ProviderCallError/ModelCallStateError 时，只返回 interaction_model_failed，交互仍 offered。
- `src/noyra/model/request_identity.py:44-67`：存在 prepared/executing/unknown 时继续使用原业务身份；这是正确的防重复调用边界，本身不应删除。
- `src/noyra/model/resources.py:2898-2907`：资源路由发现未知结果时隔离该逻辑请求。
- `src/noyra/cognition/cycle.py:411-424`：交互返回非空失败结果后，本轮在该阶段返回，后面的工作也无法在本轮推进。

**根因：** 账本隔离与调度可运行性没有衔接。网关正确拒绝重复发送同一未知请求，但调度器仍不断把它当成下一条可执行消息。

**触发条件：** 当前最早或最高优先级消息发生一次结果未知；后续消息没有更高调度优先级，未知结果尚未人工核对/授权恢复。提供商恢复健康或新增消息不会自动改变这条记录的调度资格。

**影响：** 后续独立消息长期不能处理，日志/状态重复出现交互失败。没有重复真实请求，也没有在复现中重复收费；问题恰恰是保护未知调用的机制扩大成了整个消息队列停滞。

**本地复现：** 正常写入 Alice 的首条邀请和 Bob 的独立邀请；provider 第一次产生 unknown，第二个已经准备好的响应合法。裸 ModelGateway 和实际 RoutedModelGateway 分别连续调用四轮，得到相同现象：

```text
每轮结果：interaction_model_failed
每轮下一候选：仍然是 Alice 的第一条消息
Alice：offered；Bob：offered
真实 provider 请求次数：始终为 1
账本：第一条调用为 unknown
```

**根因修复方向：** 用明确的调度等待/隔离状态让未知业务轮次暂时退出可运行候选，让其他独立消息继续；保留原 call、请求身份、未知费用和人工恢复证据。显式核对或授权后再恢复原轮次。

**修复风险来源：** 如果简单换幂等键、忽略 unknown、删除调用或把它记为 failed，就可能重复请求、重复计费或错误释放保留。不能把调度上的“暂不可运行”伪装成主体主动拒绝/沉默。

**回归要求：** 单条未知后另一联系人继续；同一联系人后续消息如何处理需明确；进程重启、跨日、资源更换、显式 retry 授权、核对成功、核对失败、多个未知并存和日预算用尽；每个未知轮次未经授权不得新增物理调用。

### B04：主动社交的记忆召回没有按联系人来源隔离

**风险 P2；修复风险中至高。**

**代码证据：**

- `src/noyra/cognition/social.py:224-236`：选定联系人后，按该名字/关系描述调用全主体 MemoryStore.recall。
- 同文件 `:252-258`：把召回的完整记忆片段加入该联系人的社交上下文。
- `src/noyra/mind/memory.py:261-306`：召回按 subject_id、状态和记忆类型等筛选，没有“允许分享给此联系人”的归属过滤条件。
- `src/noyra/cognition/social.py:290-309`：该上下文直接进入生成社交回应的模型请求。
- 同文件 `:311-344`：校验联系边界和证据 event_id，但不校验生成内容的私密来源。
- 对照当前直接交互路径 `src/noyra/cognition/interaction.py:280-305`：有明确联系人归属时，已在召回前跳过未限定来源的记忆；主动社交没有同等边界。

**根因：** 隔离只在直接回应入口实现；主动社交仍把“属于 Noyra 的记忆”当成“可用于对当前联系人输出的记忆”。文本相关性不能证明分享授权，尤其另一人的私密内容可能提到当前联系人的名字。

**触发条件：** Bob 的私信进入一条 private 记忆，该文本与 Alice 的关系描述足够相关；实例随后准备联系 Alice。无需伪造身份、同名合并或跨账户 API 读取。

**影响：** Bob 的私密文本进入面向 Alice 的社交生成上下文，存在被带入回复的风险。确认的污染发生在上下文；本轮没有调用真实模型来测泄露概率，也没有向 Alice 外发消息，因此不声称已观察到外部实际泄密。

**本地复现：** 使用真实账户分别建立 Alice、Bob 的独立私信归属；为 Bob 事件建立合法 private episodic 记忆，内容含合成标记及 Alice 的名字。仅为 Alice 建立候选关系，再执行真实 `_context()`：

```json
{
  "selected_recipient_is_alice": true,
  "private_bob_memory_in_alice_social_context": true,
  "formal_model_calls": 0
}
```

召回的 memory_id 与由 Bob 私密事件形成的 memory_id 一致。

**根因修复方向：** 将直接回应和主动社交统一为可复核的输出来源策略。没有可靠归属或分享授权时，主动社交应先排除未限定来源的记忆；后续可引入明确可共享、本人来源及私密来源集合。不要在全局 recall 已发生后再仅提示模型保密。

**修复边界：** 私密来源的归属与记忆混合来源、历史记录兼容、授权共享需要清楚定义；不能擅自公开历史记忆，也不应为了一个联系人删除 Noyra 的合法私人记忆。一般自我反思与面向特定收件人的输出需要不同的来源策略。

**回归要求：** 两人名字互相出现、混合来源记忆、无归属旧记忆、公开可共享记忆、授权共享会话、多个账号/渠道属于同一联系人及不同联系人；断言其他人的私密片段不进入本收件人的生成上下文。

### B05：旧标识的文本前缀被误当作内部实体类型

**风险 P2；修复风险低至中。**

**代码证据：**

- `src/noyra/cognition/social.py:182-200`：无 participant 映射的历史消息按原 counterparty 匹配旧关系，说明该路径仍支持旧身份。
- 同文件 `:367-380`：只要 relationship.entity_key 以 entity_ 开头，就按新 participant 实体查来源；没有先确认 participant_entities 是否存在对应实体。
- 同文件 `:381`：判断是否真正要发送，发生在来源解析之后。因此 wait/respect_distance 也会进入不必要的路由失败。
- 同文件 `:112-116`：只在 _validate 周围捕获 RelationshipSocialValidationError，_commit 抛出的同类异常没有在此处理。

**根因：** 数据类型通过字符串前缀猜测。旧渠道标识/用户名本来是任意合法字符串，可以合法地以 entity_ 开头；新表迁移并未给所有历史消息建立 participant 映射。

**触发条件：** 历史关系的 entity_key 例如 `entity_legacy_peer`，对应交互合法但没有新 participant_message_links；它被选作社交候选。

**影响：** 合法社交决策无法提交，甚至主体选择 wait、不联系任何人也会异常。下一轮可恢复同一个成功模型结果并再次异常，造成持续的社交阶段失败；没有发生外部发送。

**本地复现：** 正常 API 构造旧式交互及关系，外部标识 `entity_legacy_peer`；合成 provider 返回合法 wait。连续两轮：

```text
RelationshipSocialValidationError: contact channel changed
物理模型调用：仅 1 次
完成的 relationship_social_runs：0
```

没有修改 schema、关闭完整性约束或篡改保存的哈希。正向对照只把旧标识改成 legacy_peer，同一流程正常完成 relationship_social_wait，随后本轮不再重复执行。

**根因修复方向：** 依据真实实体记录/明确类型字段区分内部身份和旧地址，不能用前缀替代归属判断；无发送意图的决策不必解析地址。提交阶段的预期来源变化应有可恢复结果，不能裸抛反复破坏运行周期。

**回归要求：** entity_ 开头的合法旧用户名、确实存在的新实体、缺少来源的新实体、普通旧标识、wait/respect_distance、真实 contact，以及撤销来源后的恢复；不能因为修复旧数据而把不存在实体随意路由到外部地址。
