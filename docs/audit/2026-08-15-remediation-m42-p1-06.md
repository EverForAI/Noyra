# M42 P1-06 Export Worker Ownership and Cancellation Remediation

Date: 2026-08-16

Baseline: `main` / `87e059a` plus the verified M41/M42 remediation work.

## Scope

The audit found that `ExportJobManager.close()` changed queued/running jobs to cancelled and used
`shutdown(wait=False)`. A running Python worker could therefore survive service shutdown, append
runtime/training success records after cancellation, and continue writing the subject database after
the process lock was released. Manager construction also performed restart recovery before a new
service had acquired that lock. This remediation closes worker ownership through shutdown and the
cancel-versus-publish state transition. It does not claim to close P1-07 long-history memory,
temporary-volume, sharding, or real-time disk-budget contracts.

## Implemented boundary

- Every job has an `ExportControl` with a cooperative cancellation event and a publication decision
  lock. Database backup progress, runtime table batches, training rows, workspace reads, ZIP chunks,
  metadata hashing, and the final publication path call its checkpoint.
- Cancellation and publication use the same decision lock. If cancellation commits first, the job is
  durable `cancelled` and no final archive or success row can be published. If publication commits
  first, the final rename, job completion metadata, and runtime/training success records are in the
  same SQLite transaction; a later cancellation is rejected as not cancellable.
- Runtime and training workers publish only to their job-owned target. The control validates the
  lexical artifact root, root identity, and symlink/reparse boundary before work and publication.
  Runtime temporary ZIP creation is exclusive and flushed to disk before the decision transaction.
- `ExportJobManager.close()` requests cooperative cancellation and then uses
  `shutdown(wait=True, cancel_futures=True)`. `NoyraService` calls this before `kernel.close()`, so the
  graceful path cannot release the subject process lock while an export writer is alive. The
  deployment supervisor remains the bounded escalation path if a host operation does not return.
- Restart recovery moved out of the manager constructor. `start_after_ownership(subject_id)` runs
  only after `SubjectKernel.boot()` acquires the process lock, is scoped to that subject, marks only
  queued/running jobs as `service_restarted`, and removes only their canonical final/hidden partial
  files. Completed, cross-subject, unrelated, and outside-root files are preserved.
- A second service that loses process-lock acquisition closes an inert export manager; it cannot
  rewrite the first owner's job state or remove its in-flight files.

## Evidence

`tests/test_m42_p1_06_export_ownership.py` provides ten focused cases across seven deterministic
contracts:

- runtime and training cancellation are gated immediately before publication, proving cancelled jobs
  leave no ZIP, completed job, `runtime_exported`/`training_exported` audit, or `training_exports` row;
- the inverse race holds the publication decision transaction while cancellation waits, proving the
  completed artifact and success rows commit together and cancellation is then rejected;
- shutdown is held behind an uncooperative worker gate, proving `manager.close()` blocks and the
  second kernel cannot acquire the subject lock until the worker exits and the first kernel closes;
- manager construction and a second `NoyraService` that loses lock acquisition do not perform
  recovery writes or file cleanup;
- owned recovery cleans queued/running targets and hidden partials while preserving completed,
  cross-subject, unrelated, and outside-root files; and
- cancellation raised from SQLite backup progress cleans the partial snapshot image and lock
  sidecar; and
- runtime and training target-link swaps fail before staging or publication, preserve the outside
  file, and leave no success state.

## Acceptance state

P1-06 is `verified` in `tests/contracts/remediation_acceptance.json` after both independent
ownership contracts and the fixed gates pass. P1-07 remains open: training export still uses the
system temporary root, retains unbounded deduplication/episode state, has no shard manifest or
real-time staging/free-space budget, and the compatibility byte-returning API still reads the final
ZIP into memory. None of those adjacent findings is implied to be fixed here.
