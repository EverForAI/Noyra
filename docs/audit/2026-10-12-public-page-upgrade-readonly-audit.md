## 审计结论

本审计只读检查本轮 P01–P07 公开页面升级的后端、迁移、私有导出归属、公开 HTTP 契约、管理发布表单、匿名页面、异常恢复和资源边界。没有修改应用代码、测试、配置、依赖或生产数据；只在被 Git 忽略的 `.runtime` 中使用了隔离合成数据库、合成事件、合成交互和本地浏览器诊断脚本。聊天/记忆删除和“可核验性与公开证据”仍按用户明确决定保持关闭，不把它们列为本轮缺陷。

已确认 **10 项需要处理的问题**，其中 3 项 P1、6 项 P2、1 项 P3；另有 6 类功能完成度缺口和 1 项基线契约债务。完成度缺口按 C01–C06 单独列出，部分带有 P2/P3 后续风险，不重复计入上述运行问题。最需要优先处理的是：

1. **P1：冷归档后公开生命周期历史不可读。** 归档过程把事件 `payload_json` 替换为 `{}`，公开时间线仍只从该字段读取 `from/to`，因此正常归档会让已公开的生命周期记录消失。
2. **P1：公开 v2 交互查询绕过完整性校验。** 对交互正文改写而保留旧哈希后，v2 仍返回被篡改正文并返回 200；这与公开档案“读取已验证公开内容”的安全边界不一致。
3. **P1：公开命名空间判断大小写不一致。** v2 的 SQLite `LIKE 'public:%'` 将 `PUBLIC:`/`Public:` 也视为公开，旧 v1 投影的 Python `startswith('public:')` 则不会；若这些通道承载私有内容，会越过显式公开边界。
4. **P2：公开查询的全文搜索没有数据库扫描预算。** 空结果搜索的 SQLite 虚拟机步骤随交互数量增长，可能在大历史库上超过请求预算或占用读资源。

## 已确认问题

### P1-01：冷归档会使公开生命周期记录消失

- **证据与复现：** `.runtime/public-readonly-audit.json` 的 `normal_cold_archive`：归档前 `before_items=1`，本地加密冷归档 `archived=1` 后 `after_items=0`，事件的 `payload_json` 已成为 `{}` 且 `payload_archive_key` 存在。复现使用真实 `EventPayloadArchive.archive_cold()` 和 `PublicArchive.page(kind="lifecycle")`，没有删除、禁用触发器或修改生产数据。
- **根因：** `src/noyra/core/event_archive.py` 的冷归档协议为降低热库负担将事件正文置空；`src/noyra/interaction/public_archive.py:563` 的生命周期 SQL 只选择 `json_extract(payload_json,'$.from/to')`，没有读取经过验证的加密归档，也没有把公开状态元数据单独存入热库。`_item()` 对 `from/to` 不是允许枚举时返回 `None`，所以记录被静默过滤。
- **影响：** 公开时间线、生命周期页和按时间范围的匿名查询无法再看到已公开且已经进入冷存储的阶段转换。原始事件仍在加密归档中，故这不是数据库删除；但公开档案历史在其正常保留周期后会不完整，访客无法区分“从未公开”和“已归档后暂时不可读”。
- **触发条件：** 运行归档任务将 `lifecycle_transition` 或 `lifecycle_recovery` 事件归档，且公开页面随后查询该事件。只要部署启用事件冷归档并达到保留天数就会触发。
- **触发概率：** 在启用冷归档且服务运行超过保留窗口时为高；未配置归档或事件尚未过期时为零。生产是否启用以及历史数量没有本地证据。
- **修复风险：** 高。直接在匿名请求内恢复解密归档会引入密钥、云存储延迟、缓存、请求预算和故障模式；把内容复制到热库又会改变归档和迁移合同。
- **建议：** 立即修复设计，但先做边界评审。优先为“已批准公开状态”保存独立、不可变且不含私有原因的 `public_lifecycle_projection`（含 `from/to/occurred_at/subject_id/state_hash`），在事件归档前由同一事务写入；历史数据若没有可验证公开元数据，必须明确标为不可恢复，不能猜测回填。备选是增加有界、可验证的归档读取服务，绝不让匿名路由直接解密任意归档。补充冷归档前后、密钥不可用、跨主体和恢复失败的专项验收后再交付。

### P1-02：公开 v2 交互读取绕过正文和状态哈希验证

- **证据与复现：** `.runtime/public-readonly-privacy.json` 的 `hash_integrity`：隔离库中仅把一条 `public:local` 交互的 `content` 改成 `audit injected invalid content hash`，保留原 `content_hash/state_hash`。旧 v1 路由因 `InteractionStore._from_row()` 校验失败而连接中断；新的 `/api/public/interactions?id=...` 却返回 HTTP 200 和被篡改的正文。该诊断仅使用合成库，改动在进程退出后销毁。
- **根因：** `src/noyra/interaction/public_archive.py:550-573` 直接 SQL 读取 `interactions`，`_item()` 只组装字段，未调用 `InteractionStore._from_row()` 或等价的内容哈希、状态哈希验证。行为和生命周期也有直接读取模式，需在后续修复中分别核对完整性合同；本次损坏注入直接确认的是交互路径，旧行为 v1 的直接投影同样未在此处验证 revision 哈希，不能将其全部归为本轮新增回归。
- **影响：** 公开页面可能把数据库被篡改、损坏或不完整提交的文字当作可信公开记录返回。它不造成跨主体读取，但会破坏公开档案的完整性、审计可信度和前端“已审核公开内容”的含义。
- **触发条件：** 交互行正文、状态或哈希发生不一致，且访问 v2 公开交互路由；正常写入路径不会主动制造不一致，文件/数据库损坏、错误迁移、人工改库或未来新写路径可能触发。
- **触发概率：** 正常运行低；在数据库完整性事故或维护操作期间为中。由于 v2 是新读取路径，现有 v1 完整性测试不能覆盖它。
- **修复风险：** 中高。复用存储校验可能把公开路由从“单条坏记录被返回”改成整页 503；直接补哈希检查又必须覆盖每类投影和性能上限。
- **建议：** 立即修复。建立只读的、带完整性验证的公开投影读取器：交互至少验证 `content_hash` 与 `state_hash`，行为验证 action/revision hash，生命周期验证事件 payload hash/归档状态；任何一条校验失败应返回明确的 `public_content_unavailable`（503）并记录内部诊断，不把私有原因、哈希或堆栈带给匿名访问者。增加每种 kind 的损坏注入测试和“不泄露损坏正文”断言。不要简单捕获异常后跳过而伪装成“没有公开记录”。

### P1-03：公开交流通道的大小写语义不一致，可能越过公开命名空间

- **证据与复现：** `.runtime/public-readonly-privacy.json` 的 `channel_case`：同一隔离主体写入 `PUBLIC:local`、`Public:local`、`public:local` 和 `private:local` 四条 outgoing 记录后，旧 v1 `/api/interactions` 只返回 `public:local`；v2 `/api/public/interactions` 却返回前三条。v2 SQL 为 `channel LIKE 'public:%'`，SQLite 默认 ASCII `LIKE` 不区分大小写，而旧投影用 Python `record.channel.startswith("public:")`。该诊断只使用合成内容，退出后数据库销毁。
- **根因：** 公开通道的命名空间合同没有在写入校验和读取谓词中统一；SQL `LIKE` 被当作大小写敏感前缀匹配使用。
- **影响：** 任何被其他路径视为非公开、但名称以 `PUBLIC:` 或 `Public:` 开头的 outgoing 交互可能出现在匿名 v2 档案中。若上游允许把私密/内部通道原样写入这些名称，这会造成公开边界越过；当前证据确认了读取差异，未确认生产是否已有此类行。
- **触发条件：** 数据库存在 `direction='outgoing'`、`channel` 以非小写变体 `PUBLIC:`/`Public:` 开头的记录，并访问 v2 交互或时间线。
- **触发概率：** 正常统一写入路径低；人工导入、旧版本、第三方通道适配器或大小写不规范配置时低到中。影响一旦触发是确定的。
- **修复风险：** 中。收紧过滤可能使已被误公开的内容从 v2 消失，必须保留旧接口兼容和撤回/缓存语义。
- **建议：** 立即修复。先保持旧 v1 的大小写敏感公开前缀合同；读取层使用 `substr(channel,1,7)='public:'` 或等价二进制比较，不依赖 SQLite `LIKE` 默认大小写行为。写入层若增加通道校验，必须允许既有非公开名称，不能将历史大写变体自动规范化为公开。补充大小写变体、Unicode 相似字符、跨主体和旧 v1/v2 一致性测试；对历史变体先内部盘点，不自动把它们改成公开。

### P2-01：生命周期状态过滤在 SQL LIMIT 后执行，坏记录可遮蔽有效历史

- **证据与复现：** `.runtime/public-readonly-audit.json` 的 `filter_after_limit`：在前两条原始行包含不受支持状态时，请求 `limit=2` 返回 `small_items=0, small_next=null`，而同一隔离库 `limit=100` 能找到较旧的合法记录（`older_valid_exists=true`）。
- **根因：** `PublicArchive.page()` 对每类 SQL 使用 `LIMIT limit+1`，随后才调用 `_item()`；生命周期 `_spec()` 只要求 JSON 有效，没有在 SQL 中限制 `from/to` 的 `LIFECYCLE_STATES`。`_item()` 遇到未知状态直接返回 `None`，已取出的坏行消耗了分页窗口。
- **影响：** 历史损坏、旧版本遗留或人工构造的公开生命周期事件可能令页面显示空列表且没有下一页，导致后续合法记录不可见。标准生命周期写入路径使用合法状态，因此不影响健康新事件。
- **触发条件：** 同一主体存在比目标记录更新的、`privacy_level=public_status` 且 JSON 结构可解析但状态不在公开枚举中的行；用户使用较小 `limit` 或游标页。
- **触发概率：** 正常写入低；历史迁移、手工修复或未来枚举扩展期间低到中。
- **修复风险：** 中。状态谓词必须和公开枚举保持一致，错误扩展可能意外公开新内部状态。
- **建议：** 暂缓至 P1-01 设计一起修复，但列入同一读取合同：在写入/归档前规范化状态，查询只读允许枚举，分页按“可公开候选”计数；遇到未知值应返回可观测的 503 或安全跳过并继续补足 `limit`，不能静默制造终页。为坏行在首页、游标第二页和多主体场景增加测试。

### P2-02：极端带时区日期使 HTTP 线程断开，未返回 400

- **证据与复现：** `.runtime/public-readonly-audit.json` 的 `timestamp_overflow`。`since=9999-12-31T23:59:59-01:00` 触发 `datetime.astimezone(UTC)` 的 `OverflowError`；匿名 GET 和管理发布 POST 均出现 `RemoteDisconnected`，服务进程随后仍可处理正常 overview 请求。堆栈位于 `.runtime/public-readonly-audit.log`。
- **根因：** `src/noyra/interaction/public_archive.py:64-69` 的 `_timestamp()` 只把解析异常交给上层 `ValueError` 捕获；日期偏移导致的 `OverflowError` 未被 `service.py` 的查询/发布异常列表捕获。
- **影响：** 恶意或错误客户端可以令单个连接异常关闭，客户端得到网络错误而不是契约规定的 400；高并发重复输入会制造噪声和线程级异常日志。
- **触发条件：** 任何 `since/until`、游标时间或公开摘要 details 时间字段使用接近 `datetime` 边界且带时区偏移的合法 ISO 字符串。
- **触发概率：** 普通用户几乎为零；模糊测试、恶意请求或外部系统时间错误时低。
- **修复风险：** 低到中。扩大捕获范围必须避免吞掉真正的数据库/运行时错误。
- **建议：** 暂缓但应在下一次契约修复中处理：在 `_timestamp()` 内显式捕获 `OverflowError` 并转换为 `ValueError`，增加最小/最大日期和大偏移测试，同时限制时间范围到系统合同允许的年限。服务层仍只将格式错误映射为 400。

### P2-03：管理发布编辑不是全字段可逆，旧合法摘要可能被无意改写

- **证据与复现：** `.runtime/public-readonly-browser.json` 的 `roundTrip`：后端合法的 `status="complete"` 回填到只含固定选项的 `<select>` 后变成空值，下一次收集不再携带状态；`progress=0.123456` 回填为 `12.3456`，由于控件 `step="0.1"` 变成 `stepMismatch=true`，表单会阻止保存；阶段标题包含 `|` 时，管理台的“每行名称 | 状态”格式被二次拆分成错误字段；研究资料标题包含 `|` 时会构造无效 URL。对应代码为 `src/noyra/web/admin.js:2867-3066`、`src/noyra/web/admin.html:211-225`。
- **根因：** UI 采用有限枚举和易混淆的分隔符文本协议，而后端 `_details()` 对 `status`/阶段文本允许更宽的字符串；前端回填没有保留未知枚举，百分比显示精度又高于输入步进。
- **附带契约差异：** 后端接受 `details.status="Custom Status 1"`，匿名 `?status=Custom Status 1` 却因只允许小写下划线和 64 字符返回 400。该结果在 `.runtime/public-readonly-audit.json/status_contract`，说明发布、回填、筛选三处的状态合同都需要统一。
- **影响：** 管理者打开既有摘要后只改标题，可能清除未被 UI 认识的状态；合法高精度进度无法再次保存；含分隔符的阶段/资料无法无损编辑。属于发布内容完整性和操作可逆性问题，不会修改私有源记录。
- **触发条件：** 既有或 API 创建的详情含 UI 未列出的状态、非 0.1% 精度进度、阶段/资料标题包含 `|`，再通过管理台编辑并提交。
- **触发概率：** 自由手写摘要中低到中；通过 API 或未来状态扩展时中。每个触发条件独立，不能从当前流量推算百分比。
- **修复风险：** 中。扩展枚举、精度和编码时必须保持旧摘要可读且不改变已发布内容。
- **建议：** 立即修复管理契约：详情状态使用服务端允许枚举清单；未知值只读显示并阻止破坏性保存，或提供“保留原值”选项；阶段/资料改用结构化可增删行输入或无歧义编码，避免裸 `|` 协议；百分比控件使用可表示后端值的步长/字符串精度，提交前做服务端同值回填测试。保存失败时应保持可编辑草稿。

### P2-04：首次发布失败后锁定类型和关联来源，失败恢复路径不完整

- **证据与复现：** `.runtime/public-readonly-browser.json` 的 `newValidation`：模拟新摘要请求返回 404 后，草稿仍保留，但 `kind_disabled=true`、`source_disabled=true`，`publicationEditor.revision=0`。用户无法在原草稿上修正错误的类型或来源，只能新建并重新复制文字。
- **根因：** `savePublicPublication()` 在第一次请求前就创建 `publicationEditor`，`finally` 无论成功失败都把 `#publication-kind` 和 `#publication-source` 设为 disabled；“类型/来源不可在已有记录更改”的约束被错误地应用到了尚未创建的记录。
- **影响：** 无效来源、填错类别或权限变更后的失败会把草稿锁在错误身份上，增加重复发布、内容复制错误和用户误以为已保存的风险。
- **触发条件：** 新摘要首次 POST 返回网络错误、404、409、容量错误或其他非成功结果。
- **触发概率：** 管理发布网络失败或输入错误时中；正常成功发布不触发。
- **修复风险：** 低到中。解锁未创建草稿不能改变服务端类型/来源不可变合同，但必须区分“本地临时编辑器”和“已存在的 publication_id”。
- **建议：** 立即随 P2-03 修复：只有服务端成功返回 revision≥1 后才固定类型/来源；明确区分“服务器明确拒绝，尚未创建”和“网络中断，可能已创建”。明确拒绝时允许在原草稿上修正来源/类型；结果不明时保持原 ID/内容，通过鉴权查询确认是否已落库后再决定是否解锁。不能在网络结果不明时直接生成新 ID，否则可能重复发布。为 404、409、网络失败、退出登录分别验收。

### P2-05：撤回请求期间和完成后可能把摘要编辑控件留在错误禁用状态

- **证据与复现：** `.runtime/public-readonly-browser.json` 的 `withdrawControls`：撤回异步请求开始时，函数只设置 `publicationWriting=true`，没有锁定表单控件；在请求期间切换类型会调用 `publicationFields()`，把该类型的输入设为 disabled。请求完成的 `finally` 只重置布尔值，没有再次调用 `publicationFields()`，因此控件仍为 `after_disabled=true`。反向地，撤回期间用户可在未锁定的输入中修改草稿，造成展示状态与正在撤回记录混淆。
- **根因：** 撤回复用了发布写入标志，却没有自己的控件快照/恢复路径；`publicationFields()` 把瞬时 `publicationWriting` 直接写入 DOM，finally 没有根据当前编辑器和类型重新计算。
- **影响：** 撤回后用户可能看到无法编辑的字段，或在撤回进行时编辑未提交内容。不会改变服务器已撤回的摘要，但容易造成误操作和草稿丢失感。此复现要求编辑器处于可切换类型的新建草稿；已有摘要的类型本来就固定。
- **触发条件：** 管理员在新建摘要草稿中，从列表撤回另一条记录，并在请求尚未返回期间切换摘要类型。
- **触发概率：** 正常快速请求低；慢网络、重复操作或编辑与列表并行时中。
- **修复风险：** 低。应只改变前端控件生命周期，不放宽撤回 CAS/权限。
- **建议：** 暂缓到 P2-03/P2-04 一起修复：撤回开始时保存控件 disabled 快照并锁定整个编辑器，完成/失败后统一调用 `publicationFields()`；若正在编辑的恰是被撤回的摘要，提示其修订已变化；若是另一条新建草稿，保留其内容，不随撤回清空。完成和失败后重新计算控件状态。补充慢请求、409、401 和网络失败浏览器验收。

### P2-06：匿名全文搜索没有扫描和数据库工作量预算

- **证据与复现：** `.runtime/public-readonly-audit.json` 的 `anonymous_search_scaling` 使用隔离库插入 100、1,000、5,000 条 2,000 字符公开交互，搜索不存在的词。SQLite progress handler 记录的近似虚拟机步骤分别为 10,900、22,600、74,600，耗时约 17.09、36.43、81.58 ms；结果均为空。`src/noyra/interaction/public_archive.py:466-476` 使用 `instr(lower(text), lower(?))`，没有全文索引、扫描上限或查询级取消。
- **根因：** 返回行数有 `LIMIT`，但搜索谓词和行为最新 revision 的相关子查询仍需检查大量候选行；`_json()` 的 2 MB 限制只在 SQL 读取、对象组装和 JSON 序列化完成后执行，不能限制数据库工作量。外层 HTTP 虽有请求 deadline，但 SQLite 查询不会以同一预算主动中止。
- **影响：** 大历史库、空结果搜索或时间线 `all` 查询可能占满读连接、CPU 和内存，导致匿名请求超时并与后台完整性/服务请求争抢资源。它不是现有小库的即时 DoS 证明；证据只证明成本随数据增长且没有独立的扫描合同。
- **触发条件：** 访问 `search`，或访问会遍历多个类别的 timeline/overview，且主体公开历史达到较大规模；最坏情况是不存在的搜索词。
- **触发概率：** 小库低；公开内容长期增长或被机器人重复查询时中，实际概率取决于生产数据量、限流和并发。
- **修复风险：** 中高。引入 FTS、工作量中止或新索引会改变迁移、排序、Unicode 搜索语义和恢复合同。
- **建议：** 暂缓到容量模块但列为 P2：先在生产规模样本上定义每请求最大 SQLite steps/墙钟/扫描行数，接入可中止的查询进度回调；再选择受限 FTS 或规范化搜索列，保留 subject、kind、时间和撤回过滤。超预算应返回稳定 503/429 和 Retry-After，不能只提高全局超时或取消匿名限流。为空词、Unicode、撤回、分页和多主体写压力测试。

### P3-01：暂停自动更新不能取消已在途的首页请求

- **证据与复现：** `.runtime/public-readonly-browser.json` 的 `pausedPending`：暂停后让待处理 overview 响应完成，`paused=true` 仍把新数据写入 `overviewData` 并重绘 3 张卡片。代码 `src/noyra/web/app.js:1129-1131` 只切换布尔值，未递增 `overviewGeneration` 或 `abortScope("overview")`；轮询本身虽然会停止。
- **根因：** 暂停逻辑只防止未来 `setInterval` 调用，没有处理已开始的 `loadOverview()`。
- **影响：** 用户点击暂停后仍可能看到一次迟到更新；暂停语义不严格，调试或阅读固定快照时会被新数据覆盖。没有发现管理员请求、写入或私有数据泄露。
- **触发条件：** 点击暂停时 overview 请求正在等待网络/服务；响应在暂停后返回。
- **触发概率：** 普通低延迟部署低；网络拥塞、服务忙或故障时中。
- **修复风险：** 低。只需复用已有请求作用域和 generation 防护。
- **建议：** 暂缓为 P3，但建议在下一次前端修复中让暂停递增 generation、取消 `overview` scope，并在恢复时明确重新读取一次；保留已显示的快照并显示获取时间。

## 完成度缺口与优化建议

这些项目不一定是本轮“错误实现”，但与升级目标相比仍不完整，应进入后续路线图。

### C01：深链接文章缺独立 SEO/社交元数据（P3，暂缓）

- **实现状态/根因：** 已保留首页 SEO；服务端对 `/` 生成统一 title、canonical、OG 元数据，`#goals/id` 等详情只由 JavaScript 切换。片段不发送到服务器，服务端没有按文章生成可抓取正文或分类 sitemap。代码在 `src/noyra/service.py:9517`、`app.js:353`。
- **影响/触发：** 无 JS 的爬虫、社交预览抓取或搜索索引具体文章时，只看到首页元数据；普通应用内深链接可以阅读。不是本轮明确承诺文章 SSR 后又遗漏，应列为体验深化。
- **概率：** 使用服务端社交抓取时高；搜索表现取决于爬虫执行 JS 的能力，未做真实搜索引擎验证。
- **风险/修复风险：** P3／中高。增加 SSR 路由必须兼顾撤回、缓存、权限、数据库成本与 canonical。
- **建议与验收：** 可暂缓。未来提供按公开 ID 查询的安全预渲染路径，复用可见性和完整性校验；撤回后返回明确 404/410，不把私有源内容写入 HTML。用无需 JS 的 HTTP 抓取验证标题、正文、canonical、OG，并测试撤回后内容消失。

### C02：公开正文是转义纯文本，阅读结构有限（P3，暂缓）

- **实现状态/根因：** `app.js:508` 将正文整体 `escapeHtml()` 后放入单一 `.article-body`。CSS 保留文本换行，已经可以阅读段落；但没有语义标题、列表、引用、目录或段落导航。
- **影响/触发：** 长日记和研究正文阅读时，结构层次有限；不影响纯文本完整性。避免任意 HTML 是当前正确安全边界。
- **概率：** 长文阅读中高，短摘要低。
- **风险/修复风险：** P3／中高。引入富文本解析可能新添 XSS、外链或远程资源读取，不能只为排版放开 HTML。
- **建议与验收：** 可暂缓。先做纯文本段落分组、复制深链接等低风险优化；再评估受限 Markdown/结构化段落合同，默认转义并禁用原始 HTML/脚本。验证恶意输入、长文、移动屏和键盘阅读；不将内部推理转成公开正文。

### C03：公开修订历史没有独立容量/保留策略（P2，暂缓但需容量设计）

- **实现状态/根因：** `public_publications` 有 2,000 条/16 MB 当前摘要上限，`public_publication_revisions` 只受外键和不可变触发器约束；每次编辑/撤回追加六字段修订元数据，没有正文历史，也没有独立行数/字节容量预算或归档策略。上限不能称为整个公开模块的磁盘上限。
- **证据：** `.runtime/public-readonly-audit.json/revision_growth`：同一条摘要 12 次成功修订后，当前表 1 行，修订表 12 行。可从 `public_archive.py:218,256,286` 与 `public_archive_schema.py:22` 确认持续追加；没有在合成库无限写入。
- **影响/触发：** 仅鉴权管理者能够写。长期高频发布/编辑时增加数据库、导出和备份体积；每条修订较小，不能把 12 次编辑说成即时磁盘耗尽。
- **概率：** 普通手动低，管理自动化或多年累计中；没有生产修订速率。
- **风险/修复风险：** P2／中高。直接清理会破坏不可变修订、归属图和恢复合同。
- **建议与验收：** 可暂缓短期交付，但容量设计必须区分当前文字与修订元数据。可先设置主体级追加预算和明确容量错误；若归档，先定义历史保留、验证/恢复和迁移合同，不能直接删除触发器或丢弃修订。测试容量边界事务回滚、正常相同内容重试、撤回保留必要余量与双主体导出。

### C04：200 条之后没有常规翻页阅读路径（P2，暂缓优化）

- **实现状态/根因：** 后端有游标；前端 `MAX_VISIBLE_RECORDS=200`、`loadView()` 在达到上限后隐藏“加载更多”，只提示缩小筛选。现有六种时间范围都是从某个过去时间到现在，没有“某日期之前”或下一批替换视图。该上限是计划中的内存保护，不能误报为后端没有分页。
- **影响/触发：** 同一分类超过 200 条、特别是全部已过三个月的历史，普通访客无法顺序读完较旧记录，只能已知标题搜索或已知 ID 深链接。
- **概率：** ≤200 条时零；超过上限且使用常规列表时确定。生产是否达到上限未检查。
- **风险/修复风险：** P2／低到中。无限追加会破坏内存边界；应保留 200 条上限。
- **建议与验收：** 可暂缓。在前端提供“下一批”替换当前页、上一页游标栈，或自定义 `since/until` 日期范围，保留筛选和滚动位置；合成至少 450 条同类历史验证最终记录可达、单屏最多 200 条、撤回和游标错误不会展示旧正文。

### C05：公开行为详情没有展示全部已批准的上下文（P3，暂缓优化）

- **实现状态/根因：** v2 行为 details 返回 `tool/resource_summary/redaction_reason` 等字段，但 `app.js:485` 只渲染公开影响和公开目标；行为标题常直接显示 `action_type`。读取器具备字段，页面没有完成它们的说明/展示。
- **影响/触发：** 访客阅读已经明确公开的运行行为时，不易理解原始工具代号、资源摘要或为何隐藏目标；不表示应开放内部工具参数、费用或私有理由。
- **概率：** 有此类行为记录时中高，空页不触发。
- **风险/修复风险：** P3／低到中。只允许显示已在既有公开合同中的字段，绝不扩展到私有参数。
- **建议与验收：** 可暂缓。增加中文/英文动作词典和可折叠“公开上下文”，字段缺失时不推断；核对已脱敏资源摘要，不把供应商、凭证或内部判断补出来。测试所有允许字段和未知动作的安全回退。

### C06：新匿名错误没有完整的可操作提示（P3，暂缓优化）

- **实现状态/根因：** `publicErrorMessage()` 对投稿限流等已有明确文案，但没有映射 v2 的 `rate_limited`、`invalid_public_query`、`public_response_too_large`；`getJson()` 丢弃 HTTP 状态和 Retry-After，只留错误码。限流、无效筛选和真正连接失败因此常显示同一个“服务暂时不可用”。
- **影响/触发：** 快速导航达到匿名限流、被错误筛选拒绝或响应超过容量时，访客不清楚应等待多久或如何收窄查询；不会绕过服务端限流。
- **概率：** 普通低，快速导航和机器人触发 429 时高；前一轮视觉矩阵已遇到限流，但没有以真实生产 soak 验证。
- **风险/修复风险：** P3／低。需保留通用私密错误回退。
- **建议与验收：** 可暂缓。带回状态、机器码和安全的 Retry-After，分别提示等待、检查筛选和收窄结果；不自动无限重试，不把堆栈或内部原因显示给访客。补 400/413/429/503 与语言切换验收。

## 已检查但未列为本轮缺陷的边界

- schema 92→93 追加 DDL 使用 `IF NOT EXISTS`，私有运行导出已注册 `public_publications` 主体归属和 `public_publication_revisions` 父表归属；双主体导出、历史 schema 71 和外键检查专项已通过。
- 发布、修订、撤回使用当前主体、CAS、显式 `confirm_public`、CSRF/操作员鉴权；同内容重试不新增修订；撤回不删除聊天、记忆或原始运行记录。这些边界不应因本审计再增加聊天删除功能。
- 投稿验证码仍是图像模式，读取/提交有 30 秒超时，匿名页面没有私有管理员路径、证据导出或操作令牌；公开响应有 `no-store` 和 2 MB 序列化后的响应上限。响应上限是在数据库读取和 JSON 序列化完成后才检查，不能替代查询预算，因此仍对应 P2-资源风险而非完整防护。
- 入站交互仍受 `direction=outgoing` 排除。本次 P1-03 是 outgoing 通道公开命名空间扩大，不能误述为所有入站或所有私密渠道都被公开。
- 管理摘要没有自动复制私有目标、项目、预测、研究、睡眠、聊天或记忆；未实施公开证据/证明模块是用户明确排除项。
- 本轮既有 OpenAPI 中仍有 `LengthRequired`、`NotImplemented`、`RateLimited`、`RequestEntityTooLarge`、`RequestTooLarge` 五种未定义旧响应引用。`.runtime/verify-public-openapi.py` 确认本轮新增引用可解析、183 个 operationId 唯一，但严格解析全文件仍可见这五项。它们在基线 `a27354a` 已存在，属于既有 P2 契约债务，不归因于本轮；建议单独按实际 HTTP 响应补齐定义。

## 本轮实施质量与完成度

主体隔离、默认不公开、明确审核、CAS、独立草稿、HTML 转义、匿名 Cookie 排除、版本别名和历史迁移/导出联动具有实际测试证据。前一轮发现的 schema93 导出归属和中央 API 路由遗漏已修复，最终全仓回归成功；不能继续把已修复的中途失败列为当前阻断。
