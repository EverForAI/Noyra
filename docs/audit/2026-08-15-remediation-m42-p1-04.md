# M42 P1-04 Runtime Export Ownership Remediation

Date: 2026-08-15

Baseline: `main` / `87e059a` plus the M41 verification foundation.

## Scope

The read-only audit identified a completeness defect in `core/runtime_export.py`: ownership was
inferred from the first column ending in `_id`, so tables sharing names such as `revision_id`,
`decision_id`, or `transition_id` could overwrite one another's selection set. A child table could
therefore be omitted from its subject archive or receive another subject's history. This remediation
implements the verification and ownership boundary for runtime exports. It does not change the
underlying subject state machine, persistence semantics, or public projection.

## Implemented boundary

Schema 33 now has ownership graph version 1 with a complete inventory of the current schema:

- 98 tables with direct `subject_id` ownership;
- 28 revision/child tables with an explicit parent table, parent key, child key, and correlated
  `EXISTS` predicate;
- two custom common-knowledge rules for package publisher/import reachability and trusted-key
  reachability through a subject package;
- `schema_meta` reduced to the global `schema_version` key; and
- six rebuildable memory FTS tables explicitly marked `skipped`.

The graph validates that every actual schema table is registered, every registered table exists, direct
subject tables really contain `subject_id`, and every parent edge is declared by SQLite. Export reads
use the explicit predicate and a bounded cursor. The manifest contains an ownership graph version,
`table_inventory`, expected/exported row counts, reconciliation status, skipped reasons, and
referential-gap counts. A missing graph entry, row-count mismatch, undeclared edge, or foreign-key
reference outside the selected subject graph fails closed before the archive or `runtime_exported`
audit row is published.

## Evidence

The focused contract suite covers the independent sub-contracts rather than only a happy-path archive:

- 11 focused P1-04 tests, including exact 28-family graph coverage, two-subject collision isolation,
  common-knowledge and `schema_meta` allowlists, manifest reconciliation, unregistered-table rejection,
  and cross-subject parent-reference rejection;
- a 1,100-parent/1,100-revision history proving the selection does not build a variable-sized `IN (...)`
  list;
- historical schema 6, 16, 21, 27, and 31 fixtures migrated to schema 33, preserving the anchor event
  and reconciling inserted parent/child evidence;
- 44 related runtime/storage/service regressions;
- M41 smoke profile: 72 passed; M41 large profile: 72 passed; and
- full repository pytest: 345 passed.

The focused and full pytest evidence is recorded. Windows evidence is local. The Windows/Ubuntu entry
point is reproducible, but Ubuntu could not be executed on this machine because no Ubuntu/WSL
distribution is installed.

## Acceptance state

P1-04 is `verified` in `tests/contracts/remediation_acceptance.json`. Both independent contracts are
closed by the focused, large-data, historical-fixture, static, deployment, and read-only evidence above.
The graph remains schema-versioned and fail-closed: any future schema change must add representative
fixture rows and an independent expected-set assertion before this issue can be re-opened. Composite
cross-subject constraints remain a database-schema hardening topic outside this exporter remediation.

The count reconciliation verifies that the selected predicate and emitted cursor agree; the focused
fixtures independently populate the audit-named parent families, custom common-knowledge rules, and
collision cases. At the time of this P1-04 record, P2-16's long-read snapshot and asynchronous
compatibility-route concern remained a separate open finding; it was subsequently addressed and
verified in `docs/audit/2026-08-15-remediation-m42-p2-16.md` without changing the P1-04 ownership
contract.
