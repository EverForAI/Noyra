## 风险和概率口径

P0 表示正在发生且可能造成不可逆跨主体或资金损失，本轮没有足够证据确认 P0。P1 表示外发隐私/费用、生产发布或恢复边界可能被绕过；P2 表示在特定配置、并发或数据损坏条件下影响正确性、容量或管理判断；P3 表示质量门禁或可维护性问题。修复风险描述实施本身可能引入的回归、迁移和数据兼容风险。

“触发概率”只表示条件在现实中出现的可能性，不能从临时数据库样本推导公网事故率。写“满足条件必现”表示探针在满足条件后稳定复现；写“无法估计”表示缺少生产样本。

## 新发现

### N01：运行租约失效后仍可能发送模型请求

- **风险等级：P1。** 运行时进入暂停、隔离、迁移围栏或关闭后，已经通过资源授权的模型调用可能在连接/DNS/TLS 等待之后继续把请求头写给供应商。一旦供应商接受输入便可能外发私密信息并产生费用；返回后的旧 epoch 检查只能阻止结果进入认知，无法撤回这次发送。
- **修复风险：中至高。** 发送边界必须同时保留密钥/资源授权检查、运行租约检查、账本终态结算和 unknown 语义。过于宽泛地把失效调用改成取消会丢失已发送费用；过于晚的检查又不能关闭外发窗口。
- **根因：** `src/noyra/model/gateway.py` 的 `before_send()` 只调用 `ModelLedger.check_request_authorization()`，没有调用 `assert_current_lease()`。`src/noyra/model/openai_compatible.py` 在 `send_request_headers.started` trace 中再次调用该钩子；该时刻已经跨过连接等待，正是运行租约可能被失效的窗口。返回后 `gateway.py` 的 `assert_current_lease()` 能发现旧 epoch，但它只能阻止结果继续使用，不能撤回已经写出的请求。
- **影响：** 绑定运行租约的认知模型调用；没有证据表明普通未绑定租约的后台诊断请求受影响。密钥撤销路径已有独立的发送前授权检查，不能把本问题与密钥撤销缺陷混为一谈。
- **触发条件：** 调用取得租约并开始连接；另一个线程执行 `invalidate()`/迁移围栏/隔离；连接完成后进入 `send_request_headers.started`；资源本身仍然处于 active。满足条件后本轮合成 transport **必现发送**。
- **触发概率：** 普通稳定请求低；服务暂停、完整性隔离、迁移和优雅关闭时，连接等待越长窗口越明显。没有生产并发样本，事故百分比无法估计。
- **证据：** `.runtime/reaudit-db9d495-boundaries.log` 的 `fenced_model_trace`：`sends_after_fence=1`，`lease_valid=false`，账本为 `call=succeeded, attempt=succeeded`。探针使用临时数据库、合成密钥和本地 `httpx` transport，没有网络外发。现有 `tests/test_model_authorization.py` 覆盖资源撤销而非运行租约在 trace 点失效。
- **建议：立即修复。** 在发送头 trace 和同步发送前共同执行租约检查；保持已发请求的真实费用/unknown 结算，禁止自动换路由重发。增加暂停、隔离、迁移和连接等待四类回归，验证检查失败发生在任何字节写出之前。真实供应商门禁仍需独立执行。

### N02：未知价格的成本上限不能限制实际付费调用

- **风险等级：P2。** 资源价格状态为 `unknown`、输入输出单价均为零时，成本预算会预留 0 微美元。仅打开每日成本上限（例如设为 0）不会阻止发送；供应商实际收费若高于零，管理台的成本保护不足。当前 UI 已提示“价格未知不代表免费”，因此这是后端防护和可操作性缺口，不是隐藏收费的证据。
- **修复风险：中。** 需要区分“已确认免费”“已填估算单价”“价格未知”，并在未知时拒绝成本唯一准入或要求明确的有风险确认；必须保留 unknown 账务和历史价格证据，不能把旧记录回填为免费。
- **根因：** `src/noyra/model/resources.py` 在未填写价格时构造零价格 `ModelPricing`；`src/noyra/model/ledger.py` 用数值 `reserved_cost_microusd` 比较预算，未知价格没有非零保守上界。`admin.js` 的说明文字虽提醒风险，但 `confirmUnlimitedLimits()` 只在四个维度全关闭时确认，成本开关单独开启不会触发价格未知保护。
- **影响：** 仅启用成本维度、同时价格未知或填零的认知资源；次数和 Token 维度关闭时最明显。已知价格或免费确认的资源不触发该具体路径。
- **触发条件：** 资源 `pricing_status=unknown`、两项单价为 0；成本上限开启且其他维度关闭；供应商接受请求。临时真实账本/网关探针发送 3 次并全部成功，报告成本为 0、`unknown_price_attempts=3`。
- **触发概率：** 新接入资源未录入供应商价格时中等；已按文案填价后低。实际供应商账单金额无法从本地探针估计。
- **证据：** `.runtime/reaudit-db9d495-probes.log` 的 `cost_only_unknown_price`。探针没有真实模型调用，所有凭据和 provider 均为合成值。
- **建议：近期修复。** 采用 fail-closed 合同：成本是唯一启用维度且价格未知时拒绝授权，或要求一次性、清晰标注的 operator opt-in 并强制同时启用次数/Token 上限。列表、API、预算状态和审计日志都显示“价格未知，成本限制未生效”。补充未知、免费、改价、重试和费用未知四类回归。

### N03：旧健康哈希兼容路径不验证新增明细形状

- **风险等级：P2。** `ProviderHealthStore` 接受旧版 bucket hash 时，没有要求新增的 `error_counts_json` 和 `latency_samples_json` 必须是规范、非负、与 attempt 数一致的值。被篡改的健康投影可能显示负错误数或负 P95 延迟，影响运营判断和熔断决策。需要本地数据库写权限或迁移/恢复数据损坏，当前没有远程直接写入路径。
- **修复风险：中。** 直接取消旧 hash 会破坏合法历史迁移；应将旧格式转换为明确的 legacy 空明细，或在兼容期只接受 `{}`/`[]`，然后用新 hash 重写。修复需验证 schema71/旧备份恢复和完整性告警。
- **根因：** `src/noyra/core/provider_health.py:_verify_bucket()` 将 `state_hash` 与新 hash 或 `_legacy_bucket_hash(row)` 任一匹配即接受；legacy hash 不包含新增明细，且当前代码只做 JSON 解析，没有检查字典键、整数非负性、样本范围、样本数上限或 `len(samples) <= attempts`。`src/noyra/core/integrity.py` 使用同一兼容集合。
- **影响：** 健康页面、路由可用性和按小时汇总；模型账本和秘密值不会因此直接改变。只有健康记录被外部篡改、损坏或不可信恢复时触发。
- **触发条件：** 临时数据库先写合法 legacy hash，再写 `{"auth":-999}` 和 `[-800]`；`list_projection()` 接受并返回这些值，探针稳定复现。
- **触发概率：** 正常产品写入路径低；拥有数据卷/备份写权限的恢复、人工修复或损坏场景无法估计。不是公网无鉴权漏洞。
- **证据：** `.runtime/reaudit-db9d495-probes.log` 的 `legacy_health_validation`。本轮针对临时数据库运行，未修改项目或生产数据库。
- **建议：近期修复。** 保留合法旧 hash 的明确迁移状态；对兼容记录强制空明细，新增记录严格验证类型、非负性、计数关系和 128 样本界限。任何不合规值应产生完整性 finding 并阻止投影/路由，而不是展示修复后的猜测值。

### N04：公开投稿容量控制存在请求外快照窗口

- **风险等级：P2。** HTTP 路由先读取控制配置，再将 `queue_cap` 和 `storage_cap_bytes` 传入 `PublicPostStore.create()`；`create()` 在事务内重新读取长度限制，却使用调用方传入的队列和存储上限。管理员降低容量后，已经取到旧配置但尚未提交的请求可能仍写入超出新上限的内容。它不会删除已有帖子，也不会绕过验证码或字符长度限制。
- **修复风险：低至中。** 在同一写事务内读取并锁定当前控制快照，或传入配置 revision 并在事务内比较；必须保留幂等、并发容量、可信作者和访客验证码合同。
- **根因：** `src/noyra/service.py` 的 `/api/public-posts` 处理器调用 `owner.public_post_controls()` 后再调用 `public_posts.create()`；`src/noyra/interaction/posts.py:create()` 对 `length_policy()` 在事务内复核，但对传入 `storage_cap_bytes`/`queue_cap` 只当作有效值使用。
- **影响：** 管理员刚降低队列或存储上限时的并发投稿；旧配置快照在请求开始前已经获得的时间越长，窗口越大。新请求在没有旧快照时会按新值拒绝。
- **触发条件：** 请求 A 读取旧配置；管理员提交更低上限；请求 A 随后进入事务并完成投稿。临时探针以旧 10000 字节快照提交 1100 字节内容，在当前新上限 1000 时仍接受；用新上限调用则正确拒绝。
- **触发概率：** 单次配置变更期间为并发窗口，普通低流量环境低至中；高并发公开页面更容易遇到。没有生产请求时间线，不能计算比例。
- **证据：** `.runtime/reaudit-db9d495-boundaries.log` 的 `stale_public_cap`：`new_cap=1000, accepted_chars=1100, new_cap_blocks=true`。临时数据库、operator provenance、无网络。
- **建议：近期修复。** 将队列/存储控制读取移入 `create()` 的同一事务，或让控制 revision 成为准入条件并对旧 revision 返回明确冲突。补充降低上限与并发投稿、幂等重试、访客/可信作者和已有内容保留回归。

## 仍需单独修复的前端会话问题

### N05：写操作后的刷新延续可污染新登录会话

- **风险等级：P2。** 这是上一轮 R07 的补充缺口：旧动作状态可能出现在已清空的新登录会话，不证明服务端越权、原文/密钥泄露或自动重试。
- **修复风险：低至中。** 前端 continuation 增加 generation 判断即可，但不能把已被服务器接受的写操作当作取消/回滚，也不能自动重发。
- **根因：** `src/noyra/web/admin.js:810` 的 `walletRefreshAfterWrite()` 在接受写操作后等待 `refresh()`，成功之后没有 generation 复核；失败时将 `errorText(staleSession)` 的 `null` 插入字符串，绕过 `setStatus()` 对 literal null 的抑制。公共 `request()` 已保护单个迟到 GET/POST 响应，却不能保护调用者已持有的消息及后续刷新延续。聊天发送内层 catch、保留设置读取失败提示也有类似固定文本写入，需要按同一根因排查。
- **影响：** 钱包登记、采集、付款策略和执行后的状态提示；用户可能误认为新会话已经执行旧动作。当前探针只证明状态污染，没有证明新会话列表/资金被改写。
- **触发条件：** 旧会话写操作成功返回；刷新尚未结束；退出并重新登录；刷新完成或返回 staleSession 错误。原函数 VM 稳定复现。
- **触发概率：** 正常连续使用低；慢网、主动换会话、后台处理较慢时中等。没有真实会话日志计算百分比。
- **证据：** `.runtime/reaudit-db9d495-ui.log` 输出旧提示 `old private operation 42` 和 `old operation；读取更新失败，请刷新核对。null`。该实验执行实际 helper，不访问浏览器/服务器，也不含真实私密内容。
- **建议：近期修复。** 所有写操作在入口保存 generation，任何 await 后改变提示、表单、缓存、按钮前复核；stale 错误要直接结束延续，不能经模板字符串变成可见错误。增加写成功后刷新挂起、刷新失败、退出后重登录、同会话正常完成四类行为测试。

### N06：迁移策略表单的版本冲突保护被最新 GET 绕过

- **风险等级：P2。** 已打开的旧迁移草稿可能覆盖其他管理员/窗口刚保存的费用、目标 allowlist、启用状态等策略。服务端参数校验和自动模式确认仍存在，本轮没有证明不经授权自动迁移或突破签名门禁。
- **修复风险：中。** 必须把“编辑基准版本”和“提交前最新策略”分开；后台自动刷新保留未保存草稿时不能悄悄更新其基准 revision。冲突后保留草稿并让操作者比较/重载，避免丢失输入。
- **根因：** `admin.js:1916` 的 submit 先 GET 最新 policy，然后使用 `expected_revision: current.revision` 提交 DOM 里的旧字段；`:191` 的 `loadMigration()` 保留 dirty draft，却没有给草稿绑定版本。`MigrationStore.update_policy()` 的 CAS 正确，客户端主动拿最新版本号替旧草稿背书，导致后端无法识别这次过期编辑。
- **影响：** 两个窗口/管理员同时编辑迁移策略，或策略被其他渠道修改而旧草稿仍打开。
- **触发条件：** A 读取 revision1 且费用0；B 改成 revision2、费用100；A 保存时先 GET revision2，再提交费用0和 `expected_revision=2`。原 submit handler VM 确认该 payload，真实 MigrationStore 接受并改回0；若传 revision1，后端正确拒绝冲突。
- **触发概率：** 单窗口无并发低；多窗口编辑或长时间保留草稿时中等。满足上述条件必现，无法给出生产百分比。
- **证据：** `.runtime/reaudit-db9d495-policy-ui.log` 的 `actual_migration_submit` 和 `.runtime/reaudit-db9d495-boundaries.log` 的 `migration_cas`，均为合成值。
- **建议：迁移管理交付前修复。** 表单加载时记录编辑 revision；dirty draft 不被自动刷新更新基准；提交该 revision。最新 GET 可用于风险确认和对比，但不能替换编辑基准。复测两窗口、dirty 自动刷新、冲突重载和策略安全确认。

### N07：embedding 和搜索连接等待期间缺少撤销复核

- **风险等级：P1。** 本地资源撤销完成后，已有请求如果仍在连接/工作线程等待、尚未发送，可能继续用内存凭据发送输入。embedding 涉及记忆内容，搜索涉及查询与费用；当前没有真实供应商外发或生产事故证据。
- **修复风险：中至高。** 同步 embedding worker 与异步搜索要共享“最终发送前授权”的合同；不得把已发送但结果未知的费用清零，或自动更换资源重发私密输入。工作线程还需要明确租约传播/终态结算边界。
- **根因：** `model/embedding.py:231` 的 `call_authorizer` 在构造/执行 HTTP 请求前读取 live 状态，但发送头时没有复核；`research/search.py:510` 读取 active API key 后进入异步连接，同样没有 trace 授权检查。它们没有复用认知模型已添加的 `send_request_headers.started` 保护。现有 embedding 测试只覆盖“调用开始前已经停用/撤销”，不能覆盖等待期间发生撤销。
- **影响：** 已通过前置授权但尚未写请求头的两个适配器；撤销后才新开始的调用仍会被正确拒绝，不能声称所有撤销均无效。
- **触发条件：** live 授权/取 key 完成；连接/transport 等待中管理员撤销；随后开始请求发送。合成 transport 在发送前 barrier 完成真实 `revoke()`，之后仍接受发送，分别返回向量和搜索 succeeded。
- **触发概率：** 窗口通常短，正常场景低；连接延迟、线程排队、故障期间集中撤销时增加。网络供应商是否已撤销对应凭据仍决定其是否接受请求，百分比无法估计。
- **证据：** `.runtime/reaudit-db9d495-external-dispatch.log`：embedding `resource_status=revoked, sends_after_revoke=1, vectors_returned=1`；搜索 `resource_status=revoked, sends_after_revoke=1, result_status=succeeded`。使用真实存储和适配器、本地合成 transport，无网络、无付费。transport 模拟前置授权与写头之间的等待，不是实测公网 DNS/TLS。
- **建议：与 N01 一起立即修复。** 每条实际发送头路径重新读取资源状态/key 指纹，同步 worker 不能只依赖调用线程的旧检查；同时检查运行租约。涵盖禁用、撤销、秘密清理失败、连接/池/线程等待以及 unknown 费用回归。

### N08：紧急恢复整文件哈希产生线性内存和写锁占用

- **风险等级：P2。** 大备份注册/复核会一次性分配与备份大小相当的内存；紧急恢复复核还持有 SQLite 写事务，可能在最需要恢复时 OOM 或长时间阻塞其他写入。这是可用性边界，不是签名/文件哈希绕过。
- **修复风险：中。** 流式哈希可减少内存，但移出事务后必须复核文件身份、注册状态和期望哈希，防止 TOCTOU。不得仅凭第一次扫描的结果继续恢复。
- **根因：** `migration/recovery.py:88` 和 `:395` 使用 `hashlib.sha256(path.read_bytes())`；`:184` 的 `restore_standby()` 在 `Database.transaction()` 内调用 `_verified_backup()`。备份字节数只要求正数，没有常量大小上限/内存预算或取消截止时间。
- **影响：** 注册迁移恢复备份和执行 emergency recovery，文件越大内存/写锁越大。普通聊天/定期健康检查不直接调用此函数。
- **触发条件：** 使用大于剩余内存的合法备份，或哈希盘读取很慢；OOM 取决于运行环境。8MiB 合成备份的 tracemalloc 测得注册峰值8398188字节，事务复核峰值8403087字节，确认完整线性分配，而没有制造真实 OOM。
- **触发概率：** 小备份低；主体长期积累、低内存服务器、紧急恢复时中至高；不能据8MiB探针推算实际故障率。
- **证据：** `.runtime/reaudit-db9d495-backup-memory.log`：`file_bytes=8388608`，`verification_inside_writer_transaction=true`；注册和签名/恢复既有回归仍通过，不代表大备份预算通过。
- **建议：大备份/紧急恢复使用前修复。** 改为固定块流式哈希和时间/尺寸预算；耗时文件扫描移出写事务，进入事务后进行文件身份和注册 revision 再确认。复测文件替换、尺寸变化、读取错误、超时、低内存、并发数据库写入。

### N09：发布 full gate 的 Ruff 范围与全仓 CI 不一致

- **风险等级：P3。** 当前 db9d495 全根 Ruff实际通过，但未来标签发布可以仅通过钱包 full gate 的部分路径检查，未要求同 SHA 的 quality CI 完成，可能漏检其他 scripts/受跟踪素材。它不是当前代码 lint 失败，也不表示发布绕过所有测试。

- **根因：** `.github/workflows/release.yml:39` 依赖 `audit-wallet-stage4b4.py --scope full`；该脚本`:442` 起只对 `src`、`tests` 和两份脚本执行 Ruff check/format。全仓 CI 和 `verify-committed.py` 已使用根目录，release没有要求 quality workflow 同 SHA 的成功结果。
- **影响/触发条件：** 未来引入仅在上述路径外的 Ruff 错误、然后直接创建标签。条件成立后该 full gate 不检查这些文件；本轮没有创建标签或注入业务改动测试该假设。
- **触发概率：** 当前无错误，低；路径外脚本持续增加时上升，无法估计。
- **证据：** 发布 workflow和钱包审计工具的命令清单；已有静态检查记录证明当前提交全根通过。
- **建议：下次发布前修复。** full gate 改为根目录 check/format，或发布必须依赖同 SHA 的完整质量门禁。契约测试应断言完整范围，不能只断言命令存在。
