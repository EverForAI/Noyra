4. 使用 OS 只读 URI 和 query_only 的单一 SQLite 快照重跑 `_check_actions`：动作账本校验通过；失败位于随后执行的 `_verify_core_provenance` → `_provenance_object`，而非动作状态哈希比较。

6. 用户随后提供完整的审计操作类型分组：模型发现拒绝 3 条、发现成功 4 条、草稿测试失败 12 条、草稿测试成功 4 条，共 23 条；搜索测试成功 2 条、搜索路由更新 1 条，共 3 条。合计正好 26 条，均为原校验器遗漏的动作类型。其他现存管理登录、唤醒、钱包配置与采集、历史钱包授权类型已有对应校验器。计数吻合只确认类型覆盖，不替代全部 26 条的实际字段、所有权和动作链校验。
7. 对升级前提交 `b9ee0c56ed4da1a21d2d500525f4fe0ffc673ea3` 的源码复核确认：上述模型/搜索管理写入端已存在，搜索测试解析器也限制最多三个结果。兼容边界来自实际历史写入合同，未推测或重建生产记录。

根因是审计写入端与完整性读取端合同遗漏：写入端可以正常产生模型发现与测试、搜索测试和路由记录，读取端既未接纳其历史 JSON 编码，也未提供对应的语义校验。仅扩大 JSON 编码白名单仍不够，记录会在后续“未知审计动作”检查处失败。不能把这类兼容性误报解释为服务器性能不足、API 延迟、物理数据库损坏或已经证实的迁移破坏。

另一个已由本地用例复现的同类不一致：投稿配置写入端增加 `max_content_chars` 与 `length_revision`，而审计读取端仍要求八个历史字段；存储上限下限也仍为旧的 1,000,000 字节，实际 schema 82 起支持 1,000 字节。这会使合法的新配置再次触发 P0。

## 补丁内容与复审

- 精确登记六类模型发现/草稿测试动作及字段集合，兼容 canonical JSON 和管理写入端的精确历史 JSON 编码。
- 对发现数量检查整数、非负和 500 上限；对测试模型检查非空字符串和 256 长度上限；错误码检查类型、长度与字符集合；两类输入拒绝操作要求对应的固定错误码。
- 无资源落库的草稿操作只验证写入端摘要，不虚构资源所有权或真实供应商成功证明。
- 搜索测试只接受四种已支持的供应商类型；成功结果数量要求整数且在 0..3 之间，与真实解析器限量一致；失败只接受写入端两种固定脱敏错误码。搜索路由只接受三种合法模式，不以当前可变模式否定历史模式。兼容三种动作的精确历史编码，不放行任意搜索动作。
- 投稿配置只接受完整的旧八字段合同或含两个长度字段的新十字段合同；拒绝半套字段、额外字段、布尔值冒充整数、非法范围。
- 未知动作、非规范空白、重复键、非有限数字及原有跨主体引用错误仍不被接受。没有放宽核心/钱包审计的历史 JSON 编码要求。
- `scripts/diagnose-action-integrity.py` 使用 `_ReadOnlyDatabase` 和固定快照；不构造 SubjectKernel，不初始化/迁移数据库，不启动主体，不调用模型/搜索。输出计数或失败校验位置，不输出 payload、异常原文、令牌或 API Key。可要求 systemd 单元已停止。
