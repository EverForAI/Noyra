# M42 P1-05 Training Consent Concurrency and Publication Remediation

Date: 2026-08-16

Baseline: `main` / `87e059a` plus the verified M41/M42 remediation work.

## Scope

The audit found two consent failures. Training-policy updates read the current row before opening
their write transaction, so concurrent updates could overwrite unrelated fields and write duplicate
version claims to the audit ledger. A long training export also checked consent only at startup and
published its final ZIP before recording the export, so a revocation committed during the export
could not stop that artifact. This remediation closes those two contracts. It does not claim to fix
export-worker shutdown/cancellation ownership (P1-06) or long-history resource bounds (P1-07).

## Implemented boundary

- `TrainingStore.update_policy()` reads the current policy inside `BEGIN IMMEDIATE`, validates an
  optional caller version, and updates with `WHERE policy_version = ?`. The same transaction writes
  a complete before/after audit event with a strict `N -> N+1` chain. HTTP management updates require
  `expected_version`; malformed or missing versions return `400`, and stale versions return `409`
  with the current policy without changing state.
- Policy audit rows are database-enforced append-only. Idempotently installed triggers reject update
  and delete attempts, so the ordered before/after consent history cannot be rewritten through a
  normal SQLite write path.
- Training archives are written to a hidden same-directory pending file. A final `BEGIN IMMEDIATE`
  publication transaction re-reads every policy field and the policy version. The pending file is
  atomically renamed and the `training_exports`/`training_exported` rows are written only while that
  lease still matches.
- If policy or version changed first, the pending file is destroyed, a `training_export_aborted`
  audit event records the lease/current versions and cleanup disposition, and no final target or
  success row is created. Export jobs therefore finish failed and remain non-downloadable.
- Pending-file cleanup covers ZIP writing, flush/fsync, digest, and stat failures. This closes the
  sensitive staging path introduced by the new publication boundary without claiming the broader
  P1-07 temporary-space contract.

## Evidence

`tests/test_m42_p1_05_training_consent.py` provides five deterministic contracts:

- two callers are held immediately before their write transactions; the old implementation would
  have read the same version first and lost one field, while the fixed implementation serializes the
  reads, preserves both fields, and records the exact version chain;
- a stale compare-and-swap is rejected without an audit event, and the management API independently
  verifies required versions and `409` conflict behavior;
- a publication gate commits revocation after staging but before publish, proving the target,
  `training_exports`, and success audit remain absent while the abort audit survives;
- the same revocation through `ExportJobManager` never reaches a downloadable job; and
- injected pending-file digest failure leaves no final or hidden pending artifact, while database
  triggers reject consent-audit mutation and deletion.

## Acceptance state

P1-05 is `verified` in `tests/contracts/remediation_acceptance.json`. P1-06 was still open at this
closure point because a manually cancelled or closing worker could run exporter code and append
success rows before the manager discarded its ZIP; it was subsequently verified in
`docs/audit/2026-08-15-remediation-m42-p1-06.md`. P1-07 remains open for data-volume work roots,
disk-backed deduplication, bounded episodes, real-time byte/free-space budgets, cooperative
cancellation, and all-exit cleanup.
Those findings are not implied to be fixed by the consent publication transaction.
