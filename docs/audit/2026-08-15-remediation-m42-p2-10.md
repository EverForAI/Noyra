# M42 P2-10 Migration Safety Remediation

Date: 2026-08-15

## Scope

This remediation closes the database migration safety finding from the read-only audit. It does
not alter application behavior beyond making schema initialization fail closed and recoverable.

## Changes

- `Database.initialize()` reads and validates the existing `schema_version` before running
  current-schema DDL. A marker newer than the runtime is rejected without changing the database.
- Every migration from an older marker creates a SQLite-backup image beside the database. The image
  is checked for its original marker and `PRAGMA quick_check = ok` before it becomes durable.
- Migration setup runs under rollback journaling and enables WAL only after all schema and policy
  setup succeeds. This keeps a failed migration from retaining Windows WAL handles.
- Any versioned migration or its optional-feature setup failure restores the verified image, removes
  temporary journal sidecars, and rechecks the restored database before returning the original
  failure.
- Schema 32 owns the `secret_cleanup_queue` table and index, and schema 33 owns the
  append-only `behavior_log_revisions` chain; optional-feature setup remains idempotent for
  databases created by earlier versions.

## Evidence

- Historical schema 6, 16, 21, 27, and 31 fixtures migrate to schema 33 with their anchor event
  unchanged and a verified `.pre-migration-vN.bak` image retaining the original marker.
- A future-schema fixture is rejected before DDL and remains byte-identical, including a sentinel
  table and row.
- Injected failure before migration 21 restores the original marker and anchor event, leaves the
  backup verified, and passes `PRAGMA quick_check` on Windows.
- Focused M41 verification: `16 passed`.
- Cross-platform targeted runner: `53 passed` for both smoke and large profiles.
- Full repository pytest: `326 passed`; deployment audit: `40 passed`, `72.07%` coverage.
- Ruff, format, Mypy, compileall, pip check, and production-lock `pip-audit` all passed.

## Residual risk and follow-up

The backup is local to the database directory and is intended for crash rollback, not disaster
recovery. Current-version additive feature checks remain idempotent and are outside this historical
migration contract; any future repair that changes their durability must add its own rollback test.
Operational backup retention and restore drills remain part of P2-14/P3-06. M42 next continues with
the next open acceptance contract; no schema-changing repair should bypass this preflight and backup
gate.
