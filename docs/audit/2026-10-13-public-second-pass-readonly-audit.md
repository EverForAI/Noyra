## A01：首页 DOCTYPE 被帮助文字破坏

**证据位置：** `src/noyra/web/index.html:1`；引入提交 `780091f`，git blame 与父提交已核对。

当前首行是：

~~~html
<!doctype <small>空行分段；#、##、### 加空格表示标题。正文不执行HTML、图片或链接代码。</small>html>
~~~

父提交首行仍是标准 `<!doctype html>`。因此这是本轮 S05 的明确模板回归。

**根因：** 投稿语法帮助文字插入了 DOCTYPE 内部，HTML tokenizer 将文档类型名称读为 <small；后续说明文字成为 body 文本。普通字符串检查、JS/Node、Ruff/Mypy，以及“375px 没有横向溢出”不会检查文档模式。上一份复审把新增帮助说明视为已交付，却没有验收其实际 DOM 位置。

**真实浏览器证据：** 直接读取当前静态 HTML/CSS/JS，Chromium 返回：

~~~json
{
  "compatMode": "BackCompat",
  "doctype": "<small",
  "headElementCount": 0,
  "bodyContainsHead": true,
  "syntaxHelpInForm": false
}
~~~

375×812 截图位于 `output/playwright/second-pass-doctype-audit.png`。页面顶部出现帮助文字和 html>；document.head 为空，title/meta 位于 body。截图没有水平溢出。静态服务没有 API，截图中的“服务不可用”和 404 是诊断环境，不将它们报告为生产故障。

**影响：** 所有首页进入 quirks mode，盒模型和解析语义可能因浏览器不同而变化；原 head 中的 SEO/分享/viewport 等元数据进入正文，不能再仅凭响应文本包含标签就宣称有效 SEO。移动页出现额外文本，屏幕阅读器也可能读出。CSS/JS 在 Chromium 仍可运行，不能夸大为整个网站失效；没有看到本项导致越权或正文泄露。service.py 的首页 asset 替换只注入资源版本/metadata，不修复首行，因此实际首页也继承该结构问题。

**触发条件与概率：** 当前首页按 text/html 解析，Chromium 已必现；没有穷举所有浏览器，不给出跨浏览器显示细节的百分比。

**修复风险/安全边界：** 低。恢复标准声明，将说明移到投稿正文控件旁的 small。保持 SEO、CSP、主题、草稿和无脚本阅读合同，不能用运行时脚本遮住顶部文本冒充修复。

**建议与验收：** 立即修复。增加 HTML 解析和浏览器 CSS1Compat/head 归属断言；确认说明出现在表单内；检验实际 Noyra HTTP 首页而非只搜索 HTML 字符串；重新核对 SEO 注入和移动页面。

## A02：站点图分片缺少稳定的实例生命周期合同

**证据位置：** `public_archive.py:328`、`330`、`646`、`704`；`service.py:9755`。token 加密由 `3fe2109` 引入。

**根因：** 每个 PublicArchive 构造随机 AES-GCM 密钥，描述符使用随机 nonce。密钥仅在该实例内保存，没有跨重启/worker 共享与轮换兼容窗口。重新生成 index 即使数据不变也会生成不同 URL。旧描述符拒绝已在当前测试和 public-contract-v2 文档中明确规定；这不是隐藏的越权漏洞，而是可用性/爬虫合同取舍尚未完整。

**复现：** 合成主体有一条公开摘要。当前实例读分片成功；另一个 PublicArchive 实例读取同一 token 得 ValueError。连续两次生成描述符，token_same=false。HTTP 的 ValueError 分支会映射为 400 invalid_public_query。

**影响：** 爬虫保存 index 后，服务重启就无法读取其中分片；多进程部署若 index 和 part 分属不同 owner，将有类似失败。当前服务为同一 owner 的单进程多线程，不能误称当前已经多 worker 故障。每次重新抓取 index 会发现新的一组分片 URL，增加抓取成本。no-store 不等于爬虫承诺不保存链接。旧 token 仍不能读撤回正文，保密和主体隔离有效。

**触发条件与概率：** 重启/新实例后复用旧 token 必现；多实例故障频率取决于路由粘性、worker 数和滚动策略，未实际部署测量。只在同实例立即顺序请求通常不触发。

**修复风险/安全边界：** 中。规划仅用于路由描述符的版本化共享密钥或稳定不泄露私有字段的索引机制；明确备份、恢复、轮换与兼容期。继续认证绑定 subject/kind/anchor/range，重新查公开状态/hash，禁止将明文主体/未经验证边界泄露到 URL，也禁止正文缓存绕过撤回。随机 AEAD nonce 不应简单改成固定 nonce。

**建议与验收：** 稳定 sitemap 是发布前优先项。至少验证真实 systemd 重启、两个独立 owner 和滚动切换；保留篡改、跨主体、损坏和撤回测试。暂时保留单实例实现时，必须公开其重启限制，不能宣称稳定生产分片合同已交付。

## A03：未配置站点图的 404 缓存与新合同不一致

**证据位置：** `service.py:9724` 的未配置分支；`_text:9806` 默认 `public, max-age=300`；`service_contract.py:19` 和 v2 文字合同承诺 no-store。

**根因：** 未配置分支没有显式传 cache_control，继承静态文本的默认缓存。git blame 显示该分支来自 `e36cf643`，本轮不是新写入这个缓存行为；S06 新登记 no-store 合同时，没有补齐旧分支。应归为既有遗漏被新增合同暴露，不能归咎于 3fe2109 新增该分支。

**HTTP 复现：**

~~~
/sitemap.xml（未配置）    404  Cache-Control: public, max-age=300
/public/goal/not-present  404  Cache-Control: no-store
/public/goal/x?theme=bad  400  Cache-Control: no-store
~~~

配置后的 sitemap 成功分支明确 no-store，JSON 400/413/503 使用公共合同 no-store，公共 article 404 也显式 no-store。本项没有扩大为所有动态错误都错误缓存。

**影响：** 客户端/代理可能将未配置 404 保留 300 秒；配置完成并重启后，仍可能先看到旧 404。本项目没有后台实时修改该服务设置的证据，不推定能即时热更新。短暂不可发现属于低影响运营合同问题，没有数据泄露。

**触发条件与概率：** 服务未配置 URL 时响应头必现；后续负缓存影响需客户端/代理实际缓存并在窗口内访问，条件概率依缓存策略。

**修复风险/安全边界：** 低。只给该动态 404 显式 no-store，并覆盖未配置、重复/错误参数、预算、撤回、413/429/503 的路由缓存矩阵；不要全局修改静态 _text 缓存合同。

**建议：** 立即补正，局部小改动足以关闭。P3 不代表可以继续把合同测试称为所有分支已闭合。

## A04：阅读返回状态在无关视图中残留

**证据位置：** `app.js:19`、`400`、`596`、`1048`、`1094`。

**根因：** readingReturn 在列表打开文章时保存；showView 仅在返回同一列表且无 activeId 时消费并置空。进入 about/participate 或另一个列表时保留它，使“返回文章来源”的一次性状态变为跨导航的旧状态。

**Node 复现：** 加载当前 app.js 的函数，使用合成 DOM，路径为 diary 搜索 old → 文章 → about → diary。about 后 readingReturn 仍存在；重新进入 diary 时恢复 old 与旧 batchPath。控件被设为 new 后也会被旧值覆盖。showView 和保存/消费逻辑均为当前源码，refresh stub 只阻止外部请求，不改状态逻辑。

**影响：** 用户从菜单重新访问列表也会恢复旧查询、时间锚或批次；从 about 的其他文章链接进入时，返回链接还可能沿用旧列表。只影响导航/解释，不修改数据库，不缓存私有内容。正文重新读取，所以不能称为撤回绕过。

**触发条件与概率：** 上述跨视图路径在当前状态机中必现。直接点文章返回链接时消费状态是正确行为；常规直返不受影响。

**修复风险/安全边界：** 低中。按明确的阅读导航链消费状态，进入非相关视图即清除，或与 origin/代次绑定。保留投稿草稿，不能通过重载整文档清掉状态，也不能保存正文/验证码/令牌到持久存储。

**建议：** 可暂缓，随导航模块增加菜单/后退/直链/语言主题矩阵和原批次恢复专项。

## C01：极短页下完整批次恢复仍未成立

**证据位置：** `app.js:735`、`752`；当前复审明确说明最多 20 次请求。

**根因：** wanted 为原可见条数，恢复最多执行 20 次读取。S02 合法页可短到 1–2 条或空过滤页；20 次读取不一定补足原 200 条。原测试证明普通 20 条和 13 条短页可达，不能代表全部短页组合。

**有界复现：** 当前 loadView/refresh，mock API 每页 2 条且持续有 next_cursor，请求恢复 200 条：reads=20、visible=40、nextCursor=240。没有跳过记录，用户仍能继续加载。

**影响：** “返回上一批/原阅读批次”在冷段碎片和大量过滤下只能部分恢复。数据显示当前 40 条，没有伪装成 200 条；问题是原条数恢复目标不足，而不是数据丢失或阻断所有历史访问。

**触发条件与概率：** 原批次需要超过 20 次短页或空页请求恢复，满足时必现。冷段粒度和过滤决定生产发生率，未统计。

**修复风险/安全边界：** 低中。保留有界请求上限，增加“尚未恢复完，可继续”说明，或设计总时长/次数受控的恢复目标元数据。不能无限串行请求、保留撤回正文作为快照或假装完整。

**建议：** 可暂缓。把“完整恢复”改成准确的有界合同；如需实现完整恢复，须增加 1/2 条短页、空过滤页、撤回、超时及迟到响应矩阵。

## C02：站点图总索引仍为全量扫描

**证据位置：** `public_archive.py:646`；`_ReadBudget:90`；`service.py:9755`。

**根因：** 每次索引请求都枚举所有公开类别和行，为每 100 条（冷段另分割）生成描述符，没有增量/持久索引。仍受 250000 VM steps、2 秒、128MB 逻辑读取、5 万描述符和 2MB HTTP 响应约束。现有支持范围已经文档化，不将它报成新隐蔽容量漏洞。

**复现：** 隔离库批量生成 25000 条公共日记投影，使用不同时间与 ID，正文/state hash 与当前 PublicDiaryStore 校验同源。单条分页可返回一条并有游标；sitemap_partitions 在约 0.026 秒触发 public SQL read budget exceeded。先前同时间元数据合成也触发，正式结论采用不同时间/hash 有效版本，避免把全同排序键当唯一原因。

这些是合成当前表投影，没有通过 25000 次真实睡眠/发布流程，因此不把该数宣称为所有生产实例的固定阈值；证明的是读取容量边界和查询步骤限制。

**影响：** 长期增长的合法记录会使整个索引返回 503，即使单页仍可读。文字合同提出“缩小支持范围或未来索引”，但当前 HTTP sitemap 没有日期范围参数，不能给管理员不存在的缩小参数操作建议。

**触发条件与概率：** 大数据/慢盘/锁竞争；本机合成已复现步骤预算触发，小数据较低，长期增长风险上升。

**修复风险/安全边界：** 中高。索引需主体隔离、增量更新、撤回重新检查、可重建/备份恢复和一致性边界。不能删除公开验证、取消预算、把 503 改成成功空图，也不能裁剪数据但标记为完整。

**建议：** 可暂缓完整索引工程，立即确认支持规模并在发布前做容量验收。1002 条成功证明旧 1000 上限已解除，不证明未来任意数据规模可读。

## C03：逻辑预算不能代表 RSS 或硬终止期限

**证据位置：** `public_archive.py:90`、`210`；`event_archive.py:812`、`844`、`915`。

**根因：** consume_bytes 在 load_segment 完成后记账；该阶段包含读取、认证解密、有界解压、JSON 对象构建和逐事件 hash。64MB 单段和128MB累计限制防止无限原始正文，但字节数不统计 Python 字符串/字典/中间副本的 RSS。deadline 在 SQL progress/checkpoint 检查，不能抢占阻塞文件系统或整次 CPU/JSON 操作。公开冷读两槽限制并发，只解决解密请求数量，不是全服务进程资源隔离。

**影响：** 请求可能在检查点前超过2秒，RSS可能高于128MB；被拒绝后保留槽直到实际工作结束。没有真实负载测量，不能断言已经 OOM、能无限膨胀或所有 hard timeout 无效。

**触发条件与概率：** 较大冷段/JSON 对象、慢盘、非可取消调用和其他运行任务并发。存在结构风险；实际超时/RSS概率未知，当前不编造百分比。

**修复风险/安全边界：** 中高。先测RSS/墙钟/慢盘并设部署容量，再考虑流式处理、检查点或进程隔离。保留主体/hash、local-only、无云写入、槽释放和未知结果合同，禁止异步强杀线程冒充可靠取消。

**建议：** 大规模隔离可暂缓，发布前必须给出目标硬件实测。保持“协作检查点、逻辑工作量”的准确表述，本轮已说明这一点。

## C04：钱包管理投影仍保留自己的 monotonic 时钟

**证据位置：** `wallet/admin_projection.py:89`、`91`、`139`、`142`；代码由 `b99233c` 引入，本轮未修改。

**根因：** 该模块独立创建3秒时限并用 time.monotonic 同源消费。同步 HTTP/钱包RPC等改为 perf_counter，但本模块没有参与迁移。这里没有把旧时钟的绝对数传给新时钟消费者；因此不是跨原点混用，也没有证据表明新改动导致付款错乱。

**影响：** 现有 Windows 低分辨率平台在3秒边界附近仍有约15ms量化误差。作用对象是只读列表查询，无资金 side effect。S07 已限定同步HTTP生产/消费范围，不能仅凭残留字符串就说其全部修复失败。

**触发条件与概率：** 低分辨率Windows查询接近3秒阈值；普通短查询低，刻度边界条件下可出现偏差。本次没有实际3秒超限故障复现，结论为静态完成度建议。

**修复风险/安全边界：** 低中。同源替换并保留预算、SQL progress handler、hash和错误类型；审查是否还要组合请求剩余预算，避免改变既有只读列表合同。service 健康缓存、shutdown等待和asyncio私有时钟不与同步HTTP绝对时限互传，不要求盲目全局替换。

**建议：** 可暂缓，随管理列表时限完善；不把它当新P1/P2资金安全回归。

## E01：目标环境与精确 SHA 发布证据未完成
