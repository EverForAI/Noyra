### D01：合法审计事件仍能造成完整性误报与暂停

**问题风险 P1；修复风险中；置信度高。**

**位置**

- [协作申请撤回写入](<E:/我的项目/Noyra/开发版/src/noyra/interaction/collaboration.py:572>)：`participant_application_withdrawn` payload 用普通 `json.dumps()`。
- [管理员来源绑定写入](<E:/我的项目/Noyra/开发版/src/noyra/interaction/participant_http.py:106>)：`participant_source_bound` 也用普通 `json.dumps()`，字段顺序是 entity_id、binding_id。
- [规范 JSON 验证](<E:/我的项目/Noyra/开发版/src/noyra/core/integrity.py:1515>)：`_provenance_object()` 比较 `canonical_json(parsed) == value`；只对 `_ADMIN_AUDIT_ACTIONS` 允许一种旧管理端序列化格式。
- [实际调用验证器](<E:/我的项目/Noyra/开发版/src/noyra/core/integrity.py:3115>)：两个参与者 action 不属于该旧格式例外，进入业务分支前已经失败。
- [QQ 私聊关联](<E:/我的项目/Noyra/开发版/src/noyra/interaction/inbound.py:1176>) 与 [解除关联](<E:/我的项目/Noyra/开发版/src/noyra/interaction/inbound.py:1204>)：写入 `private_route_changed` / `private_route_unlinked`；当前 core/management/wallet action 集合均未注册它们。

**根因**

业务写入与全局验证分别维护事件名称、序列化和引用契约。上一轮只增加参与者 action 的注册/字段验证，没有把两个真实写入器产生的历史 JSON 纳入读取兼容，也没有扩展检查同一个共享审计表的其他合法业务写入者。

普通 JSON 带空格，来源绑定还存在字段顺序差异。仅修字段名或给新写入改为 canonical，仍不足以恢复已经持久化的旧合法事件。QQ 事件则是独立的注册遗漏，不能靠 JSON 格式修复消除。

**触发条件**

1. 用户正常提交并撤回本人的协作申请；或管理员通过 HTTP 正常绑定参与者来源；或管理员确认 QQ 身份后正常关联/解除私聊历史。
2. 随后运行包含 `core.actions` 的深度完整性检查。
3. 若策略是 `pause`，错误 finding 会触发安全暂停；`alert` 则留下严重误报。

**影响**

并非数据库真实损坏，但会报告 `corrupt` / `core.actions:integrity_error`。正常账户协作与来源管理可以中断实例活动。事件持久存在，重启不会自动消除误报。

**本轮独立复现**

- 正常申请撤回：检查由 `ok` 变为 `corrupt`；异常落在 `_provenance_object`；实际 `pause` 策略将 lifecycle 从 `active` 变为 `paused`。
- 真实来源绑定 HTTP：返回 200，检查由 `ok` 变为 `corrupt`，同样是合法 payload JSON 格式被拒。
- 真实 QQ 关联接口：检查由 `ok` 变为 `corrupt`；异常为 action 未注册；解除关联后仍 `corrupt`。
- 没有手工插入异常审计行、关闭数据库约束或伪造 state_hash。

**归因与上一轮评价**

这是上一轮 C01 的未完成修复及更广的存量缺口，不把“已知问题仍未修好”重新标作新引入。`1039614` 增加的上下文冲突事件验证本轮确有正向通过证据，但参与者两个真实写入入口没有闭环。QQ 分支更早已存在，本次扩展审计发现。

**建议与安全边界**

统一精确的事件契约；对已落库合法旧格式提供限定 action、限定字段、明确 actor 与同主体引用的读取兼容。未知事件、非法 payload、错 purpose、跨主体引用仍须拒绝。不得删除历史事件或降低完整性策略“修复”误报。

**修复验收**

真实撤回、真实来源绑定、QQ 关联/解除关联后运行 core.actions；验证后续正常状态变化与历史事件并存；非法 actor、跨主体引用、字段缺失/多余、非有限数值仍失败；正常业务不误停，真实损坏仍触发暂停。

### D02：保存的 Windows 信任策略在省略参数时没有恢复

**问题风险 P2；修复风险低至中；置信度高。**

**位置**：[信任策略恢复条件](<E:/我的项目/Noyra/开发版/deploy/windows/noyra-lifecycle.ps1:265>)、[严格验证外部指纹检查](<E:/我的项目/Noyra/开发版/deploy/windows/noyra-lifecycle.ps1:211>)、[策略写入](<E:/我的项目/Noyra/开发版/deploy/windows/noyra-lifecycle.ps1:414>)。

**根因**

未提供 `[string[]]$TrustedPublisherThumbprints` 时该变量是 `$null`。当前条件使用 `@($TrustedPublisherThumbprints).Count -eq 0`；此处数组包装包含一个 null 项，因此不会进入 `Read-PublisherTrustPolicy`。后续 `Normalize-Thumbprints` 又把它规范化成空列表，严格验证报“需要外部可信指纹”。

这与已经修好的“单个字符串没有 `.Count`”是不同的调用边界。新代码没有覆盖未绑定参数的 null 形状。

**触发条件**

先以明确外部指纹成功严格安装，安装目录已存在 `trusted-publishers.json`；随后按新增文档说明省略重复的指纹参数，执行严格版本的 rollback、start 或升级验证。

**影响**

已保存策略没有兑现复用能力，正常恢复命令失败。临时重新显式提供指纹可绕过本项可用性问题，但不能解决 D03/D04，不能据此称完整恢复流程通过。

**本轮复现**

内存证书合法签名包安装和升级均成功，策略文件实际存在；省略参数 rollback 返回：

```text
Signature verification requires an external trusted publisher thumbprint.
```

未启动 EXE、未修改证书库。真实执行脚本、已保存文件与返回错误构成完整证据。

**归因**：恢复分支由 `56a89b5` 新增，属于本轮次生缺陷。

**建议与边界**

在参数边界明确区分 `$null`、空数组、单项、重复/空白项；先规范化或显式判 null，再决定读取受控策略。不能从包的 self-declared thumbprint 重建信任，也不应让损坏的策略变成无签名模式。

**修复验收**

安装后启动、升级和回滚分别覆盖省略参数、显式空数组、单/多指纹、错误/损坏/链接策略；确认清单签名、PE 签名与外部 pin 验证没有弱化。

### D03：当前版本损坏时无法回滚到完好版本

**问题风险 P2；修复风险中；置信度高。**

**位置**：[rollback 新增当前版本验证](<E:/我的项目/Noyra/开发版/deploy/windows/noyra-lifecycle.ps1:432>)。

**根因**

为决定旧版本是否需要强制签名，rollback 先对当前版本调用完整 `Verify-Package`。当前版本任何文件哈希不匹配或文件缺失，都会在检查完好旧版本之前抛异常。用于恢复的动作错误依赖于被恢复对象本身完好。

**触发条件**

有合法 previous 版本；当前版本因磁盘损坏、误修改或不完整文件受到破坏；管理员执行正常 rollback。无需恶意包或证书异常。

**影响**

明明保有可验证旧包，恢复命令却失败，current 指针仍停留在损坏版本。不会自动破坏旧版本数据，但延长服务不可用时间并迫使操作者人工修改恢复状态。

**本轮复现**

正常 install 开发包 v2、upgrade 开发包 v3；仅对临时安装目录 v3 的合成 module.py 制造文件损坏，再 rollback：

```json
{
  "old_version": "unsigned-v2",
  "new_version": "unsigned-v3",
  "rollback": "Package hash mismatch: module.py",
  "current": "unsigned-v3",
  "executable_started": false
}
```

用非严格合成包隔离了证书变量，证明是恢复顺序本身的问题。

**归因**：完整验证 current 的步骤由 `56a89b5` 引入，基线只验证 previous。属于明确次生退化。

**建议与边界**

把恢复所需的严格信任要求保存在独立受控策略中，rollback 验证候选旧版本、指针和策略，不要求损坏 current 通过全库存验证。不能直接删除签名检查或跳过旧包来源认证。

**修复验收**

当前源码/配置/launcher/manifest 损坏、current 包部分丢失与正常版本都覆盖；旧包损坏/不可信时仍拒绝；失败不改 current/previous；保留 DataRoot。

### D04：发布者轮换后旧合法包被“列表不相等”拒绝

**问题风险 P2；修复风险中；置信度高。**

**位置**：[清单与外部 allowlist 严格相等](<E:/我的项目/Noyra/开发版/deploy/windows/noyra-lifecycle.ps1:221>)、[新策略覆盖保存](<E:/我的项目/Noyra/开发版/deploy/windows/noyra-lifecycle.ps1:414>)。

**根因**

验证把“包清单声明的受信列表”要求为“当前操作者允许的列表”的完全相等副本，而不是验证实际签名者及包内执行者是否仍被当前外部策略允许。外部策略加入新的发布者时，旧包声明的较小列表没有变化，即使旧发布者仍然被允许也失败。

**触发条件**

v1 在外部策略 A 下签发；v2 显式扩展策略为 A+B，并成功安装；管理员要求回滚 v1，且保留 A 的信任。v1/v2 的清单与文件都完好。

**影响**

扩展可信发布者与保留历史 rollback 能力不能同时按当前实现正常工作。证书轮换后恢复需要额外手工切换策略，不能兑现已说明的常规升级/回滚流程。

**本轮复现**

生成两份只在内存中的证书 A/B，v1 由 A 签署、v2 由 B 签署；启动器为同一个系统有效签名文件且在外部允许列表中。初次 install 与 rotation upgrade 成功。为了隔离 D02，rollback **显式传入 A+B 的完整当前策略**，仍返回：

```text
Package trusted publisher metadata does not match installer trust policy.
```

旧签名者 A 没有被撤信，current 仍是 v2。

**归因**：完全相等约束在 `8401984` 已存在；本轮增加了 CMS 和持久策略，但没有完善跨版本轮换语义。分类为存量兼容约束/本轮未闭环，不归咎于 CMS 密码学本身。

**建议与边界**

明确当前外部策略与包的签发身份声明的关系；实际签名者和受认证库存必须由外部允许列表约束。历史允许者仍保留时允许旧合法包恢复；已撤信发布者必须拒绝。不能采用清单自证信任或默认重新接受旧被撤证书。

**修复验收**

A→A+B→B 的轮换、两证书同时有效、A 已撤信、显式回滚授权、无外部策略、签名替换与错身份；不得通过固定写回旧策略掩盖撤信。

### D05：其他联系人私聊派生的目标标题进入社交回应

**问题风险 P2；修复风险中至高；置信度高。**

**位置**：[全局活动目标查询](<E:/我的项目/Noyra/开发版/src/noyra/cognition/social.py:207>)、[加入社交 payload](<E:/我的项目/Noyra/开发版/src/noyra/cognition/social.py:314>)、[外发草稿提交](<E:/我的项目/Noyra/开发版/src/noyra/cognition/social.py:523>)。

**根因**

`origin != 'human_proposal'` 只说明目标并非未采纳的人类提议，不说明目标标题可向任何联系人分享。内部生成的 `self/environment/mixed` 目标仍可能使用 Bob 私聊作为因果来源，标题本身就含有私人事实。当前社交模块把这些全局目标标题加入面向 Alice 的模型上下文，没有检查逐收件人共享授权或来源链。

上一轮移除了 global memory recall、过滤了其他人的 affect，但“收件人上下文”尚未形成统一的来源策略。

**触发条件**

Bob 与实例有真实已归属的私聊；由该私聊事件正常形成/激活一个内生目标；Alice 是当前主动社交收件人；目标进入活动前八项。无需篡改数据库或使用命令式人类目标。

**影响**

Bob 私人事实进入给 Alice 生成内容的模型输入，并存在被复述为实际 outgoing 草稿的通路。这里证明的是条件性泄露路径，不是声称真实供应商必然逐字复述每个目标。

**本轮复现**

通过 AccountStore、InteractionStore、GoalStore 的真实接口创建 Bob 私聊及其 `origin='self'` 目标，标题含 `PRIVATE_BOB_GOAL_70fa396b`；本地响应器仅回显实际收到的该标记：

```json
{
  "result": "relationship_social_contact",
  "private_goal_in_actual_request": [true],
  "private_goal_in_outgoing": true,
  "recipient_is_alice_route": true,
  "external_send_performed": false
}
```

没有伪造模型预知秘密，没有启动外部发送器。

**归因**：全局目标查询早于本轮修复；属于存量问题。上一轮 C03 的安全边界要求检查 goal/event 等同类字段，但实际提交只改了 affect；这属于修复覆盖不足而非新引入目标泄露。

**建议与边界**

面向具体收件人构造允许来源集合。没有分享授权的目标标题/描述不进入对外生成；可保留不带私人细节的固定聚合决策压力。不要删除目标、清空心理状态或仅增加“请保密”提示词来代替来源过滤。

**修复验收**

检查 memory、affect、goal、event 以及派生标题；覆盖同联系人/他人、公开/私密/混合来源、内生目标与已采纳提议、旧无归属数据；验证实际 prompt 与 outgoing 内容，同时保留私有认知对合法目标的使用。

### D06：12 个不可用关系遮蔽第 13 个有效联系人

**问题风险 P2；修复风险中；置信度高。**

**位置**：[先截取前 12 个关系](<E:/我的项目/Noyra/开发版/src/noyra/cognition/social.py:186>)、[之后才做路由准入](<E:/我的项目/Noyra/开发版/src/noyra/cognition/social.py:268>)、[从合格候选取首项](<E:/我的项目/Noyra/开发版/src/noyra/cognition/social.py:279>)。

**根因**

上轮正确地把无有效 route 的关系排除，但关系清单早已按熟悉度/亲近度取前 12 项。不可用关系仍消耗所有扫描名额，后面的有效关系从未进入准入判断。把“输出上下文有界”误用为“先截断再验证可运行性”。

**触发条件**

至少 13 个已知联系人；排序前 12 个的 binding/transport 不可用且熟悉度较高；第 13 个仍有合法路由。前 12 个状态不变化时，该条件可以长期保持。

**影响**

主动社交返回无上下文/不执行，独立有效联系人无法被选择。这是主动社交的可用性问题，不表示所有认知工作流都死锁，也不表示每 tick 都产生额外模型费用。

**本轮复现**

通过真实入站、身份归属、关系修订和绑定禁用接口创建 13 位联系人。显式调用第 13 位的 `_route()` 成功后，执行正常 `_context()` / `run_due()`：

```json
{
  "known_contacts": 13,
  "unavailable_first": 12,
  "valid_contact_rank": 13,
  "valid_route_counterparty": "bob-room",
  "context_is_none": true,
  "run_result": null,
  "provider_calls": 0
}
```

**归因**：提前截断来自更早 `8661fcc`，基线存在。上轮 `22f052c` 的“首项失效、次项有效”基本用例确实修好，但没有覆盖候选数界限。属于存量缺口/修复不完整。

**建议与边界**

先以有界分页/可运行性索引找到合格候选，再限制送入模型的关系数量；避免每 tick 无界扫描全部联系人。继续冻结原 transport/binding/房间，不通过改投或伪造 Noyra 的 wait/拒绝来消除技术故障。

**修复验收**

0/1/12/13/更多联系人；前 12 个禁用/撤销/缺失、后项有效；状态在模型前/期间/提交前变化；恢复与重启；验证缓存不会复用到另一房间，且扫描和费用均有界。

## 5. 两项不计入确认缺陷的观察

### O01：社交未知重试失败、更换会话/时段后的业务身份

purpose 仍含小时与 route_key。旧 unknown、executing 或不匹配 route 的 prepared 在当前小时被拦截；failed 授权重试、跨小时和独立新会话是否属于同一社交业务，需要明确业务契约。不能仅以出现新模型调用判定重复执行，也不能把未知历史当作所有新邀请的永久封锁。

本轮没有把这项已存在的语义观察改列为确认缺陷，没有修改恢复语义。

### O02：严格模式目前仍是逐次显式开关，持久化文件只保存 allowlist

本轮实际验证：已完成严格签名安装后，省略 `-RequireSignature`，给 upgrade 一个 `signature_required=false` 的普通开发包，升级被接受，current 指向开发包。即使修好 D02，当前 `$signatureRequired` 的计算也不根据“已有持久信任策略”自动强制签名。

**这是已确认的行为，但是否违反既定产品契约需区分。** 当前命令行把 RequireSignature 定义为一次调用的开关，文档只承诺保存 allowlist，没有明确宣称严格安装会永久锁定安全模式。故本报告没有把“操作者未传该开关”直接归为 P1 签名绕过。

若产品要承诺“实例一旦严格安装，后续默认不能降级到开发包”，则应把严格模式独立持久化并要求显式授权降级；潜在影响 P1、修复风险高。若保留逐次选择，则需在文档与命令说明中明确这一行为。**实际传入 `-RequireSignature` 时，本轮重写清单的包被拒绝，没有证据说明 detached CMS 的内容签名被绕过。**
