## 实现问题

### Q01：通讯消息缺少连接等待后的最终外发检查

- **风险等级：P1。修复风险：中至高。** 可能在暂停、隔离、迁移围栏或停用通道之后外发消息正文；必须同时保留已发结果和 unknown 的真实含义。
- **根因：** `src/noyra/interaction/transport.py:1663` 的 `_assert_message_send_allowed()` 会检查当前租约、通道、私密路由和接收绑定，但 `_send()` 在第 1797 行调用一次后直接进入 `AsyncClient.stream()`。请求没有像模型/API 搜索一样安装 `send_request_headers.started` 授权钩子；连接池、DNS、TCP/TLS 等待之后不再复核。返回后检查失效，只能拒绝旧结果或记 unknown，不能撤回正文。
- **影响：** 已经进入发送流程的 HTTP 通讯；通道停用、绑定/路由撤销的同类最终边界也应一并审查。本探针直接确认租约失效及通道停用，未分别证明每一种路由竞态。邮件另有发送前回调，不能据该 HTTP 反例断言所有 SMTP 路径必然同样失效。
- **触发条件：** 消息先通过授权；连接尚未真正发送；另一个控制动作使租约失效或通道停用；连接完成后继续发送。
- **触发概率：** 平稳运行时低；连接慢、主动暂停/停用、迁移或隔离发生时为条件性并发窗口，无法量化线上比例。合成等待点满足条件后稳定复现。
- **证据：** `.runtime/reaudit-e4bfc5d-probes.py/log`。`transport_lease` 为 `sent_after_withdrawal=1, send_trace=false, delivery_status=unknown`；`transport_disable` 为 `sent_after_withdrawal=1, delivery_status=delivered`。后者证明通道撤销后仍发送并接受合成成功回执，不证明供应商凭空伪造回执。
- **建议：立即修复。** 把租约、通道、绑定/路由及来源授权固定到该请求，并在真正发送头之前复核；同步/异步及 token 刷新重试使用同一合同。发送前拒绝可以取消，已经发出的成功/失败/unknown 必须真实结算，不能自动重发或仅改终态名称掩盖外发。
- **验收：** 连接等待期间的暂停、隔离、通道停用、解绑、路由撤销；任何字节发出前拒绝；已发响应丢失及成功回执保留；幂等、重试与入站回复目标不串号。真实平台验证另走 E01。

### Q02：供应商令牌交换没有同等撤销围栏

- **风险等级：P1。修复风险：中。** 这是凭据交换的外发授权问题，不能只修复最终消息发送。
- **根因：** `_send()` 第 1737 行先调用 `_provider_credentials()`；`_provider_token()` 第 1102 行起获取 token 缓存锁，随后第 1150 行起直接发送 QQ/飞书的 App Secret JSON 或微信的 secret 查询参数。锁等待、连接等待及实际发送前，没有复核通道/秘密状态和当前租约。Q01 的消息检查发生在这些请求之后。
- **影响：** 需要新令牌或刷新令牌的 QQ、飞书、微信配置；有效缓存命中的调用不会发生这次外部交换。供应商本来有权在有效配置下接收 App Secret；缺陷在于本次授权撤销后仍进行交换，不等同于把凭据发给任意第三方。
- **触发条件：** token 缓存过期/不存在；任务等待 `_provider_token_lock` 或连接；通道停用或运行租约失效；等待结束后发送。
- **触发概率：** 平时取决于缓存命中率，通常低；集中刷新、多个待发消息、网络延迟及管理员停用时更易出现。无生产样本不能估计发生率。
- **证据：** `.runtime/reaudit-e4bfc5d-token-fence.py/log` 在真实 dispatcher 中锁住 token 获取，等待任务到达后撤销再放锁。`provider_token_wait_lease`：交换 1 次且 `lease_valid=false`；`provider_token_wait_disable`：交换 1 次且 `transport_active=false`。输出仅含合成状态和 URL 路径，没有凭据。
- **建议：立即修复。** token 交换应有独立、固定请求的授权快照，并在锁等待后及发送头前再次核验；处理停用/撤销后的缓存失效，禁止失效任务自动刷新。不要以消息随后被拒绝作为凭据交换安全的证明。
- **验收：** 缓存命中、缓存过期、并发刷新、401 刷新、等待锁期间停用/撤销、不同 transport 身份隔离；无效授权不触发外部交换，已完成交换的凭据仍按秘密保护合同管理。

### Q03：INFO 日志保存通讯凭据及私有搜索查询

- **风险等级：P1。修复风险：中。** 若日志被额外运维人员、收集系统或备份读取，会扩大凭据和私有研究上下文的可访问范围。
- **根因：** `service.py:10553` 默认配置根日志为 INFO；httpx 的 INFO 日志记录完整请求 URL。`transport.py:1140` 附近微信交换把 App Secret 放在查询参数；`interaction/outbound.py:187` 把 access token 放入消息 URL；Telegram adapter 第 36 行起把 bot token 放入 URL 路径；`research/browser.py:174` 把查询文本放入 Bing URL。数据库中的秘密引用、私有 endpoint digest 和 action 的 query hash，不会自动清洗第三方库的日志。
- **影响：** 微信 App Secret/access token、Telegram bot token、浏览器私有查询；含秘密 URL 的其他 webhook/供应商接口也需同根因检查，本轮不把未经探针确认的每个平台单独计为漏洞。日志是否实际外传取决于 journald 权限、收集和留存配置。
- **触发条件：** 使用这些适配器，httpx 日志有效级别为 INFO 或更详细，请求完成并生成 URL 日志。
- **触发概率：** 在默认 INFO 及上述请求路径下，合成调用稳定记录明文；是否有真实凭据已写入生产日志、是否被第三方读取均未知。本轮没有搜索或输出生产秘密。
- **证据：** `.runtime/reaudit-e4bfc5d-probes.log`：`app_secret_logged=true`、`access_token_logged=true`、`bot_token_logged=true`、浏览器 `query_logged=true`。捕获的是实际 httpx logger 输出，报告仅保存布尔结果。
- **建议：立即修复。** 为网络日志建立默认脱敏合同，清洗查询参数、路径中的 token、请求/响应头及异常；同时约束第三方 httpx/httpcore 的 INFO/DEBUG 输出。只关闭一处业务日志不足以修复。历史日志暴露评估与必要的凭据轮换要单独准备、执行和验证，不在本轮只读任务中直接轮换或删日志。
- **验收：** 按默认及调试日志级别测试微信/Telegram/浏览器，以及携带秘密的自定义 URL、超时/非 2xx/异常；内存捕获日志、文件和服务日志均不含合成秘密或完整私有查询。保留可诊断的域名、请求分类、状态码和时延。

### Q04：浏览器搜索缺少租约围栏，并可能留下 executing 行动

- **风险等级：P1。修复风险：中至高。** 暂停/隔离之后仍可能向外部搜索供应商发送私有研究查询，同时管理记录不能真实反映这次发送。
- **根因：** `research/browser.py:58` 的 `search()` 和第 168 行的 `_request()` 没有当前租约检查或发送头钩子。行动从 prepared 转 executing 后跨网络等待；租约失效后，`ActionLedger.finish()` 的普通数据库事务被提交围栏拒绝。成功/失败/unknown 收尾没有使用仅限终态记账的范围，无法在拒绝旧结果的同时保存真实结果。
- **影响：** `browser_search:bing_rss` 分支。API 搜索在 `research/search.py` 已有钩子及终态记账，不能把该修复外推到浏览器。行动的公开输入保存 query hash，并不能阻止原查询发给 Bing 或进入 Q03 的 URL 日志。
- **触发条件：** 浏览器行动已开始；暂停、隔离、迁移或关闭使租约失效；请求仍继续；正常终态事务被拒绝。取消或错误路径同样需要正确收尾。
- **触发概率：** 稳定请求低；慢请求与运行控制重叠时条件性发生，无法给线上百分比。合成场景确定性复现发送和 executing 残留。
- **证据：** `.runtime/reaudit-e4bfc5d-probes.log`：`browser_send_fence` 中 `sent_after_fence=1, lease_valid=false`；通过完整 `search()` 调用得到 `browser_settlement_after_fence.action_status=executing`。
- **建议：立即修复。** 对浏览器分支加入相同的租约/路由准入和最终发送检查；仅允许真实终态结算在失效后完成，随后拒绝旧结果，不继续换路由或新的搜索。不要开放任意过期租约写数据库的旁路，也不要把所有在途请求默认为取消。
- **验收：** 开始前拒绝、连接等待撤销、已发送成功/失败/响应未知、任务取消、重复幂等键、路由停用、小时限额；执行结束没有无来源的 executing 残留，查询原文不进日志。

### Q05：付款准备与最终签名之间没有复核最新付款策略

- **风险等级：P1。修复风险：高。** 影响紧急暂停和关闭付款的操作含义，涉及不可撤销资金执行；本轮只证明合成签名请求仍发生，没有真实付款。
- **根因：** `wallet/execution.py:1555` 的 `_prepare()` 在事务内核验策略、额度、费用、余额、nonce，并创建 signing 状态；`execute_order()` 第 934 行起随后调用 `_sign_and_broadcast()`。第 2110 行的最终边界只检查运行租约并调用 signer，没有重新验证付款策略版本/紧急暂停。`WalletEconomyStore.update_policy()` 第 597 行起及管理台暂停接口只更新政策，没有使这项已经准备但未发送的授权失效。
- **影响：** 已从预留进入 signing、但 signer 尚未收到请求的订单，包括自动执行和显式重试的最终边界。正常新准入会正确拒绝暂停，本问题不推翻已有单笔/日限额、unknown 预留和 nonce 保护。
- **触发条件：** 准备事务提交；管理员成功停用策略或紧急暂停；执行随后才调用 signer。即使运行 epoch 不变，也应明确这些尚未外发的付款如何停止。
- **触发概率：** 两步骤紧邻时通常低；线程调度、系统负载及付款队列扩大窗口，紧急暂停恰在付款准备后时可能出现。没有生产付款时序或订单量，无法量化。
- **证据：** `.runtime/reaudit-e4bfc5d-wallet.py/log` 使用既有真实临时账本夹具，在 `_prepare()` 返回后执行正常策略更新，再继续原 `execute_order()`；绑定有效运行租约。结果 `policy_mode=disabled, emergency_paused=true, signer_requests=1, execution_status=broadcast`。
- **建议：立即修复。** 为付款策略撤销和实际签名发送建立共同的线性化边界，固定并复核策略版本、暂停和执行身份；单独补一次数据库读取仍可能有新的读后竞态。定义“已准备未发送”“已发送”“结果未知”三个阶段的暂停效果，不宣称已经广播的交易能撤回。
- **验收：** 停用、急停、允许网络/资产及额度调整发生在准备后、发送前；普通执行和 unknown 显式重试都遵守；不得重复签名、擅自退款或释放可能已付出的余额/Gas 预留。并发暂停回执应清楚标注仍有已发/未知付款。

### Q06：签名 HTTP 超时后，未退出的工作线程可越过运行围栏

- **风险等级：P1。修复风险：高。** 主线程认为签名调用已经以 unknown 返回并允许暂停/迁移，但底层未完成的请求仍可能首次把转账命令发给签名器。
- **根因：** `_sign_and_broadcast()` 在主调用线程持有 `external_side_effect_scope()`；`HTTPSWalletSigner._request()` 第 335 行起通过 `call_sync_http_with_deadline()` 把实际网络发送交给另一线程。`core/http.py:170` 的绝对超时只让调用方返回，不能强制取消 worker。`SyncHTTPTimeoutHook` 第 28 行起只有收到 response 后才有可关闭对象；连接/请求头等待期没有 response，也没有最终发送前截止时间/租约钩子。调用方超时释放 gate 锁后，worker 已复制的 ContextVar 不会自动阻止请求。
- **影响：** HTTPS 独立签名器的转账请求；不是本地 MockSigner 的正常同步锁语义，也不证明每次网络超时必有迟到发送。进程最多四个 sync worker 的容量保护及 unknown 结算仍存在，不能把它夸大为无限线程或已确认重复广播。
- **触发条件：** 网络 worker 在首次发送前耗时超过整体 deadline 且未实际退出；调用方收到 unknown 并释放 gate；暂停/关闭/迁移使租约失效；worker 随后继续真正发送。
- **触发概率：** 正常短连接低；延迟分布、连接池、解析/TLS/自定义传输及超时故障时条件性增加。合成传输模拟非可取消等待，真实默认 transport 出现的频率尚未测量。
- **证据：** `.runtime/reaudit-e4bfc5d-wallet.py/log` 调用真实 engine 的 `_sign_and_broadcast()` 和真实 HTTPS signer，使用 50 ms 整体 timeout 与合成等待。调用方已得到 `WalletBroadcastUnknownError`，随后失效 gate、放开 worker：`caller_returned_unknown=true, sent_after_timeout_and_fence=1, lease_valid=false, has_send_trace=false`，路径仅为 `/v1/transfer`。
- **建议：立即修复。** 取消/截止时间及最终运行授权必须传入真正网络 worker，并在任何请求字节写出前检查；不可取消 worker 仍须被追踪到退出或被有效发送围栏阻止。保留 unknown、nonce/请求幂等和原付款预留，不因客户端超时释放已发送资金。
- **验收：** 超时发生在排队、DNS/TCP/TLS、发头前、发体后、等响应和读体各阶段；超时后暂停/迁移/重启、迟到成功和 response hook 关闭竞态；没有未发请求在失效后首次发送，已发请求对账不重复或丢失。

### Q07：令牌响应的大小限制在完整缓冲后才生效

- **风险等级：P2。修复风险：中。** 异常供应商响应会造成内存峰值和服务资源压力。
- **根因：** `_provider_token()` 使用 `AsyncClient.request()`，httpx 默认先完整读取响应；第 1157 行后的 `read_bounded_response()` 虽设 `TRANSPORT_MAX_RESPONSE_BYTES=2_000_000`，进入函数之前 body 已经消耗。现有异步整体超时限制时长，不构成严格字节或内存上界。
- **影响：** QQ/飞书/微信令牌交换。消息正文请求使用 stream，不能据此认定全部通讯响应都无界。token cache 锁串行化部分获取，仍不能防止单个响应消耗过大。
- **触发条件：** 实际 token 响应超过 200 万字节，或压缩响应解码后超过限制，且在 deadline 前持续提供数据。
- **触发概率：** 官方正常 token JSON 很小，通常低；供应商故障、可配置接口或异常代理场景未知。异常条件下稳定复现前置缓冲。
- **证据：** `.runtime/reaudit-e4bfc5d-probes.log`：合成流返回 8 MiB，`configured_limit=2000000, consumed_before_rejection=8388608, error_type=ValueError`。这是读取计数，不是 RSS 测量；本轮没有据此声称准确的服务峰值内存。
- **建议：近期修复。** 改为从请求建立到有界读取全程 stream，在同一绝对 deadline 内检查 headers、声明长度、实际及解码后字节，并在任何异常关闭响应。不要只降低事后的 JSON 解析上限。
- **验收：** 无 Content-Length、伪造长度、分块、压缩扩张、慢响应、超大头、非 JSON 与 token 刷新并发；统计读取量与内存，超过限额及时停止并释放连接/锁。

### Q08：旧登录收尾重新启用新登录按钮

- **风险等级：P2。修复风险：低至中。** 已证明按钮状态错乱，未证明服务端越权、私密数据污染或绕过鉴权。
- **根因：** `web/admin.js:576` 的 `login()` 成功后增加会话世代并等待 `loadAll()`；`finally` 无条件执行 `button.disabled=false`。旧会话退出、用户重新提交登录后，旧加载的 continuation 仍能操作同一个登录按钮。退出没有把该登录动作的所有权完整交给新动作。
- **影响：** 慢登录初始化、退出后重登、旧请求错误/完成后的交互；可能让用户重复提交、看到不一致的忙碌状态。其余已修复写操作的 generation 保护不包含这个收尾。
- **触发条件：** 第一次登录进入 `loadAll()` 等待；退出并开始第二次登录；旧等待完成；新登录请求仍未返回。
- **触发概率：** 普通单次登录低；慢网和短时间退出重登时中等，无法量化生产比例。Node VM 时序稳定复现。
- **证据：** `.runtime/reaudit-e4bfc5d-ui.cjs/log` 执行实际 login/logout 函数：`new_login_pending_disabled=true, old_login_finally_enables_new_button=true`；同时记录退出后旧初始化尚未完成时按钮仍禁用。
- **建议：近期修复。** 为登录动作单独固定请求/按钮所有权，明确登录成功导致 generation 自增后应由谁收尾；退出重置登录按钮，旧 finally 不能修改新动作。只比较登录开始时的旧 generation 又可能使首次成功后按钮永远不恢复，需要覆盖完整状态机。
- **验收：** 首次成功/失败、旧初始化成功/失败、退出立即重登、连续重复提交、登录期间退出及服务端会话过期；按钮与当前动作一致，无旧提示/自动重试。

### Q09：公开页面迟到响应覆盖当前视图

- **风险等级：P2。修复风险：低。** 影响页面内容与当前导航的一致性，不是受限管理数据泄露。
- **根因：** `web/app.js:141` 的 `loadView()` 仅在进入时判断 generation；日记、行为、交流、帖子各分支 `await getJson()` 后直接写 `content.innerHTML`。取消旧 controller 并不能保证已经完成 fetch、正在解析 body 或已排入 continuation 的响应消失。
- **影响：** 快速切换公开页面或刷新时，新导航可能显示上一模块内容；用户可能误读生命周期、行为或帖子上下文。`loadState()` 等处已有独立世代检查，不能覆盖 `loadView()` 的每个 DOM 写入。
- **触发条件：** 旧日记请求开始；切换到帖子且新请求完成；旧 body 较晚解析完成并继续写 DOM。
- **触发概率：** 单页稳定浏览低；移动网络、响应体较大或快速切换时中等；无生产导航时序统计。
- **证据：** `.runtime/reaudit-e4bfc5d-ui.cjs/log` 实际 `loadView()` VM：`before=NEW_POSTS, after=OLD_DIARY, old_response_overwrites_new_view=true`，只使用合成显示文本。
- **建议：近期修复。** 在每次 await 后及 DOM 写入前复核该视图 generation，并固定请求所对应的视图。保留 AbortController 作为资源释放，不把 abort 当作唯一正确性保护。
- **验收：** 所有公开视图互相快速切换、旧成功/错误/abort、响应头先完成但 body 后完成、重复刷新；导航、内容和空/错误状态属于同一视图。

## 后续修复建议与停止边界

若用户后续授权修复，建议按以下依赖顺序实施；这份只读报告本身不启动修改：

1. Q03 日志秘密保护：先确定全部日志出口和秘密 URL 形态，保存脱敏诊断能力；历史日志盘点/轮换另列操作边界。
2. Q01/Q02/Q07 通讯模块：统一消息及令牌交换的请求授权、锁等待、最终发送、有界响应及缓存；逐条检查 unknown 与重试，再审计入站身份、QQ 路由和跨会话推送。
