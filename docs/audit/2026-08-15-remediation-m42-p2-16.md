# M42 P2-16 Export Snapshot and Request-Worker Remediation

Date: 2026-08-16

## Scope

The audit found two coupled export hazards: a long runtime or training export could hold a live
SQLite WAL read snapshot while it compressed a large archive, and the historical synchronous GET
routes performed that work on an HTTP request worker. This remediation changes the read boundary and
the route contract. It does not claim to close the separate export cancellation, retention, or
indexed-cursor findings.

## Implemented boundary

- `Database.read_snapshot()` copies the committed database through SQLite's backup API to a
  same-volume, private image. The live source connection closes before the exporter starts its long
  read/serialisation phase, and the yielded image is marked query-only.
- Runtime and training streamers, including the compatibility training collector, read all database
  rows from that image. Archived event payload and observation content metadata are resolved through
  the same snapshot connection rather than opening a second live read connection.
- A per-image lock sidecar prevents maintenance from deleting an in-flight image. Images left by a
  crash are conservatively scavenged after a one-hour grace period only when the lock and SQLite
  exclusive probe are idle. `StorageUsageScanner` counts active and orphaned images while they
  exist, so a crash cannot hide full-database copies from storage pressure handling.
- `POST /api/admin/export-jobs` is the canonical bounded job API. The legacy runtime/training GET
  routes now enqueue the same job and return `202` JSON; clients poll the job and download the
  staged artifact. Export work therefore runs in the bounded export executor, not on an HTTP
  request worker.

## Evidence

The independent P2-16 contracts are covered by
`tests/test_m42_p2_16_export_snapshots.py` and the service route regression:

- runtime and training exports reject live `read_transaction()` use, create and clean isolated
  images, reconcile manifest rows, and release the image after completion;
- an in-flight export test performs a live write and WAL checkpoint while serialisation is paused,
  then proves the new row is not part of the already-copied archive;
- stale-image accounting and cleanup are tested, including an active locked image that cannot be
  scavenged;
- the legacy GET route test blocks the background worker and verifies the `202` response returns
  promptly, then polls the job to completion;
- existing service tests cover authenticated runtime/training job creation and poll/download
  semantics.

The final gate records the exact targeted, full-suite, static, deployment, and read-only counts below
after all changes are applied. Windows execution is local; the reproducible Ubuntu entry remains a
release-environment check because this machine has no Ubuntu/WSL distribution or systemd runtime.

These are the counts at the P2-16 closure point. Later Gate B remediation can increase the repository
test total without changing this historical verification record.

## Acceptance state

P2-16 is `verified` in `tests/contracts/remediation_acceptance.json` only after both independent
contracts pass the focused regressions, M41 smoke/large profiles, full pytest and static gates,
deployment audit, and the read-only API/WAL/snapshot review. P2-04, P2-05, P2-07, and the other
unrelated open findings remain open.
