# Noyra 全项目只读审计

审计日期：2026-10-10（Asia/Shanghai）。被审计提交：`c7ac7cb16d2254d391c3f934b6ee80e74b10be19`。分支：`codex/admin-optimization-20261009`。数据库合同版本：90。

## 1. 结论

本轮确认 **12 项顶层问题或验收缺口：3 项 P1、8 项 P2、1 项 P3，未确认 P0**。其中 R02 是尚未交付的私密删除合同，R03 是精确提交的外部验收证据缺口；不能把这两项描述成已经发生的生产安全事故。R02 的六个子项、R12 的三条依赖公告分别展开，不重复计入顶层数量。

当前版本不能称为“全部优化已经完成并通过生产验收”。最优先的代码问题是：认知密钥在本地撤销后，已创建网关仍能用内存中的密钥发起新的重试请求。其次，资源停用会留下错误的在执行状态、小容量投稿合同不一致、历史用量来源分类失真、部分管理台读取会跨越退出/重新登录边界、路由证据增长没有进入现有容量计数。仓库既定静态门禁和 soak 判定也存在确定问题。

此前审计发现的若干迁移、存储及运行循环阻断已经有实质修复，见第 6 节。本轮没有证据支持“历次修复使整个程序普遍变差”的结论；也不能因为部分修复和测试通过，就推断全部功能与真实环境均已验收。

建议先修复 R01、R04、R05、R09、R10、R12，并补上 R11 的持续回归入口。R06、R07 应在管理台优化交付前完成；R08 应在长期持续运行前解决。R02 必须完成全部删除合同才能宣称该模块完成。R03 应在最终修复提交上实测，不能拿旧服务器版本的健康输出代替。

| 等级 | 本报告含义 |
| --- | --- |
| P0 | 可广泛触发的严重资金、密钥或主体安全紧急问题；本轮没有确认 |

| P2 | 正确性、资源、隐私隔离或质量门禁问题；按使用条件决定是否能短期暂缓 |

修复风险使用低、中、高三级，描述修复引入回归的可能性与后果，不是问题本身的严重程度。低：局部合同或门禁调整；中：并发、跨模块状态和兼容；高：删除、单活、不可变账本或恢复，需要完整迁移/故障验证。

没有足够生产样本计算真实事故百分比。以下严格区分：**满足条件后的结果是否确定**，以及**现实中是否经常出现该条件**。确定性复现写“满足条件必现”；并发窗口写条件性概率；外部环境未知写“无法估计”。不把小型实验当作公网统计。

## 5. 详细发现

### R01：撤销密钥不能阻止既有网关的新重试

- **风险等级：P1。** 管理员执行本地撤销且密钥秘密文件已经删除后，仍可能启动新的模型请求。涉及外发私密输入和费用的授权合同；不是无鉴权远程攻击，也不表示所有新路由都会选择撤销密钥。
- **修复风险：中。** 需要把选中密钥的身份/版本传入每次授权与请求前检查，并保留已经发送、已完成和结果未知请求的真实账务。不能把已送出的请求强行改为“未发送”。
- **根因及证据：** `src/noyra/model/resources.py:3431` 的 `_gateway()` 只读取一次密钥并将其保存在供应商对象；`:2044` 的 `revoke_key()` 提交撤销、审计及秘密清理。`src/noyra/model/gateway.py:147` 每次重试调用账本授权，`:171` 调供应商；`src/noyra/model/ledger.py:121` 的授权检查组状态和策略版本，却没有选中密钥参数或密钥状态复查。撤销密钥不使该供应商对象失效。
- **影响范围：** 已创建、仍在执行/等待重试的认知资源网关。组配置允许多次尝试时尤其相关。没有证明影响与其不同实现的所有搜索或 embedding 路径。
- **触发条件：** 第一次请求以已知结果的可重试错误失败；在下一次供应商请求前撤销选中密钥；同一网关继续重试。外部供应商仍接受该密钥时会完成请求。
- **触发概率：** 撤销落入重试窗口是条件性、通常低至中；故障期间主动撤销时相关性显著增加。满足上述状态且供应商接受时，本轮确定复现。普通无重试调用不触发该分支；不能提供事故百分比。
- **复现：** 完整 schema 临时数据库配置经济池和两个最大尝试。合成供应商第一次调用通过真实 `revoke_key()` 撤销自己使用的密钥，再返回已知可重试失败；真实 `RoutedModelGateway` 随后发起第二次调用并成功。结果：`provider_calls=2`、`key_status=revoked`、尝试状态 `failed,succeeded`、调用终态 `succeeded`。全部秘密均为合成值，没有真实网络外发。
- **建议：立即修复。** 本地密钥撤销应阻止撤销后才开始的新网络请求。故障期间需要彻底阻断时，还应在供应商端撤销密钥；本地撤销不等于供应商端凭据失效。在修复前，不能承诺单凭后台撤销按钮就立即停止所有后续重试。
- **修复验收：** 第一次尝试结束后、重试等待中、授权后但请求前分别撤销；涵盖单密钥、多密钥、组停用、秘密清理失败与 unknown。已撤销密钥不得开始新请求；已完成费用必须保留；未知请求不得自动换密钥重发。

### R02：完整私密删除仍是交付阻断

- **风险等级：P1，功能/隐私承诺阻断。** 用户明确要求删除窗口、聊天原文并清除相关记忆。当前只读评估固定返回删除不可用，没有公开删除动作。现有保守拒绝降低了误删与伪装删除的风险，但不满足已接受的需求。
- **修复风险：高。** 涉及多来源知识、不可变审计、模型输入输出、导出、并发投递、备份恢复和历史数据。不能通过删表、隐藏窗口、清空整个主体或绕过触发器快速完成。
- **根因与证据：** `src/noyra/interaction/erasure.py:95` 的 `assess()` 是只读原型评估，`:118` 固定 `deletion_available=False`。`:427` 的 `_review()` 和 `:486` 的 `_check_derivatives()` 在缺来源、在途调用和未审计域存在时拒绝。管理台没有对应删除 API/按钮。`docs/roadmap/2026-10-10-private-erasure-audit.md` 明确记录内部范围和六项阻断，与本轮源码一致。
- **影响范围：** 所有要求完整删除的用户；成熟主体尤其容易包含旧反思、多来源记忆及心理/目标等派生内容。
- **触发条件和概率：** 当前公开产品路径尝试完整删除时，功能不可用是确定的；内部原型是否能处理某个简单会话取决于数据。不能把简单合成会话测试成功称为生产主体可删。
- **建议：必须在宣称全部优化完成前补全。** 保留只读评估和拒绝保护。先做来源/派生域清单，再实现清除、进度、恢复与残留验证，最后开放确认入口。对于不可重建的历史，必须明确合法处理选择；现有“删除某一窗口”的授权不包含清空其他会话或整个主体。
- **完整验收：** 所有六个子项通过后，验证同主体隔离、窗口 revision、确认、幂等、并发围栏、后台续跑、失败重试、跨域残留、重新检索、迟到响应、导出竞态及恢复防复活。保留无正文收据与费用证据，准确说明外部副本边界。

- **根因及证据：** `scripts/remote-acceptance.sh:142` 在 live 成功后每轮清零 `consecutive_failures`；`:151` 再累计 ready 失败，`:159` 检查 >=3。只要 live 一直成功，ready 每轮失败计数总是 1。终点 `:167` 不依据总失败数输出 degraded/failed，直接 `soak=passed`。
- **影响范围：** 直接使用此脚本的 soak 或只凭零退出状态/末行 `stability=passed` 判断稳定性。额外扫描全部 health-samples 的 wrapper 可以发现异常，但不是每条启动命令都带该检查。
- **触发条件与概率：** live 始终 2xx，ready 连续非 2xx/失败，至少三轮，达到观察终点。在模拟中确定通过。生产持续 degraded 的概率未知；这是服务设计中完全可能的状态，不能仅看进程 running。
- **复现：** 从原文件提取未修改的 soak 函数，仅把输出文件替换为 `/dev/null`；模拟时间、sleep、live 成功和 ready 永远失败。四轮得到 exit=0、`soak=passed samples=4 probe_failures=4`。没有启动/停止真实服务，也没有等待真实四小时/八小时。
- **历史解释：** 用户此前 8 小时记录的 `probe_failures=1` 和 final smoke passed，表明至少有一条就绪失败，不能称为零失败稳定。这个单独瞬时失败不等于本轮复现的连续失就绪，更不能凭脚本缺陷推断其具体根因。
- **建议：立即修复，正式 soak 前阻断。** 每个 endpoint 独立统计连续失败，或按“整轮全部成功”重置，明确定义总失败阈值、恢复间隔和最后 smoke。无故障、容许瞬时退化和失败应有可区分结果；不能仅用 passed 包括全部情况。

### R12：可选 cloud 与开发依赖锁包含已知漏洞

- **风险等级：P2，依赖与持续扫描问题。** 固定版本已知受影响；三条公告的后果包括可用性和特定代理配置的 TLS 保护失效。但本轮没有证明默认 Noyra 请求路径可直接利用，不能把“依赖受影响”改述为已发生的秘密泄露或默认网络鉴权绕过。
- **修复风险：低至中。** 更新 cloud/开发锁中的 `urllib3` 至修复版本并重建哈希，复验 boto3/botocore、代理、流式读取和审计工具兼容。PyPI 的 botocore 1.43.72 元数据要求 `urllib3!=2.2.0,<3,>=1.25.4`，范围允许 2.8.0；这只证明版本约束允许，仍不能代替兼容测试。
- **根因及证据：** `requirements-cloud.lock:21` 与 `requirements-dev.lock:1508` 固定 `urllib3==2.7.0`。基础 `requirements.lock` 不包含它。质量 CI `ci.yml:47`、发布 SBOM `release.yml:161` 仅扫描基础锁；cloud-profile 只安装、导入和 pip check，没有漏洞扫描。锁文件有哈希不代表版本无漏洞。
- **影响范围：** 安装 cloud profile 的运行环境、安装完整开发锁的工具环境；不是所有 base 部署都会安装 urllib3。本轮开发环境确实安装 2.7.0，但没有安装真实 botocore，相关测试使用模拟接线。
- **实测：** `pip_audit -r requirements.lock -r requirements-cloud.lock --no-deps --disable-pip --timeout 15` 和对 `requirements-dev.lock` 的同类扫描均返回 1，发现同一包的 `PYSEC-2026-4177`、`4176`、`4175`，修复版本均为 2.8.0。在线 OSV 记录及 urllib3 官方公告核对一致，公告发布于 2026-10-01。
- **应用路径边界：** `src/noyra/core/archive.py:1131` 起 S3 读取使用 `body.read()`，而不是公告要求的 `HTTPResponse.stream()/read_chunked()`；`:1484` 的默认 boto3 构造没有显式配置禁用 TLS 验证或自定义 proxy SSL context。因此，不能只凭扫描就宣称正常 S3 读取满足三条全部条件。外部 SDK/工具与代理配置仍应独立核对。
- **触发概率：** 锁扫描命中是确定的；可利用性取决于下面各项条件。默认受信 HTTPS endpoint、无特殊代理时预计低；恶意流式源或满足公告代理配置时属于条件性风险，本轮没有攻击实验或生产样本估算事故率。
- **建议：近期修复，cloud profile 正式交付前完成。** 更新两个锁和哈希，不手工向生产 venv 随意安装绕开可重现部署；CI/发布扫描纳入基础+cloud，开发依赖也应定期扫描。受控 base 实例可暂缓 cloud 相关部署动作，但不能宣称整个依赖集合无已知漏洞。
- **验收：** 三组锁扫描不再命中这些公告；受哈希约束的 base/cloud 安装、pip check、S3 超时/池/重试/读取测试、HTTPS 代理验证及审计工具测试通过。暂缓时明确没有相关不可信流式源/特殊代理路径，不把应用层读上限当作修复了库内部解析漏洞。

## 8. 修复顺序与安全边界

1. **恢复可信门禁与依赖：R09、R11、R10、R12。** 先使固定版本静态检查与前端行为测试进入正式验证，纠正 soak 判断，更新已知漏洞依赖并扩展锁扫描；这一步不改变生产主体数据。所有后续修复基于固定提交验证，防止结果口径再次混淆。
2. **修复模型授权与调用终态：R01、R04。** 每次新请求前核对密钥/资源/策略；区分未发送、已知失败与真正 unknown，保留已发生费用与单次逻辑请求幂等。相关竞态审计无阻断后再继续。
3. **修复小容量投稿：R05。** 统一参数合同并走实际 HTTP 接线，保持已有内容和验证码防滥用保护。确认字符数、UTF-8 字节和整体容量分别正确。
4. **修复统计与会话隔离：R06、R07。** 先定义不可变尝试来源和历史 unknown 口径，再处理前端响应 generation/全量退出清理。不得回写猜测的历史 usage，不泄露秘密原文。
5. **补齐长期容量：R08。** 在保留真实审计和多进程互斥的条件下控制等待证据/锁空间，验证满容量时现有工作仍可结算。
6. **完成私密删除：R02a–R02f。** 每域建立来源、清除、恢复与残留合同，逐域审计。无法证明独立的历史保持拒绝；不可推定全主体清空授权。全部验收后才开放删除确认、进度与重试。
7. **固定最终提交，再做 R03。** 在隔离 Ubuntu/LUKS 双机、HTTPS、测试网和 signer 中执行八项正式验收。开发/本地通过与生产可用分别记录，不提前宣称全部交付。

## 9. 尚不能得出的结论

- 没有确认所有潜在缺陷；本报告是全面风险导向复核，不是逐行形式化验证或渗透测试认证。
