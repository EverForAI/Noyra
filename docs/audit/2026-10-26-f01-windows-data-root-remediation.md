# F01 Windows 数据根修复与复审（2026-10-26）

基线：`2dc8fbcc79babce66b4fdaa95a1bad8e637b4f9a`；分支：`codex/fix-f01-windows-data-root`。本轮只实施 F01，不处理暂缓的 F02，也不改变 F03/F04。

## 问题与根因

原生 P1：Windows 生命周期只用 DataRoot 放锁/PID/恢复绑定，没有把该值传给启动器。标准环境配置默认 `.runtime/data`，而子进程工作目录是版本目录，所以数据可能落入 `InstallRoot/versions/<version>/.runtime/data`；换版本会指向不同目录，卸载安装树可能删除实际数据。

修复风险为高，主要是旧数据位置不明确、存在多个主体副本、已有运行进程和 R03 路径绑定。方案采用启动显式绑定、默认拒绝隐式新建、遗留数据阻断，以及不自动迁移真实数据来控制这些风险。

## 最终行为

### 1. 实际启动绑定绝对持久化根

`deploy/windows/noyra-data-root.ps1` 使用 ProcessStartInfo 配置当前子进程，设置 NOYRA_DATA_DIR、NOYRA_MANAGED_INSTALL_ROOT、NOYRA_MANAGED_DATA_ROOT、NOYRA_MANAGED_INITIALIZE。父进程环境不改动；两个实例分别创建自己的环境副本。子进程 UseShellExecute=false、CreateNoWindow=true、窗口隐藏，不通过 shell 拼接参数。

生命周期的 start 仍由原有签名、清单、已选择版本与发布者校验决定启动器。新 helper 纳入 Windows 包 builder 的文件集合和 manifest 哈希，不从运行状态目录加载代码。

### 2. 标准运行时再次验证

新增 `src/noyra/core/managed_data_root.py`，在 ServiceSettings.from_env 及 NoyraService 构造最前面检查：托管信息完整、所选路径与 DataRoot 一致、安装和数据根互不包含、路径没有文件/链接组件、Windows 路径没有危险别名。

检查在创建数据目录、获得数据库锁、初始化 SQLite 前执行，不打开或改写现存数据库。没有托管变量的源码/Linux/container 路径保持原有配置。

已有非空普通数据库继续由原有 schema、主体身份、genesis、事件链、加密、所有权与准入门禁验证。本 guard 的 ready 不是对数据库内容完整性或运行健康的认证。

### 3. 缺库不静默新建主体

普通 start 遇到缺库会拒绝。零字节库、目录或链接也会拒绝。明确创建全新主体时，首次 start 必须加 `-InitializeDataRoot`，而且目录不能有主体残留；仅允许生命周期锁与父进程刚发布的 PID 文件。

已存在数据库时不能使用初始化开关；库丢失而残留 secrets/WAL 等时不能用该开关“修复”。开关只对 start 有效，不是迁移、恢复或绕过旧数据审查的授权。

此处引入了有意的使用变化：全新托管 Windows 实例首次启动需要明确初始化。用户可见步骤已写入部署与发行文档；不能为兼容旧的隐式创建行为而恢复风险。

### 4. 旧安装数据先保护

在 install/upgrade/start/rollback/recover/uninstall 的接管和版本状态写入前，遍历完整安装树，检查隐藏和未选中的版本；发现 `.runtime` 或 `noyra.sqlite3*` 就阻断变更，不读取或移动秘密内容。目录链接不会被跟随；不可读树、逃逸路径或超过 100,000 个条目时拒绝继续。

这针对已知默认位置和库/sidecar 标记；无法推断任意历史自定义 NOYRA_DATA_DIR。因此缺库默认拒绝、且初始化要求明确确认仍是必要的第二道保护。

stop/status 在旧数据存在时继续可用。status 增加 data_root_status 和 legacy_data_paths。根路径本身不安全或原有权威状态不可读时，仍按相应边界拒绝，不承诺绕过原有失败。

卸载先检查、再停止匹配进程、再检查一次数据和解析后的根路径，最后才递归移除安装树。外置 DataRoot 保留。数据在停止期间新出现的场景有真实入口断点注入测试覆盖；不依赖函数调用顺序文本断言。

### 5. 旧进程身份兼容

新记录为 noyra-process/v2，包含绝对 data_root。读取 v2 时检查该值与当前 DataRoot 一致；旧 v1 记录仍按 PID、开始时间和可执行文件路径匹配后允许停止。

已运行 v1 的普通 start 不会把它视为已完成数据绑定，需要先停止并审查实际数据位置。PID-only/无效/错误数据根的记录仍拒绝控制，不按猜测杀进程。

## 旧数据迁移的安全边界

[迁移规程](../deployment/windows-data-root-migration.md) 规定先确定权威数据和主体锚点，停机并锁定，备份完整持久数据及外置历史密钥，还原到原生命周期已绑定的 DataRoot，核对后把旧版本内的遗留数据移到安装树外保护区。多份不同主体不自动选取或合并；不删 WAL，不重写 R03 绑定，不删除旧存档以消除提示。

遇到真实旧安装的 `legacy-data-detected` 表示保护生效，需要按具体实例完成迁移，不代表代码已自动迁移该实例。标准备份的 cache/本机控制队列等排除项与外置凭据须单独审查。

## 差异复审与剩余边界

- 未修改数据库 schema、主体生成规则、迁移协议、认知/模型/钱包逻辑、R03 权威状态机或签名撤销策略。
- 新的早期检查只约束托管数据根或已发现的遗留安装数据；不自动放行有歧义的恢复场景。F02 的真实旧安装接管问题仍按用户决定暂缓。
- 新旧 PID 记录的读取/停止兼容、重复启动、PID 复用及错误路径均有回归；测试中没有控制不相关进程。
- 生产环境变量/配置不打印凭据。扫描诊断只列安装路径和稳定错误代码；不读取秘密文件内容。
- 路径检查拒绝链接，但不声称防御恶意本机管理员在最后检查后立即替换目录；受信任本机维护与现有目录权限仍是部署前提。
- 自定义发布启动器必须传递托管环境并调用标准入口；本地环境报告子进程与真实服务构造不能替代最终签名启动器、目标主机 BitLocker/ACL/断电演练。
- 本轮没有迁移现存 Windows 数据，没有连接 Linux 服务器；不能将源码修复已完成表述为线上已升级。

## 使用与下一步

合并/发行前在隔离 Windows 目标机执行 install→首次显式初始化→普通启动→upgrade→rollback→uninstall，确认各阶段都读取同一外置数据库，且卸载后主体仍在。已有旧安装必须先按迁移规程处理；不要在原生产实例上把 -InitializeDataRoot 当作排错操作。

本轮完成后可以保留修复提交。下一项建议单独设计 F03 的重试退避取消结算；F02 继续保留复现和待办，不混入当前数据根修复。
