- **P1 / 高**：破坏核心安全、费用或一致性契约，正常业务恢复路径即可触发，需优先修复。
- **P2 / 中**：在明确功能、规模、环境或并发条件下造成错误、不可用、错误核验或不应发生的额外操作。
- **P3 / 低**：影响较窄、已有主路径绕开或可控的运维/兼容问题，仍应记录，但可后排。

### 2.2 修复风险（与问题等级独立）

- **低**：局部、兼容、容易验证，不涉及持久化契约或关键时序变化。
- **中**：涉及配置、schema/index、既有数据、部署流程或多调用点一致性，需要迁移/兼容/失败回退验证。
- **高**：涉及未知结果和幂等语义、计费账本、并发生命周期与实际发送边界；简单局部修改容易导致重复执行、误封锁、错误结算或死锁。

## 4. 逐项详解

### R1 — 业务层通过新幂等键绕过未知结果隔离

**问题风险：P1；修复风险：高。**

**代码位置**
- `../../src/noyra/cognition/reflection.py:67–105`，核心是第 75、85 行。
- `../../src/noyra/cognition/cycle.py:835–896`，核心是第 847–851、864–871 行。
- `../../src/noyra/cognition/interaction.py:86–110`，核心是第 93–106 行。
- `../../src/noyra/model/resources.py:3248–3285`、`3419–3427`。

**根因**

路由器的未知结果隔离按传入的“逻辑幂等键”识别此前的 `unknown/executing` 调用；业务层却把调用记录数量、当日调用数或日期拼入下一次的幂等键。第一次调用未知后，账本多出一条记录，下一次推进同一未完成业务就换了逻辑键。路由器因此把它当作新请求，而不是仍未核对的旧请求。

睡眠反思使用 `sleep-reflection:{sleep_id}:{calls + 1}`；世界认知使用同一 observation 的 `call_count + 1`；交互认知使用同一交互轮次叠加日期和当日调用数。成功结果恢复路径不能覆盖 `unknown`，等待退避到期也只限制何时再次尝试，不保证后续尝试沿用同一逻辑身份。

**触发条件**
1. 同一业务轮次第一次请求的远端结果未知，例如已可能送达但本地超时。
2. 业务父对象仍允许继续推进；尚未达到该业务的模型调用次数/预算上限。
3. 正常退避期已过，再次调用该业务推进函数。
4. 未通过核对结算或显式一次性人工授权解除该未知结果。

**影响**
- 同一未完成业务可能再次推理、再次计费，甚至选择不同资源，削弱“未知结果先隔离再核对”的契约。
- 账本各自记录两次请求仍可正常工作，所以单独检验账本并不足以发现业务层绕过。
- **不是已证明双重付款或无限重试。** 本次验证的是重复物理模型请求；调用次数和预算上限仍存在。

**离线证据**
- 脚本：`../../.runtime/20261022-independent-audit/reproduce_core.py`。
- 结果：`../../.runtime/20261022-independent-audit/reproduction-results.json` 的 `unknown_reflection`。
- 使用真实睡眠反思业务类、资源路由和账本，FakeProvider 首次返回未知，第二次返回合法结构化结果。
- 首次抛 `ReflectionCognitionPending`；只模拟正常时间推进至退避期之后，不修改账本。
- 第二次得到合法 plan；`physical_requests = 2`，`operator_retry_grants = 0`。
- 同一 `sleep_reflection:{sleep_id}` 下第一条仍为 `unknown`，第二条使用另一个逻辑键，状态 `succeeded`。
- 动态复现覆盖睡眠反思；世界认知、交互认知确认同类调用点，但本次没有分别端到端复现。

**来源判断**

相关业务键和隔离实现可追溯至 `13a3cb7e` 等旧提交，早于最近修复。不是新终态等待取消逻辑创造的问题。

**建议修复方向与风险**

持久化稳定的业务轮次/逻辑请求身份，明确区分“业务新一轮”“已知失败的新尝试”“未知结果的核对或显式授权”。未知结果没有完成处置时，不允许仅靠计数、换日期、换资源生成新逻辑身份。不能简单按整个 `purpose` 永久封锁：正常的交互新轮次、内容变化以及管理员主动发起的新测试，语义并不相同。

修复会触及请求恢复和费用契约，需先明确历史数据兼容策略及授权消耗语义，避免把已知失败变成永远不能重试，也避免把未知预算误释放。

**必要回归**

world/reflection/interaction 三条链；同进程重入、重启后继续、跨日、资源轮换；已知失败可控重试、未知结果无授权不得重发；显式授权只消耗一次；成功结果恢复不再发送；业务终态收口不更改旧调用状态或释放未知费用预留。

### R2 — 记忆更新后仍用旧语义向量，常规重建无法发现

**问题风险：P2；修复风险：中。**

**代码位置**
- `../../src/noyra/mind/memory.py:139–225`。
- `../../src/noyra/mind/retrieval.py:80–164`，特别是第 114–118、141–161 行。
- 同文件的 `similarities` 校验向量内容完整性，但没有校验它对应当前记忆内容版本。

**根因**

正常 `MemoryStore.revise` 更新记忆正文、正文 hash 和修订身份，却不使已有 embedding 失效。`missing()` 只判断是否有向量、provider 是否相同，没有将内容 hash/revision 作为向量身份。重建时读取旧正文、外部生成向量、再写回，也没有以当前正文 hash 做 compare-and-swap。

因此即使向量自身 hash 正确，也可能是另一版记忆的合法但陈旧向量。存在性和完整性不等于语义新鲜度。

**触发条件**

同一记忆先建立向量，随后通过正常修订更改内容，继续使用同名 provider。另有读正文到写入向量之间发生修订的竞态窗口。

**影响**

修改、纠错、重新表述后的记忆持续按旧含义参与相似度和排序；常规 `rebuild_missing` 不会自动补救。检索结果可能长期偏离当前记忆。未证明这一问题造成了真实隐私泄漏或跨主体读取，不把这种可能性写成已发生事实。

**离线证据**

`reproduction-results.json` 的 `stale_embedding`：先为 `apples` 建立 1 条向量，正常 revise 为 `oranges`；此后 `missing_after_revision = []`、`rebuilt_after_revision = 0`，对旧内容相似度为 1，对新内容为 0。使用真实 MemoryStore/MemoryEmbeddingIndex，embedding provider 为确定性的离线实现。

**来源判断**

关键修订和索引逻辑在 `13a3cb7e` 已存在；不是最近一轮修复引入。

**建议修复方向与风险**

为向量绑定输入正文 hash 或修订身份；记忆修订时原子失效；生成完成写回时复核目标版本；查询时拒绝陈旧向量。处理存量数据和分批重建，不能贸然全量在线重算造成外部费用和资源压力。

**必要回归**

连续多次 revise；只改元信息和改正文的区别；索引生成期间 revise/撤回/删除；provider 切换及同名配置变更；旧向量存量迁移；多主体隔离；重建批次的有界成本。

### R3 — 保存前后的模型测试额度不一致，推理输出可能被误判失败

**问题风险：P2（条件性）；修复风险：中。**

**代码位置**
- `../../src/noyra/model/openai_compatible.py:195–233`，第 217–222 行。
- `../../src/noyra/model/resources.py:3466–3507`，第 3505 行。
- `../../src/noyra/service.py:8729–8818` 的新错误解释没有统一上述测试预算。

**根因**

草稿测试对 completion-token 型模型或设置了 reasoning effort 的模型给出 4,096 输出额度；保存后的测试固定只给 64。两者不是等价测试。对于输出额度包含推理消耗、必须先使用一部分额度才能返回可见 JSON 的模型，64 可能不足以输出结构化结果，而 4,096 可以。

**触发条件**

相同资源在草稿状态完成连接测试；保存后走正式资源测试；模型/网关所需推理和输出额度超过 64，或在该小额度下返回截断/空结果。

**影响**

有效配置可表现为“保存前成功、保存后失败”，管理员可能误改密钥、误停资源或反复测试增加费用。失败反馈改得更具体有价值，但不能消除测试行为不一致。

**离线证据**

`reproduction-results.json` 的 `probe_limits`：用 MockTransport 合法模拟在额度不足时返回空结果和 `finish_reason=length` 的推理服务；运行实际两条测试路径，捕获请求输出额度为 `[4096, 64]`；草稿 `ok=true`，保存后抛 `StructuredOutputError`；请求共 2 次。

**范围限定**

这是可触发的产品缺陷证据，**不是已证明用户当前真实供应商失败的根因**。未调用该供应商，也未据此验证任何特定模型的真实能力或当前价格。

**来源判断**

保存后 64 的实现早于最近修复；草稿 4,096 来自 `cbdfaa04`，同样早于 `c9e2d9c`。最近新增分类不是根因。

**建议修复方向与风险**

统一两种 probe 的测试契约、模型适配和有界预算，明确 reasoning token 的处理；保留单次有意付费尝试，不悄悄重试或切资源。不能简单无限放大输出额度，也不能把生命周期/预算/资源授权被阻断当作配置缺失。

**必要回归**

普通模型、completion-token 模型、不同 reasoning effort；保存前后参数等价；小预算截断的明确分类；单次点击只发一次；未知结果不得隐式重试；预算/生命周期拒绝不触发外部请求。

### R4 — 生命周期检查存在发送前时间窗口

**问题风险：P2；修复风险：高。**

**代码位置**
- `../../src/noyra/model/gateway.py:100–106`：入口查询生命周期。
- 同文件 `:204–246`：`before_send` 只复核 lease 和资源授权，没有复核生命周期。
- `../../src/noyra/model/openai_compatible.py:116–139`：实际发送边界具备回调，但回调未涵盖生命周期。
- `../../src/noyra/sleep/engine.py:98–105`、`273–299`、`721–730`：睡眠转换及 quiescent 检查；后者只检查 actions。

**根因**

请求入口允许时的 lifecycle 状态没有与实际派发原子绑定。请求在 await、连接准备或调度间隙暂停期间，另一路可推进到深睡眠；原 lease 仍可有效，资源仍已授权，因此发送前回调继续放行。

**触发条件**

例如管理员测试与主服务睡眠推进并发：测试通过入口检查后尚未发送，主体进入深睡眠，再继续发送。无需伪造密钥或破坏账本。

**影响**

不能将“处于深睡眠就不会再发出新的正式模型请求”视为已可靠落实到实际网络派发边界。可能在主体已休眠时产生新的请求/费用。这里说的是**尚未发送的首次请求**；已经发出的请求晚到、正常结算是另一回事，不应混为一谈。

### R5 — 新终态收口将全表扫描引入业务热写事务

### R9 — Windows 生命周期脚本仅凭 PID 文件判断并强杀进程
