## 三、确认发现

### R1 / P1：Windows 严格签名模式没有覆盖实际复制的启动器

**修复风险：中。置信度：高。来源：原生。**

**代码位置**

- `../../deploy/windows/noyra-lifecycle.ps1#L67`：`Verify-Package` 只遍历清单中的文件，对这些文件计算 hash，并按扩展名检查签名。
- `../../deploy/windows/noyra-lifecycle.ps1#L224`：安装时递归复制包目录内全部文件，并没有仅复制经过验证的清单集合。
- `../../deploy/windows/noyra-lifecycle.ps1#L165`：启动时按固定文件名选择启动器，不要求该文件曾列入清单。

**根因**：被校验的文件集合，与被复制/随后可能执行的文件集合不一致。清单既不是闭合的文件库存，也不强制包含启动器。

**触发条件**：用户执行 Windows 安装/升级，输入包包含未列入清单的启动器，且用户依赖 `-RequireSignature` 或清单的 `signature_required` 作为可信执行门禁。需要能够提供/篡改用户导入的包；**不是公网未认证请求直接执行代码，也不是证明攻击者已控制用户电脑**。

**影响**：未列入清单的启动器可在没有 hash/签名检查的情况下进入安装目录，破坏“严格签名模式只接受验证过的可执行文件”的承诺。之后正常启动路径会选择同名启动器。实际权限取决于用户启动 Noyra 时的权限，不能直接声称必然提权到管理员。

**隔离验证**：构造只有一个文本文件列入清单、另带未列入清单的 `noyra.exe` 的包；同时设置两种严格签名要求。执行真实安装器的 install 动作，退出码 0，未列入清单的启动器被复制。该启动器是“不可执行的合成文本”，**没有启动它**。

**建议根因修复**：校验真实包文件集合与清单严格相等（仅允许固定清单文件例外）；强制声明实际启动器；只复制已验证库存；对实际可执行文件落实签名策略；复制后重新校验闭合库存，同时拒绝重解析点和大小写碰撞。不要仅对当前两个启动器名追加一条签名检查而留下其他可执行输入。

**修复可能引入的次生问题**：历史包有未声明文件时会被拒绝，目录/大小写规范化不一致可能误拒合法包。应先检查构建器输出契约，不能以“兼容旧包”为由静默跳过验证。

**必需回归**：清单外启动器/其他文件拒绝；启动器缺席拒绝；列入清单但未签名拒绝；有效签名合法包通过；安装和升级都一致；在复制后篡改、重解析点、大小写冲突时失败关闭。

### R2 / P2：人工重试失败后，业务围栏缺少安全、可用的关闭入口

**修复风险：高。置信度：高。来源：原生缺口 + 本轮扩大影响。**

**代码位置**

- `../../src/noyra/model/resources.py#L3305`：业务 purpose 查询跨逻辑 key 包含历史已授权且未取消的 failed 调用。
- `../../src/noyra/model/resources.py#L3423`：这类 failed 调用继续返回 quarantine。
- `../../src/noyra/core/operator_controls.py#L350`：failed 已被视作终态，再次确认 failed 直接返回幂等成功；不追加关闭围栏所需的事件。
- `../../src/noyra/model/ledger.py:734-768,835-882`：重试授权只接受 unknown，取消授权只走 prepared 关闭路径。
- `../../src/noyra/model/request_identity.py#L39`：调用变为终态后产生下一代业务 key，但新围栏仍追溯旧 failed 调用。

**根因**：执行状态与恢复授权状态没有完整建模。管理接口认为“failed 已终结”，调度器却认为“此前的未知重试授权尚未关闭”；两个状态机对同一记录是否已处理完的定义不一致。

**触发链**：业务调用 unknown → 管理员明确授权一次 retry → 原物理调用重试得到已知失败、账本变 failed → 管理员再次确认 failed → 接口返回 `idempotent=true`，但未关闭授权/围栏 → 后续业务轮次及重建 gateway 后仍隔离。

**影响**：受影响业务目的可能持续不能推进；并非整个服务死锁。即使资源恢复、换 key、重启，也不消除该目的上的持久化围栏。其他业务主动终止时可能停止等待，但不能当作缺失人工恢复入口的修复。

**重要安全说明**：后一次重试“明确失败”，不证明最初 unknown 尝试从未执行或从未计费。继续隔离本身有安全理由；问题是管理员已经有额外证据时仍没有合规的关闭/重新授权路径。**不能简单删掉围栏或看见 failed 就自动换资源重试。**

**隔离验证**：使用真实资源存储、路由器、账本及 OperatorControlService，供应商为 FakeProvider。最后账本 failed；再次确认 failed 仅返回幂等成功；请求 retry/succeeded 都冲突；两次重建 gateway 都返回 `routed_model_call_quarantined`。总共只有两次 mock 调用，没有真实请求。审计事件仅留下 retry 授权而无关闭事件。

**归因说明**：HEAD 中“failed + 旧授权仍隔离”的分支以及管理端终态快速返回已经存在，不能把整段错误地说成此次新写。本轮将围栏扩展到整个业务目的，并修复变化 key 绕过未知结果的漏洞后，旧恢复缺口跨新 key 持续生效。将 HEAD 的查询方法和当前方法加载到内存，在同一份复现库、同一个新业务 key 上比较：HEAD 返回无围栏，当前返回 quarantine。因此属于**原生缺口被安全修复扩大/显化的集成问题**。

**建议根因修复**：增加对“failed 但有未关闭未知尝试/重试授权”的显式人工核对流程；要求覆盖历史未知尝试的结果/费用证据或明确的重复风险授权；追加独立、可关联的关闭或新授权事件，不改写既有审计。若允许重复授权，应有授权代次/消费绑定，不能把“历史上出现过一次授权”当作无限许可。

**修复可能引入的次生问题**：错误释放围栏可能重复付费；关闭事件与执行并发可能造成授权被重复消费；旧事件集合解释不正确可能误放行旧调用。必须在事务/执行锁边界内校验预期状态和授权代次。

**必需回归**：unknown→retry→成功/再次 unknown/已知失败/预算拒绝/发出前拒绝；人工核对覆盖历史未知尝试；相同核对幂等；双管理员并发；重启后围栏一致；没有新授权时绝不自动重复执行；三种业务 purpose 以及 legacy 路径都覆盖。

### R3 / P2：向量空间身份缺少 endpoint 和维度信息

**修复风险：中—高。置信度：高。来源：原生。**

**代码位置**

- `../../src/noyra/model/embedding.py:135-140,221-223`：资源 ID 与 provider 名称是不同概念；provider 名称只为 `openai-compatible:{model}`，环境资源 ID 也未包含 dimensions。
- `../../src/noyra/model/embedding_gateway.py#L89`：gateway 原样透传 provider.name。
- `../../src/noyra/mind/retrieval.py:145-158,202-245`：缺失检测及相似度查询依据该名称和正文 hash，未绑定真正的向量空间标识。

**根因**：计费资源身份、API 模型别名、向量空间兼容性被混为一谈。新加的正文 hash 绑定能证明正文版本一致，却不能证明查询和库存向量来自同一语义坐标系。

**触发条件**：已有向量后，更换为另一个同模型别名但实际坐标系不同的 endpoint；或同模型名修改输出维度，然后重启/重新构造 embedding 链。若不同 endpoint 实际提供完全相同的向量空间，则不一定出错。

**影响**：不同空间但相同维度时，旧向量被当作有效值参与比较，悄然影响记忆排序；维度变化时旧向量被相似度查询跳过，但 missing 又不把它列为需重建，语义检索可长期退化。本地词法等召回仍可能工作，不能说所有记忆丢失。

**隔离验证**：使用真实 OpenAIEmbeddingProvider + HTTP MockTransport；同名的 A/B 资源 ID 不同，provider.name 相同。A 为某正文存 `[1,0]`，B 对同一正文返回 `[0,1]`，切换后 missing 仍为空，同一正文相似度为 0。改为 3 维后 missing 仍为空，相似度结果为空。没有真实网络或计费。

**建议根因修复**：引入可持久化的 embedding-space fingerprint，至少覆盖协议/规范化 endpoint、模型、请求维度及必要的空间版本；索引写入、缺失检测和查询过滤统一使用。旧向量应渐进失效重建，不能直接把新指纹盖在旧向量上。不要把 API key 原文或秘密指纹放进空间身份，也不要仅靠包含 resource_id 的改名解决——环境 resource_id 本身仍不区分维度。

**修复可能引入的次生问题**：升级瞬间全量重建导致成本峰值、长事务或影响召回；若只因换 key 就改变空间身份，会不必要地重新计费。保留有界批次、预算、回退及正文 CAS，必要时使用新的 schema 迁移和兼容策略。

**必需回归**：同名不同 endpoint、维度变化、同空间仅轮换 key、旧库迁移、重建中正文修改/隐私删除、旧空间与新空间并存、错误维度响应，以及配额耗尽时本地召回仍可用。

### R4 / P2：独立 embedding 配置的 desired 状态与 effective 状态不一致

**修复风险：中；完整热切换为高。置信度：高。来源：原生。**

这里指**独立向量资源 API**，不是聊天模型资源启用状态，也不是认知主开关；不应把它和此前后台“认知未启用”的问题混为一谈。

**代码位置**

- `../../src/noyra/service.py#L10885`：仅在服务工厂构造 CognitionCycle 时读取 active_settings 并创建 gateway/index。
- `../../src/noyra/service.py:8696-8730,8846-8870`：配置/启停 API 只更新持久化存储并返回状态，没有更新已构造的认知对象，也没有返回“待重启应用”。
- `../../src/noyra/model/embedding_resources.py:208-238,240-273`：数据库选择当前资源与已构造 provider 的发出前鉴权是两个独立操作。

**根因**：后台资源“配置已启用”被用作成功结果，但没有运行时应用协议或明确的待应用状态。运行中的 cycle、gateway、index 和 MemoryStore 持有旧对象引用。

**触发条件**：已启用认知的进程启动后，经 embedding 资源 API 新增/替换/启用资源。新配置写入数据库并不触发服务重建。

**影响及复现**：

1. 启动时没有 embedding：配置后数据库 active 且 active_settings 能选到它，但 cycle.embedding_gateway 仍为 None；重启后才创建对应 gateway。
2. 启动时已有 A，随后配置 B：数据库选 B，运行时仍使用 A；A 仍 active 时旧 authorizer 允许继续使用 A。禁用 A 后旧 authorizer 拒绝发送，但不会切换到仍 active 的 B。

上述使用真实隔离服务对象/存储验证，没有运行认知循环或真实网络。**撤销/禁用的发出前授权检查是有效的，本报告没有发现或声称“撤销后仍能绕过鉴权发送”。**

**建议根因修复**：首先明确运行时应用契约。低风险止血是区分 desired/effective 版本和资源 ID，API/管理解释明确返回 `restart_required`/未应用状态，不能把数据库 active 展示为正在使用。若承诺无需重启，应由主服务在准入/排空边界统一热应用，原子更新 cycle、index、MemoryStore 相关引用并正确关闭旧 worker/provider；不能只替换一个字段。

**修复可能引入的次生问题**：旧请求未完成时切换空间可能混写向量；仅换部分引用导致同轮使用两种资源；关闭旧线程过早造成记账不完整；重建对象重复启动工作流。应分阶段实现，先解释清楚真实生效状态，再做受控热切换。

**必需回归**：无→有、A→B、启停及撤销、运行中请求、版本冲突、进程重启、配置失败、预算归属、运行时实际资源 ID 与接口显示一致。

### R5 / P2：围栏查询在返回零行时也可能扫描大量审计记录

**修复风险：中。置信度：高。来源：本轮新增/放大的查询成本。**

**代码位置**

- `../../src/noyra/core/database.py#L7086`：新增的 model_calls 索引不覆盖审计 action/call_id 关联。

**根因**：将业务级安全围栏扩展到历史失败调用时，新增了按每个候选调用执行的审计相关子查询，没有对应的可索引查询形态。`LIMIT 257` 仅限制返回行数，不限制为证明“不存在授权”所做的扫描工作。

**触发条件**：同业务 purpose 有已知失败调用，且该主体长期积累较多审计记录；即使从未人工授权重试、最终查询返回零行，也可触发。不需要先发生 R2。

**隔离验证**：真实 schema 100 合成库，固定 3 条 failed 调用，只增加与这些调用无关的审计记录；直接执行产品源码中的 SQL，并以 SQLite progress handler 近似计数到 100 步。还在相同库上执行 HEAD 方法作对照。

| 主体审计行数 | 当前查询约 VM 步数 | 当前本机耗时 | HEAD 方法约 VM 步数 |
|---:|---:|---:|---:|
| 1,000 | 25,000 | 20.413 ms | 9,900 |
| 10,000 | 160,000 | 52.177 ms | 9,900 |
| 50,000 | 760,000 | 180.991 ms | 9,900 |
| 200,000 | 3,010,000 | 761.468 ms | 9,900 |

查询计划显示相关子查询只按 `subject_id` 使用审计时间索引。这是本机一次测量，不是服务器延迟承诺；决定性证据是扫描工作量随无关审计记录增长、而 HEAD 对照保持固定量级。**没有据此认定它就是当前服务器后台卡顿的原因。**

**影响**：长期运行后，调度器为同一个阻断判断反复支付更高 SQLite 扫描/CPU 开销，延迟在事件循环上的同步路由工作。在低资源实例上应关注，但本轮没有实测生产资源占用。

**建议根因修复**：为授权状态使用可按主体、call_id、动作定位的查询/派生状态或合适的表达式索引；维护证据的 append-only 语义，确保缺失/损坏授权仍失败关闭。也可重构为先取本 purpose 的候选调用，再做有界且可索引的授权关联。新增索引时采用清晰的 schema 迁移契约，不随意改写已发布迁移及指纹。

**修复可能引入的次生问题**：只为加速而截断授权历史可能误放行未知调用；索引表达式若不处理非 JSON 历史记录可能迁移失败；额外索引会提高写入/磁盘成本。不能用放宽隔离或删除历史账本换取性能。

**必需回归**：无关审计量从千到数十万时的 VM 步数/查询计划；授权、取消、重复授权、未知、畸形 JSON、旧库升级、并发写入；结果与原安全语义严格等价。

## 四、确认可以保留的修复与不应误报的事项

1. **20 秒连接、100 秒单次 provider 操作总时限**：默认设置符合约定；provider 外层绝对截止时间不是只修改 httpx 的读空闲超时。连接、响应头、分块读取在同一单次调用预算内。整个业务若对“明确已知失败”作多次重试，业务累计时间仍可能超过 100 秒，不能混淆这两种口径。
2. **unknown 跨 key 围栏**：换 key、跨天、重启不能证明之前的供应商调用没有执行。应保留该边界，R2 应补人工恢复，而不是恢复旧的 key 变化绕过路径。
3. **生命周期发出前检查**：已暂停/失效的准入不继续发请求；已发出的请求可以完成结算，不应把真实完成的记账抹掉。针对性测试通过。
4. **正文—向量绑定和 CAS**：修正文更改/撤回与远程 embedding 返回之间的竞态，是正确方向；R3 是空间身份遗漏，不构成回滚正文绑定的理由。
5. **schema 100 与导出所有权**：本轮迁移/严格契约/历史库和导出回归通过；新增绑定表通过 memory_embeddings 归属主体，不应为回退代码而直接将真实数据库降版。
6. **Ubuntu 发布输入与 venv 路径**：不可变提交快照、忽略文件不混入发布、拒绝 dirty/submodule/symlink、最终路径构建及入口点验证值得保留。测试并不证明一台真实系统已走完整安装/断电/回滚。
7. **token 轮换及 Windows PID 身份验证**：合成 systemctl 和合成进程验证的恢复/停止边界通过。没有把“PID-only 旧文件必须失败关闭”直接当成误杀漏洞；实际旧部署迁移指引仍应有运维验证。
8. **HTTP 公网地址钉住、有限响应读取、钱包已知/未知区分、备份解包拒绝链接/库存核验**：在本轮精读范围及选定测试中未确认新的可利用问题。此结论不覆盖所有连接器、签名服务、链上情形或迁移平台。
