# M42 P1-13 Capability Approval Boundary Remediation

Baseline: `main` / `87e059a` plus the M41 verification foundation and verified P1-01/P1-08
contracts.

## Contract decision

Noyra's product contract says that it decides whether to use an operator-owned capability; an
operator may revoke that capability, but there is no human approval required for every use. The
old `requires_approval` flag therefore cannot remain as an apparent security control. A real
per-use approval ledger would require a new durable schema and belongs after the P2-10 migration
safety gate.

## Change

New capability grants with `requires_approval=true` are rejected. Existing rows carrying the legacy
flag fail closed in authorization, regardless of the supplied `approval_id`; they must be revoked
and re-granted. Ordinary capability use remains within the existing immediate SQLite transaction,
rate limit, append-only use ledger, action binding, grant expiry, and operator revocation boundary.

The capability configuration UI no longer presents a per-use approval toggle or sends the legacy
field. Cognition and project formation no longer expose the unsupported flag to autonomous context.
The legacy database column and state-hash inputs remain intact for compatibility and inspection; no
schema migration is introduced while P2-10 migration safety is open. The `approval_id` call
parameters remain deprecated compatibility inputs; they never authorize an ordinary grant and
cannot bypass a legacy blocked grant.

## Evidence

- focused M41/M42 regression runner: 29 passed, including new flag rejection, arbitrary-token
  denial for a legacy row, ordinary grant use, expiry, revocation, and append-only use accounting;
- full pytest: 312 passed;
- deployment audit: 40 passed, 72.02% focused coverage;
- Ruff, format check, Mypy, compileall, pip check, and production-lock pip-audit passed;
- UI/API snapshot confirms no per-use approval control is advertised;
- read-only review confirms no new approval table or migration was introduced.

P1-13 is verified under the explicit no-false-approval product contract. A future real approval
workflow requires a separate design with actor, subject, grant, operation, exact scope/resource,
cost, request hash, expiry, nonce, atomic single-use consumption, and migration evidence.
