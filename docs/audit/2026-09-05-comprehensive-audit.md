## 2. 评级方法

| 等级 | 含义 | 处理要求 |
| --- | --- | --- |
| P0 | 已证明可直接导致灾难性未授权执行、重大泄露或不可逆破坏 | 立即隔离 |
| P1 | 破坏支付授权、主体隔离、完整性或关键资金执行合同 | 立即进入修复队列；对应危险能力开放前必须关闭 |
| P2 | 显著可靠性、性能、运维或有限入口的安全风险，有可控绕行 | 可缓修，但必须遵守每项列出的启用/规模边界 |
| P3 | 文档或维护性偏差，不直接造成已证明的运行事故 | 可排期修复 |

修复风险独立评级：低 = 局部、无状态迁移；中 = 多入口/查询/队列合同变化；高 = 金额、并发、不可逆外部副作用、数据库迁移或跨平台文件所有权变化。高风险问题不能靠直接改生产库、重算所有历史 hash 或笼统 catch 异常“修复”。

发生概率是**触发条件下的定性判断**，不是线上事故率。本次没有真实运行遥测，不能给出可信百分比。“条件满足必现”表示可重复复现；“低”通常表示需要本地目录控制、离线改库或很窄的竞态，不表示后果轻。

来源分类：

- 原生：在对应功能首次进入可追溯历史时已经存在，不能归咎于最近修复。
- 次生集成回归：后来新增入口没有遵守既有全局边界；条目同时说明新增模块本身从第一版就遗漏，不伪称此前已有正确钱包实现。
- 原生残留：旧缺陷经修复缩小范围，但尚有兼容路径未覆盖。
- 未能归因：历史不足以确定，不强行二选一。

## 5. P1 详细记录

### AUD-01 策略禁用未覆盖已有订单

- 证据：`src/noyra/wallet/economy.py:596`、`:985`；`src/noyra/wallet/execution.py:1201`。`confirm_order -> _reserve_order -> _policy_allows` 不检查 mode；执行现有 reserved 订单只查 emergency_paused，没有重新确认 disabled、allowlist/限额收紧或旧策略版本授权的处理规则。
- 复现：`test_a01` 中先 reserved，再把 mode 改成 disabled，仍 broadcast；`test_a15` 中待人工确认订单在 disabled 后仍成功 reserved。全部使用有权限 operator，不是匿名转账漏洞。
- 影响：操作者以为禁用生效，旧队列却仍能产生新预留/签名；收紧权限后的撤销语义不一致。若旧授权需保留，应明确设计“承诺支付”与“禁止新增外部副作用”，目前没有这份契约。
- 触发/概率：存在非终态订单并变更策略后调用确认/执行，复现路径必现；默认无 signer 时不会实付。
- 来源：确认路径原生于 `113a888`，执行路径原生于 `809e686`；不是 schema60 hash 修复造成。
- 决策：立即。临时必须停止相关执行入口/不注入 signer，不能仅把 mode 切到 disabled 就宣称全停。
- 修复风险高：集中定义各状态的策略撤销/版本规则，避免重复预算计入、重复预留或误拒已广播交易的只读对账。回归覆盖三种模式、已有订单、允许列表撤销、策略 CAS、并发确认。

### AUD-02 紧急暂停不能阻止 unknown 重发

- 证据：`execution.py:654`、`:1105`，retry 分支在普通执行的暂停检查之前返回。未重新验证当前暂停、资源撤销或支付许可。
- 复现：`test_a02` 模拟第一次响应丢失得到 unknown，设置 `emergency_paused=True`，显式 retry 后仍 broadcast，签名器收到第二次请求。
- 影响：应最高优先级生效的停付开关被故障重试路径绕过；未知交易本身不应因暂停被随便退款或重新分配 nonce。
- 触发/概率：unknown + 操作者调用 retry；该组合必现。暂停时查询既有交易回执本身是允许且必要的，不应一并禁掉。
- 来源：`809e686` 原生分支遗漏。
- 决策：立即；禁用重发能力，保留只读查链与人工事故处理。
- 修复风险高：把查证已发生交易和发起新签名拆开授权，确保 emergency pause 阻止后者；覆盖响应丢失、链已成功/失败、撤销地址、并发暂停与重复重试。

### AUD-03 生命周期栅栏没有围住外部签名

- 证据：`execution.py:591` 的 `_prepare()` 返回后直接 `sign_and_broadcast()`；`core/admission.py:151` 有提交序列化机制，但此调用未利用当前 lease 的外部副作用边界。
- 复现：`test_a10` 在 prepare 提交完成后、进入签名器前失效当前 gate。签名器仍收到请求，后续数据库提交才抛 `OperationInvalidated`，记录保持 signing。
- 影响：暂停/隔离发生后仍可能花钱；本地记录与已发出的链上动作暂时分离。重启恢复能保留 unknown 线索，但不能撤销已经广播的交易。
- 触发/概率：HTTP 执行请求持有 lease，同时另一个控制请求 pause/quarantine，命中准备与签名间窗口。自然概率取决于并发；注入窗口可稳定复现。
- 来源：`809e686` 新支付入口没有接入 `94916dec` 先前建立的 Gate 0，属于次生集成回归，同时是钱包第一版的遗漏；不是近期完整性修复破坏了已有正确支付路径。
- 决策：立即，实钱接入前必修。
- 修复风险高：需要定义可取消阶段、外发线性化点和过期后仅允许终态记账的范围；仅在调用前多加一次布尔判断仍有竞态，也不应持全局锁等待整个慢网络。测试暂停/关机/隔离在准备前后、外发前后、回包前后及终态恢复。

### AUD-04 可观察的钱不等于可支配的钱

- 证据：`economy.py:1025`、`:1042`，最近余额只按主体/network/asset 查询，未绑定支付 source address。真正 spending 地址直到 `execution.py:1214` 才挑选。
- 复现：`test_a04` 注册 spending 余额 0、observation 地址余额 100，min_balance=1，10 单位订单仍 reserved。
- 影响：以观察地址甚至非自己控制地址的余额批准支出。签名器/链最终可能拒绝，但不能补救本地错误预算、错误承诺或其他尚有少量资金时低于保底余额的支出。
- 触发/概率：同资产有多个地址，最近快照来自非实际资金来源；该数据形态下高/确定。
- 来源：`113a888` 原生政策查询缺陷。
- 决策：立即；临时单一地址配置只能缩小触发面，不能作为最终修复。
- 修复风险高：在预留时确定 source 身份与版本，并让余额、新鲜度、在途资金、nonce 和签名器校验使用同一来源；禁止地址切换后继续沿用旧预留。测试多地址/同时间多源、撤销和来源切换。

### AUD-05 预留没有减少下一笔的可用余额

- 证据：`economy.py:1034` 至 `_reserve_order` 只比较 snapshot.balance 与本笔 amount+min_balance；没有扣除其他 reserved/signing/broadcast/unknown 占用，也没有 gas 预算。
- 复现：`test_a05` 快照 11、保底 1，已有 reserved 10 后再接受 10，累计预留 20。
- 影响：超额承诺、低于保底余额、资金不足失败及后续 nonce 阻塞。ERC-20 手续费还消耗另一项原生资产；只验证 token 余额不足以准入。
- 触发/概率：余额近阈值并出现多笔在途订单或手续费显著，概率高；不会令链凭空创造资金，但会破坏业务资金保证。
- 来源：`113a888` 原生，非账本改成游标后才出现。
- 决策：立即。临时可关闭自动支付，不用“提高 min_balance”冒充准确预留。
- 修复风险高：事务内计算可支配额并正确去除已经反映在快照里的历史支出，避免双扣；单独预留费用，明确释放/unknown/手续费实际消耗。回归并发预留、快照更新、失败/退款及多资产 fee。
