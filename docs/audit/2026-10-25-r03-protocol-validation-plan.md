# R03 恢复协议原型验证计划

日期：2026-10-25（北京时间）。产品基线 b069cd3ea7793390b4a18a8791c7de70a48e6647。分支 codex/audit-r03-protocol-validation。

本轮仅实施 tests 内隔离原型和文档，不修改 deploy/windows、src、scripts、产品格式或 CI，不连接服务器、不部署、不推送合并。R03 在产品中仍未修复。

验证顺序：
1. 用原生 Windows 签名包和允许读/禁止替换的句柄重新复现当前 A→B 撤销 A 的失败状态。
2. 选择单一权威状态文件；PREPARED 内保存完整意图和新 trust，作为接受撤销的持久时点。此前失败保持原状态；此后 pending 阻断 start/rollback，恢复只前滚，不回退已撤销 signer。
3. 包仍使用现有 Verify-Package 的真实 CMS/Authenticode/文件清单验证；原型不把包内 metadata 当授权。原型不运行任何 launcher，不导入证书库，测试证书仅内存持有。
4. 用真实原子文件替换、共享句柄/跨进程互斥和进程中断注入验证 prepared/receipt/commit/兼容镜像/cleanup 每一边界；同意图幂等、冲突拒绝、状态损坏/路径异常拒绝、撤销后 rollback 禁止复活旧签名。
5. 验证旧入口绕过风险。旧 current/previous/trust 只能是兼容投影；旧脚本若不识别新协议，必须在正式上线时纳入统一入口门槛。原型不能声称能限制直接运行旧二进制或本地管理员任意覆写。
6. 文档区分“接受命令/完成激活/镜像清理”；新协议标记建立后缺少/损坏权威状态必须拒绝，不从兼容镜像猜测恢复。明确程序崩溃验证不是断电持久性证明。

默认建议的撤销语义：新策略在 durable PREPARED 成功后立即生效（不是 CLI 一开始，也不是等升级成功）；原运行进程不自动终止，禁止新的受支持 start/rollback。若 marker/intent 尚未可靠写入，不能向操作者宣称撤销已经生效。

完成标准：记录全部实际矩阵结果和产品集成缺口，评估是否满足正式实施条件；不把 tests 原型作为可部署修复。不启动 GitHub 等待或重复长测；静态、已有 Windows 回归和所需原型验证通过后提交并汇报。
