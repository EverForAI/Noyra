# P2-02 / P2-03 修复记录（2026-10-19）

## P2-02：失败 GC manifest 证据保留

`_cleanup_orphan_gc_manifests()` 现在先验证数据库 run 状态哈希，再按状态处置 sidecar：`planned` 与 `failed` manifest 保留，`applied` 和确实没有数据库记录的孤儿 manifest 才清理。数据库 run row 的 `run_id` 可确定 sidecar 路径，`cursor_json` 保存字节数、action 数量和 SHA-256，失败记录继续保存 failure code；因此不需要增加数据库 schema 或改写历史记录。

GC 已经持久化为 `applied` 后，删除 manifest 或同步目录失败只在结果中报告 `manifest_cleanup_warning`，不会再把已完成的删除任务改记为 `failed`。后续 maintenance 可继续清理遗留的 applied sidecar。

失败 manifest 目前没有自动过期或应用内 purge 操作，会一直保留以供审计；这避免了再次静默丢失证据，但失败计划较大或频繁失败时会占用额外磁盘空间。运维需监控数据卷空间，并在完成证据归档后按 run id 执行受控的人工清理。

## P2-03：环境资源与 durable 状态冲突

环境同步遇到同名 `disabled` 或 `revoked` durable resource 时，会写出包含 pool、label 和状态的错误日志并跳过该 proposal。同步不会自动启用资源、重建 revoked 资源、替换密钥或改变 durable 状态；服务仍可启动，其他 active resource 继续可用。`active` 资源仍走原有逐字段和 key fingerprint 一致性检查，配置不一致仍以 `environment_model_resource_conflict` 阻止该次启动同步。

操作员可通过管理界面显式启用 disabled resource 后再重启。revoked 是终态，需用新 label 配置替代资源；环境同步不会绕过该撤销记录。
