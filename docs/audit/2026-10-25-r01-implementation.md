## 根因修复与实际合同

### 持久身份见证（schema 107）

新增 relationship_identity_bindings，以独立不可变记录绑定 relationship_id、subject_id、entity_type、entity_key、关系创建时间、来源类别、来源事件引用、记录时间和摘要。关系权重及旧 revision 的 state_hash 算法保持原样，不重算历史。

- 新关系与首个 revision、created 身份见证在同一事务提交；见证失败整组回滚。created 只表示本软件创建时记录的绑定，不是对现实身份、消息亲自撰写或意识状态的额外认证。
- 旧关系在升级事务中记录 legacy_observed，保留原键、昵称、全部权重、边界、revision 与时间字段；明确不证明创建之前的归属。不通过泛化/多源事件猜测另一个实体，也不把昵称相同的主体合并。
- 对缺失/跨主体的形成引用、无效后续社交快照或明确身份冲突，保存固定 reason code 并逐关系标记 review_required；不自动改键、不建立替代关系继承信任。
- 后续社交快照矛盾仅在“迁移记录的精确 social_id + state_hash”范围内作为已知历史兼容，不能把这一例外扩展到新记录或重算后的不同历史。其他模型/消息/签名完整性检查继续执行；无效旧证据并不因迁移获得豁免。
- UPDATE、主键/归属/类型/实体键/形成时间改写，以及 SQLite INSERT OR REPLACE 的替换路径均受保护。读取同时核验独立见证，不能只依赖触发器。

### 迁移和版本边界

MIGRATIONS[107] 创建表/索引/触发器，backfill_legacy_bindings 与版本标记在 BEGIN IMMEDIATE 事务中执行；使用已有迁移前备份机制。迁移失败恢复的是完整逻辑 SQLite 状态，不承诺文件页/日志模式头逐字节相同。单元测试比较旧 schema 和全部表内容，而归档 fixture 本身另有逐字节 SHA-256。

同版本启动绝不补造缺失绑定、重新散列见证或把 legacy_observed 升为 created。迁移记录异常则明确失败/隔离，不能默默重新背书。schema 107 更新完整 DDL 与结构指纹；旧 runtime 拒绝打开新库，不删除新表绕过降级门槛。

### 读取、推理及发送边界

- RelationshipStore 的 ensure/get/find/list/revisions/revise 与 MindEngine/mind.state 使用相同身份核验。所属主体被改出原查询范围时，独立按 witness 所属主体检查，避免“查不到就算安全”。
- social 候选与提交/重放前重新核验，冲突关系不自动外联。发送仍遵守原路由、同主体、私有消息、联系限制、冷却和高冲突保护，没有扩大分享权限。
- thought、motivation、self-model、metacognition 的直接 SQL 上下文接入共享守卫；不可信绑定不因绕过 Store 而进入模型。正常旧关系带 legacy_observed 说明，权重不被清空或调高。
- 新因果引用校验关系见证；旧历史不重写。隔离关系的旧邀请不垄断队列，其他正常邀请仍可被调度。仅捕获专门的 RelationshipIdentityReviewRequired，不吞掉其他修订冲突。
- 管理后台的私有状态接口增加绑定总数、升级观察数、待复核数和中文说明；匿名 PublicSubjectStateV1 不增加身份/关系细节。本项没有重做后台页面布局，逐关系 record 也保留 origin/status/reason code 供受控读取。

### 导出、保留与恢复

- schema 107 的诊断导出 ownership graph 明确将新表归为 subject-owned，并沿既有外键/归属校验防止跨主体混出。
- retention 将身份见证登记为 core_evidence / preserve，绝不视为可重建缓存或按时间清理。
- 旧隐私 intent 的派生数据复核包含新表；不恢复归档/撤回的正文，不改变现有删除功能禁用合同。
- SQLite 备份恢复验证后见证仍存在、可验证，原权重和历史保留。真实加密卷、跨机迁移和长期运行验收仍是后续门禁，不能用本地 SQLite 副本替代。

## 验证设计与已执行预验收

新增由真实 schema 106 基线生成、带 SHA-256 manifest 的合成归档：包含原关系权重/修订、真实 InteractionStore 与 RelationshipSocialCognition 流程的 FakeProvider 社交记录。没有生产数据、真实密钥或真实模型网络调用。

预验收 25 项通过，覆盖创建原子性、普通旧库升级/幂等、强冲突隔离、绕过 UPDATE 触发器后的读取发现、见证缺失/篡改/畸形值、INSERT OR REPLACE 防绕过、真实迁移进程中断与重试、版本标记前失败恢复、旧运行时拒绝、正常修订、直接读取者、邀请队列隔离、后台私有说明、跨主体导出、保留与备份恢复。

之前的历史研究反例没有删除或屏蔽：在新版本下先验证正常写入被拒，再显式移除新防护注入 corruption；旧关系/revision 字段仍可能相同，但新见证能够区分/拒绝。保留“既存历史不能被凭空证明”的研究结论，不再要求新版本重现已修复的无防护行为。

## 风险评估与停止边界

原问题 P2；修复风险仍为中至高，主要在升级事务、schema 门槛与共享读取者。修复后的残余边界：

1. 对没有原始身份见证且此前已静默错绑的旧记录，迁移只能固定升级时观察值，不能恢复不存在的信息；不把其声称为已认证历史。
2. 拥有任意本地写权限者同时移除防护、重写见证及所有历史，不在本地散列/SQLite 触发器能防御的能力范围内。普通公开账户没有获得新写库或维护权限。
3. 新库不能交给旧二进制继续运行。部署前必须保留受控完整备份，并只读预检实际实例的绑定/冲突数量；本轮没有连接服务器或统计其私人关系。
4. 对原有模型/消息证据已经损坏的记录，既有完整性检查仍可报错；不为了让迁移“全绿”放松这些检查。
5. R03 的 Windows 多记录恢复协议本轮未修改；既有 Windows 长路径条件也未在本轮修复。
