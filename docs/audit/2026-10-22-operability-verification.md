# 2026-10-22 安装器、低成本观测与后台解释能力：实施验证记录

## 结论与范围

本轮实现用户指定的第 1、4、6 项优化：安装升级的永久修复、可观测性与资源开销控制、后台状态解释。
只修改开发工作区；没有连接生产实例、修改 SSH、部署、提交、推送或合并代码。
不增加数据库 schema 迁移，不改变认知预算、并发、休眠、付款授权、主体目标或安全准入规则。
没有新增运行时第三方依赖，也没有新增后台采样线程。

本文是本轮变更的验证记录，**不是全项目独立审计，不是八项外部门禁验收报告**。

## 根因、影响和变更风险

这里的 P1/P2 是所处理问题的技术风险优先级；“修复风险”是本轮改动引入回归的风险，两者不混用。

| 范围 | 既有问题及触发条件 | 影响/问题等级 | 本轮处理 | 修复风险及边界 |
| --- | --- | --- | --- | --- |
| 安装辅助解释器 | 系统 Python 没有项目依赖，或上个 release 的依赖与新代码不一致时运行新 helper | 升级中断、误判预检/清理结果；P1（可用性） | 构建前仅做 stdlib 空间检查；完整预检用新 staging 的 `python -I`；发布后的保留标记/GC 用新 release 自带 helper 和解释器 | 中：涉及 root 部署流程；保留锁定依赖、备份与原有保留边界 |
| 程序权限 | root 采用 `umask 0077`，构建出的公开程序只有 root 能读取 | root 导入成功但真实服务账户启动失败；P1（可用性） | 只在公开程序构建子 shell 中用 0022；停止旧服务前以服务账户导入，发布后再检查一次 | 低至中：不递归放宽 release，不改变数据、备份或私钥权限 |

| 迁移后失败恢复 | 数据已迁移，但发布组件失败、指针尚未切换，或回滚代码与现有 schema 不兼容 | 不兼容旧代码被重启、兼容新 runtime 被过早删除；P1 | 回滚先查兼容性；迁移后失败也检查旧代码契约。不兼容时保留新 runtime、阻止旧代码重启并报告需要数据恢复 | 中：宁可保持停止交由恢复，不自动覆盖持久数据；需要真实 Ubuntu 升级/恢复门禁 |
| 总览诊断成本 | 每次首屏读取完整诊断，将详细完整性/存储检查和普通状态展示耦合 | 放大 IO、锁竞争和页面等待；P2 | 增加 operator 专用轻量摘要；只读 SQLite、100ms 锁等待、250ms SQL 工作预算、2 秒缓存；不调用完整诊断或供应商 | 低：展示侧独立通路，不能参与安全准入；预算不是操作系统 IO 的硬实时承诺 |
| 用量与资源口径 | 将缺失数据理解成零，或把部分模型费用当成账单、把长期未知付款藏在近期样本之外 | 误判费用/故障，可能盲目重复外部操作；P2 | 100 次调用/500 次尝试的样本上限与截断标记；精确微美元字符串；缺失/估算分开；未知付款等提醒按全历史独立读取并限定输出条数 | 低：不改账本、不新增费用，不承担预算或结算职责 |
| 认知启用状态 | HTTP 层原本没有 cognition 字段，但既有诊断用该字段判定启用；实际服务的认知循环已创建时仍显示未启用 | 虚假的阻断提示和错误排障；P2 | 实际服务向 HTTP 观测提供只读循环存在性 getter；独立 HTTP 服务默认未启用，不把仅有 gateway 配置当成循环已创建 | 低：只改变展示证据来源，不启停认知或探测供应商；覆盖真实 from_env 创建及 HTTP 返回测试 |
| 后台解释 | 把“已配置”“近期循环成功”“HTTP 可达”“消息已回复/付款可用”混为一谈 | 误操作或错误恢复；P2 | 区分暂停、休息、停止、冷却、恢复、近期未成功、证据不足；给出依据、范围及下一步入口；配置向导明确“配置齐备，未实测” | 低：不改变状态机和自动操作；详细诊断入口保留 |

安装器保留既有数据卷身份/挂载检查，不自动解锁、格式化或绕过存储保护。
新预检位置仍保留原有额外 2 GB release 预留，属于保守容量限制；低空间机器可能比以前更早被拒绝。
报告只在受管安装生命周期建立后写入。初始参数/依赖/挂载检查提前退出、SIGKILL 或断电没有最终报告；
**没有报告不能解释为安装成功**。写报告失败会明确告警并使原本的成功退出变为非零，不自动回滚已迁移数据。

## 实现与验证边界

- API：`GET /api/v1/admin/runtime-summary` 及兼容别名，需要 operator；普通 read token 被拒绝。
- 摘要只读本地记录，不输出提示词、对话、模型响应、账户、交易原文或凭据。
- SQLite 查询限时和限行，文件只做 stat；不递归遍历数据目录、不做完整性全扫、不访问外部模型/RPC。
- P50/P95 是逻辑调用从创建到完成的样本耗时，包含排队与重试；不是供应商纯网络延迟。
- 历史未知行动/模型调用/付款及未收口投递，不依赖近期调用样本；每类显示最多 50 项及更多标记。
- 总览保持四个首屏请求。完整配置诊断只在主动展开配置检查或进入详细防护时获取。
- 缓存时间、采集时间和未知值明确显示；局部接口失败不伪装成健康/零用量。
- 页面输出转义、退出清空和迟到响应的会话保护继续保留。
- CI 的既有 Ubuntu 3.12 root 测试步骤加入本轮安装器测试；远端 CI 尚未运行。

## 过程中的测试环境问题与纠正

1. 最初 Linux 源码快照放在 `/root` 下，真实 nobody 子进程无法读取源码，导致旧有非特权备份测试失败。
   没有放宽 `/root`、数据或密钥权限。改用 `/opt` 下只含源码的可遍历目录后，该测试独立通过；
   后续全量尝试的同一测试也通过。
2. 从既有开发 venv 复制依赖后，残留 editable 安装仍指向旧源码 `/root/noyra-ci-3a9b995`。
   pytest 主进程使用当前源码，而真实启动子进程导入旧运行时，形成“数据库 schema 99、运行时 79”冲突，
   产生四个迁移激活回归失败。没有修改 schema、激活代码或放宽断言来消除失败。
   在独立测试 venv 中用 `PIP_NO_INDEX=1`、`--no-deps --no-build-isolation -e` 安装当前快照，
   并用隔离解释器核对导入位置和 schema 99 后，四个失败用例全部复验通过；最终 14 模块回归也通过。
3. Windows 导出的源码快照统一按 Git 的 100644/100755 模式重建为 Linux 的 0644/0755，
   避免把 Windows 文件模式当成 Linux 发布权限。只处理独立测试源码，没有递归修改生产目录。

初次失败记录与纠正后的最终结果分别保存；不能把上述中间失败隐藏，也不能把中断的全量测试算成全通过。

## 仍未完成的验收

- 没有执行完整的 2,000 多项 Python 全仓回归至结束；本轮全量尝试在完成 314 项后主动中断，
  当时没有失败（6 项跳过、14 个 subtest 通过），不是全仓通过证明。
- 没有在真实 Ubuntu/systemd 机器上从旧版本完成整套安装、启动、LUKS 重启解锁、异机恢复或长期 soak。
- 没有产生真实模型费用、付款、打赏或迁移外部资源；八项外部门禁未被补齐或标记通过。
- 没有生产规模吞吐/RSS 峰值对比，不对实际节费百分比或生产延迟作保证。
- 轻量摘要可因 SQL 预算、锁或 IO 故障不可读；必须继续显示未知，必要时使用详细诊断，不能自动清库或解除准入。
