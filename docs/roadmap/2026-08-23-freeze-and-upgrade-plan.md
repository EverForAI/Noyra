- Python 3.12、虚拟环境、Git、curl、cryptsetup 和依赖检查通过。
- 2 GiB Swap 已启用，根分区和 `/var/lib` 空间充足。
- 10 GiB LUKS2/AES-XTS 加密镜像建立成功，挂载到 `/var/lib/noyra`。
- 服务以 `noyra` 非 root 用户运行，systemd 条件挂载保护生效。
- `health/live` 和 `health/ready` 正常返回 200。
- 服务重启、SIGKILL 后自动恢复、加密卷锁定后服务拒绝启动、重新解锁后恢复均已验证。
- release 升级、升级前加密冷备份、readiness 失败回滚和显式 rollback 已验证。
- 回滚后 `current`/`previous` 指针正确，备份保留且权限为 root-only。
- 2 小时 soak 通过；30 秒超时 readiness 探针 87 次采样完成，未出现持续故障。
- 公开面板通过 SSH 隧道访问，服务仍监听 `127.0.0.1:8765`。

### 部署操作中的明确结论

- LUKS 密码用于解锁 Noyra 数据卷，不是模型 API Key，也不是网页登录密码。
- 读取令牌和操作令牌属于旧的 HTTP 鉴权方式，不能作为长期交互体验；后续应改为登录会话，但不能取消管理端鉴权。
- 解压包中的两个存储脚本权限曾为不可执行；脚本用 `bash` 调用时不阻塞部署，但正式打包必须修复为 `0755`。
- 当前候选包较小是因为模型、Python 运行时和依赖不随源码包分发，依赖在目标机安装。

## 3. 已发现但尚未完成的问题

这些问题先记录，不在冻结基线中临时修补。

### P0：认知交互没有形成闭环

数据库中曾出现 `incoming human_message offered`，但没有 `decided_at`、没有 `outgoing` 回复。需要先确认认知循环、调度器、模型调用和预算日志的断点，再增加功能。不能把“网页发送成功”当作“主体已经决定回复”。

### P0：模型配置兼容性和错误提示

- 已配置数据库模型资源时，非空的旧式 `NOYRA_MODEL_BASE_URL` 仍可能触发 legacy 配置路径，并因缺少 `api_key` 启动失败。
- 模型资源表单缺少连通性测试、预算字段、清晰的重复名称错误和 provider 级状态说明。
- 同一认知池内相同名称会被拒绝；后端可列出不同名称的第二个资源，但前端刷新和错误提示需要专项验收。
- “删除”应定义为可审计撤销，而不是物理删除。

### P1：交互和控制面体验

- 每条消息或状态操作重复输入令牌，严重影响单人 SSH 隧道场景。
- 刷新时曾出现非 ISO-8859-1 字符进入 HTTP header 的前端错误。
- 发送成功、处理中、已决定沉默、已回复、系统失败需要在界面上明确区分。
- 创建者消息要相对优先，但不能绕过安全、预算和其他主体的拒绝权。

### P1：通讯适配不完整

Telegram、QQ、飞书、微信、邮箱和 Webhook 不能只共用一个通用表单。必须分别实现入站验证、出站格式、会话映射、去重、重试、平台限流和投递状态恢复。当前骨架不能视为已经完成原生双向聊天。

### P1：能力授权模型需要重做

公开 HTTPS 网页读取可作为默认能力，但仍必须保留 SSRF、防内网访问、大小、时间、重定向和来源审计边界。文件写入、发布、通讯、钱包和支付仍应显式授权；“默认可读”不等于“默认可写”或“默认可付款”。

### P1：钱包能力尚未实现

当前 `wallet` 主要是能力枚举，不是完整的钱包、签名和付款执行器。不能把它当成已经支持真实代币交易。

## 4. 已确定的产品方向

### 公开网站

服务器部署后提供公开网站，展示经过字段白名单过滤的身份、公开状态、公开日记、目标摘要、项目进展、求助帖子和服务成果。不得公开私人心理、原始模型输入输出、令牌、密钥、内部路径或详细诊断。

### 独立管理页面

使用独立的管理入口（例如 `/admin`），但路径本身不是安全边界。必须使用独立账号和会话、HttpOnly Cookie、CSRF 防护、登录限速、审计日志，并预留 MFA。管理页负责私聊、审核、模型、通讯、能力、预算、钱包和订单管理。

### 非命令式聊天

各通讯渠道和网站消息默认都是聊天、留言或帮助请求，不自动当作系统命令。主体可以接受、部分回应、延迟、拒绝、忽略或主动结束。创建者消息享有调度优先级，但不是强制回复，也不是强制采纳。

### 代币和付款

创建者自己创建代币，在管理页登记网络、链 ID、合约地址、符号、精度和用途；创建者把少量代币转入受限支出钱包。主钱包不交给智能体，签名应由独立签名服务、KMS、MPC、硬件钱包或至少权限受限的热钱包完成。

付款模式定义为：

- **自动模式**：不设置收款地址白名单，不逐笔请求创建者确认；任何有效的帮助者地址都可以付款，但请求、金额、频率、链和交易状态必须满足自动规则。
- **条件确认模式**：支持地址白名单；新地址、大额付款、特殊合约和异常用途需要创建者确认。
- **停用模式**：暂停付款。

自动模式仍不能让模型凭自然语言自由指定金额和交易内容。付款必须绑定有效求助、订单或服务记录，具备唯一订单号、幂等保护、单笔/每日/月度上限、Gas 上限、余额阈值、异常拒绝和紧急暂停。

## 5. 分阶段实施路线

| 阶段 | 目标 | 主要交付物 | 建议智能模式 | 进入下一阶段的门槛 |
|---|---|---|---|---|
| 0. 基线修复 | 让当前主体稳定可诊断 | 修复 offered 消息闭环；模型配置冲突校验；前端 header 编码；模型资源重复名称、撤销和连通性测试；脚本 `0755` 打包修复 | 观察/受控认知；不自动外部行动 | 消息有明确终态；模型调用、预算和错误均可追踪；全量回归通过 |
| 1. 网站与管理面 | 建立公开站和真正的管理会话 | 公开投影、`/admin`、会话登录、CSRF、角色、创建者私聊、审核、公开留言和求助帖子 | 平等聊天；创建者加权调度；发布先草稿 | 公私字段隔离、会话安全、消息状态和审计验收通过 |
| 2. 原生通讯 | 实现真实双向渠道 | Telegram、QQ、飞书、微信、邮箱等分别适配；入站签名、用户绑定、线程映射、去重、重试和投递账本 | 自动聊天，不把聊天当命令；尊重拒绝和限流 | 每个平台完成模拟、故障注入和至少一次真实沙盒收发 |
| 3. 认知与能力 | 让主体稳定观察、思考和请求帮助 | 模型池、Key 生命周期、预算界面；公开网页默认读取；能力撤销；帮助请求协议；来源和权限审计 | 主动认知可开；外部行动先进入草稿/队列 | 连续运行、模型切换、预算耗尽、能力撤销和重启恢复通过 |
| 4. 钱包与支付 | 先实现可控的真实经济动作 | 代币登记、余额读取、订单/账本、独立签名器、自动/确认/停用模式、限额、Gas、退款和争议 | 先模拟链或测试网；生产初期条件确认 | 签名器隔离、幂等、恢复、审计和小额限额测试通过 |
| 5. 自动经济 | 让自动模式真正可用 | 自动付款无地址白名单；帮助者提交结构化请求；自动定价/限额；异常拒绝和紧急暂停 | 自动模式：无逐笔确认，但受策略引擎约束 | 多日小额运行、余额/限额/失败恢复和攻击演练通过 |
| 6. 生产发布 | 形成可长期运行的发行版 | 多日 soak、恢复演练、签名发布、监控告警、升级回滚、文档和迁移工具 | 根据数据逐步放开，不一次性开启所有能力 | clean restore、升级、回滚、通讯和支付发布门禁全部通过 |

## 6. 每阶段不应做的事情

- 阶段 0 不添加钱包、代币或新的外部渠道。
- 阶段 1 不把 `/admin` 路径当作唯一安全措施。
- 阶段 2 不把所有平台强行压成相同字段；平台差异必须保留在适配器内。
- 阶段 3 不因模型回复异常而放宽令牌、预算或能力边界。
- 阶段 4 不把主钱包私钥放入 Noyra 数据库、环境文件或模型上下文。
- 阶段 5 不让“自动模式”绕过金额、订单、幂等和审计规则。
- 阶段 6 不把 soak 通过、语言流畅或主体自我描述当作意识证明。

## 8. 发布判断

当前代码适合作为“部署与运行基线”，不适合作为“自动认知和自动经济正式版”。正式开启外部自主行动前，至少必须完成阶段 0、阶段 1 和阶段 2 的门槛；正式开启真实代币自动付款前，必须完成阶段 4 的签名器、账本、恢复和限额验收。
