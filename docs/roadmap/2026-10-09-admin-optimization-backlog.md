### 已采纳的界面方案

- 使用“经济池”“深度池”两个标签页，分别显示启用资源数、可用密钥数和今日用量。
- 默认显示启用资源，提供“已停用”“已删除”“全部”筛选及名称、模型搜索。
- 资源采用紧凑列表，显示名称、模型、状态、优先级和额度摘要；编辑配置时打开独立面板。
- 添加资源默认使用当前池，保存后保持当前池和列表上下文。
- 每个配置参数旁设置可点击的问号图标按钮，打开解释框。
- 帮助范围包括认知池、资源名称、API 地址、模型名称、密钥、优先级、权重、重试次数、单价和全部额度。
- 解释框包含含义、单位、影响、示例及特殊值，并支持键盘、焦点返回、关闭按钮和手机操作。
- 说明必须与实际规则一致：优先级越小越优先；权重仅在同优先级内比较；每日输出上限不是单次回答长度；失败重试计入尝试次数。
- 将最大整数和存储精度说明移到帮助中；界面保留用户设置所需信息。
- 新建和编辑采用一致表单，分为基础连接、调度、每日限制、价格与重试、密钥管理。

### 删除和密钥生命周期

- 停用可恢复，保留配置和密钥；停用后从默认列表移出。
- 删除复用资源撤销机制，禁止后续使用，清理本地密钥，从日常列表移出。
- 保留历史调用、费用、路由关联和审计记录；已删除资源只读且不可重新启用。
- 删除确认显示资源名称、所属池、密钥数量；删除最后一个可用资源时提示任务可能等待。
- 区分删除完成与密钥清理待重试，不能在清理失败时报告全部完成。
- 已发送到供应商的请求可能继续返回，保留迟到结果及费用，禁止迟到回调恢复已撤销密钥。
- 明确删除后同名重建策略，并防止重启时环境配置复活已删除资源。
- 补充追加密钥、撤销单个密钥和密钥状态查看。
- 密钥原文不回显、不进入日志，也不写入浏览器持久存储。
- 地址、模型或认知池变更采用创建替代资源流程，避免原地改变在途调用身份。

### 可选每日限制

尝试次数、输入 Token、输出 Token、美元成本分别提供启用开关，支持任意组合。

| 操作 | 目标语义 |
| --- | --- |
| 勾选并填正数 | 启用该项限制 |
| 取消勾选 | 关闭该项资源级每日上限检查 |
| 勾选但留空 | 校验失败，要求填写 |
| 勾选并填 0 | 额度为零，不表示无限 |
| 更新请求不包含该项 | 保留原设置 |

- 关闭时禁用数值输入，可保留上次配置值供重新启用。
- 全部关闭允许保存，但需明确确认没有资源级每日额度限制。
- 旧资源保持原有四项限制，不自动放宽；新建提供可调整的默认方案和生效摘要。
- 增加带版本、完整性校验和审计的限制策略记录，不用超大整数伪装无限额度。
- 保持旧整数额度和历史校验规则兼容；策略无法验证时不能默认为无限。
- 同步调整资源级授权、池级汇总及预算压力计算，避免旧池级累加规则误拦不限额资源，也不能放宽其他资源的有限额度。
- 关闭或恢复限制、删除资源均不清空已发生用量；授权和预留继续在同一数据库事务内检查，防止并发超额。

### 已确认的规则与表现

- 截图中填写 `100000`，浏览器提示必须大于或等于 `1000000`。
- 字段前端 `min=1000000`，后台配置、发帖校验及数据库约束也要求最低 1,000,000 字节；只改前端不能实现更小额度。
- 当前字段是该主体全部公共帖子标题、正文、署名的 UTF-8 累计字节容量，不是单篇内容上限，也不代表整个 SQLite 数据库大小。
- 统计包含待审核、已发布、已拒绝、已归档等全部保留帖子。拒绝或归档不会释放此额度。
- 1,000,000 字节约为 1 MB，不是 100 万字，不会预先分配等量磁盘；达到容量后阻止新帖，不自动删除已有内容。
- 单篇正文另有固定上限 20,000 字符，当前不在该表单中配置。
- 浏览器原生表单校验失败时不会触发本次保存请求；字段范围提示不能解释下面保留的网络错误。
- `admin_network_unavailable` 在浏览器 `fetch` 抛出异常时产生，意味着未获得可供代码处理的 HTTP 响应；该文案并不能证明缺少 HTTPS、服务崩溃或令牌无效。
- 具体连接原因需浏览器网络错误、SSH 隧道状态或服务器同时段日志定位，当前截图不足以归因。
- 保存操作与保存后的 `loadRuntime()` 刷新共用一个异常处理；刷新失败也会覆盖保存成功提示。网络失败时不能仅凭红字推断配置未写入，应只读回查实际配置后再决定是否重试。

### 待统一优化时评审的建议

- 使用持久字段标签及帮助按钮，将此项命名为“全部帖子文字存储总额度”，说明包含状态、计量单位、达到上限后的行为以及与单篇长度的区别。
- 支持 KB/MB 等可读单位输入并精确转换为字节，显示已用量及剩余额度；范围提示与后台实际可配置上限一致。
- 提供独立的单篇正文长度参数，具体要求见下一节；如需更小总额度，先评审最低值，再同步前端、后台、数据库契约、历史校验和迁移测试。
- 降低容量不得删除历史帖子；低于当前已用量时明确提示并显示不能接收新帖的状态。
- 区分字段校验、会话失效、服务 HTTP 错误和浏览器连接失败；不能把所有网络失败都提示为 HTTPS 配置问题。
- 字段验证失败时更新对应提示，避免旧网络错误与当前输入校验同时出现造成误解。
- 保存成功与后续刷新失败分别显示，保护输入；异常保存结果回查后再提示重试，避免误报成功或失败。

### 已确认：图片验证码可读性与取消音频验证

用户截图中的多条粗斜线／横线遮住字符主干，无法可靠辨认答案。用户明确要求取消语音／音频验证，并要求后台能够选择纯字母、纯数字或字母数字混合；当前继续记录方案，不即时修改页面或服务器。

#### 代码核对结论

- 本地 `PublicPostStore.issue_captcha()` 已支持 `letters`、`digits`、`alphanumeric`，默认 `alphanumeric`，答案长度固定为 6 个字符。字母集合排除了 `I/O`，数字集合为 `2–9`，避免 `I/1/O/0` 混淆；验证时去除首尾空白并转成大写，字母输入不区分大小写。
- “字母数字混合”表示从字母与数字的共同集合随机抽取，并不保证每张图片一定同时出现字母和数字。因此不能根据某一张图片看似只有字母，就认定后台设置为纯字母；当前生产实际模式仍应以后台已保存设置为准。
- 后台现有“运行防护 → 公共发帖防护”表单已提供三种字符模式选项，保存接口和配置存储也支持这些模式。问题包括位置不直观、缺少持久标签／解释，以及公开验证码响应目前未返回安全的模式／长度元信息，前端无法正确提示模式或选择数字键盘。
- 图片生成器采用 `240×82` 像素 PNG 和 `5×7` 点阵字形，再对每个字符随机缩放、旋转、剪切和偏移。绘完字符后叠加 5 条较深且有厚度的贯穿干扰线及噪点；这些线能覆盖字形，图片放大也不能恢复被遮住的笔画。截图与该代码行为一致，但不是对服务器所有随机样本的可读性验收。
- 公共页面当前提供图片／音频切换，API 和生成器允许 `presentation=audio`，音频分支强制使用数字而不是管理员选择的字母模式。取消音频需同时调整页面、请求契约、后端分支、音频资源和测试，不能只把按钮隐藏。

#### 已确认的优化方向

1. **只保留图片验证**：移除图片／音频切换、播放器、音频请求／错误状态和专用 CSS，保留验证码图片、换一张和输入框。后端停止签发音频挑战，显式请求 `audio` 时返回明确受控错误；旧网页出现该错误后提示刷新页面，不偷偷退回另一种验证码。移除不再引用的音频生成代码和打包素材，更新合同测试及文档；已有挑战短期按原有有效期与验证规则处理，不为清理音频删除历史帖子或重置数据库。
2. **重新设计图片生成**：使用清晰、许可允许随程序分发的字体，确保字形完整、对比足够、字符间有稳定空隙；控制旋转／形变范围。取消当前多条粗线贯穿字符主干的做法，干扰元素采用有界的轻量方式，不能让字符互相重叠、被线条盖住或超出图像。首版不暴露容易误配的噪声强度／旋转角度设置。
3. **适配真实显示尺寸**：图像原始分辨率与显示比例配合，保留完整宽高比、不裁切／拉伸；桌面空间足够时图像和输入框并排，窄屏改为图像在上、输入框在下，避免输入框挤压验证码。验证常见手机宽度及浏览器 200% 缩放下字符清楚、没有横向溢出，刷新时保持区域尺寸稳定。
4. **后台明确选择字符模式**：在公共发帖设置中新增醒目的“验证码设置”分组；“字符类型”使用纯数字／纯字母／字母和数字混合的三选一控件，并显示当前实际生效模式、固定 6 位、有效期、尝试次数及保存状态。每项附可点击帮助，说明字母不区分大小写、排除混淆字符和字符集合含义；沿用已有模式字段，不为选项展示另建重复配置。
5. **公开输入随模式匹配**：签发响应可增加不含答案的 `mode` 和 `length` 元信息；纯数字使用数字键盘及匹配占位文字，字母／混合使用文字键盘，关闭拼写检查和自动纠错。提示准确反映实际签发模式，前端不能从模糊图片猜模式，也不能把答案写进 `alt`、DOM、图片文件名、JSON、PNG 文本元数据或日志。
6. **刷新和失败不破坏投稿**：换图、验证码过期或错误时保留标题、正文和署名，只处理验证码输入及挑战；防止旧响应覆盖新图或出现图片与挑战 ID 不一致。新图加载成功后再标为可提交，明确区分校验失败、过期、刷新限流和图片加载失败；在途提交与刷新采用明确的并发边界，不重复提交帖子。替换挑战继续受服务端签发次数和活动数量限制，不能靠频繁换图绕过限制。

建议日常配置优先选择“纯数字”以方便手机输入；这是推荐值，不自动覆盖用户已有模式。纯数字的答案空间较小，继续保留固定 6 位、签发限流、尝试次数、过期、一次消费、来源绑定、审核队列和容量限制，不能以更清晰的图片为由关闭这些控制；图片验证码也不应被描述为能独立阻止现代 OCR 或所有自动投稿。

#### 实施与验收边界

- 字符模式保存只影响随后签发的新挑战，已有挑战在原有效期内继续按保存的答案摘要验证；不能因为管理员切换模式误拒绝在途投稿。旧配置和 6 位长度保持兼容，若调整存储或响应合同须明确版本及恢复策略。
- 管理设置沿用管理员鉴权、CSRF、主体隔离和配置审计；匿名验证码签发沿用同源检查、请求限长、随机生成、摘要校验、持久尝试计数及容量／频率保护。不能把后台预览设置变成匿名接口可自行指定更简单模式的入口。
- 先核对合同和模式口径，再移除音频全链路，随后改善图片／响应式输入，最后整理后台设置；每阶段完成后复审再继续。使用脱敏或合成测试样本，不把真实挑战答案或用户投稿发给外部模型评测。
- 验收覆盖三种模式的真实字符集合、大小写／空白规则、输入键盘、模式切换后旧挑战有效性、数字模式随机性／尝试限制、已消费与过期挑战、签发限流、音频请求拒绝、旧前端提示、图片加载失败、刷新响应乱序、投稿草稿保留、提交幂等和答案不泄露。
- 可读性需用三种模式的多批合成随机样本在桌面／手机实际尺寸人工检查，特别检查字符主干遮挡、近似字形、边缘裁切和缩放；生成尺寸／字形边界检查辅助验证。PNG 有效、像素非空或旧模板匹配失败不能单独证明人能读清楚，也不能证明能防现代 OCR。

## 私密交流

状态：2026-10-09 已根据多次截图、生产版本代码及用户提供的服务器输出进行只读核对；确认方向、回复关联、刷新和状态展示存在缺口，近期两次交流认知调用成功，但不能单凭模型成功证明每条消息已经回复。完整页面优化方案待统一评审和实施。

### 已确认的状态语义与界面问题

- 截图中的多条入站消息显示 `offered`。该状态表示交流邀请已写入服务器、尚未提交最终处理决定，不是已读回执，也不能证明当前正在处理。
- 生产代码在模型调用期间仍保留 `offered`；额度不足、供应商调用失败、结构化输出失败或提案校验失败也可能让消息保持该状态。
- 真正提交的交流决定包括 `accepted`、`rejected`、`deferred`、`silent`。选择沉默对应 `silent`，不能把技术失败或等待误报为主体选择沉默。
- 回复作为独立出站记录保存，通过 `related_interaction_id` 关联入站消息；`/api/mailbox` 已返回方向、关联关系和决定时间，但页面只显示时间、英文状态和正文。
- 当前私密交流页面没有定时刷新；发送后的即时刷新可能早于异步处理完成，后来产生的回复需要再点“更新”才能看到。
- 每次发送会新建一条交流邀请；重复发送不能解决资源或调度问题，还可能增加待处理数量。
- 发送提交与随后刷新共用异常处理；消息已经记录但刷新失败时，页面可能显示发送出错，需要分别反馈提交结果与刷新结果。
- 页面宣称回复、沉默、延迟和失败都会保留明确状态，但目前展示不足以让用户区分这些情况。

### 本次现象仍需确认的运行原因

- 认知是否启用、主体当前生命周期是否允许处理交流、循环是否正常运行。
- 分池路由中的私密交流调用使用经济池；需要核对对应资源、可用密钥、额度、供应商错误及等待任务。仅配置深度池不能证明私密交流可以调用模型；池状态正常也不等于供应商调用成功。
- 用户此前未配置有效 API Key，但截图不能证明现在仍未配置，应以当前只读诊断为准。
- 调度还受每日交流调用上限和冷却控制影响；同一调度优先级内先处理较早的邀请，历史未决消息可能先被选中，但截图不能证明它们正在阻塞新消息。
- 下一步只读查看当前生命周期和 `/api/diagnostics` 的认知启用标记、交流调用状态与错误码、等待原因和经济池可用性；诊断不输出令牌、API Key、私密正文或完整环境变量。

以上为最初截图的诊断边界；后续服务器记录已证明两次 `interaction_cognition` 成功，以及世界认知／反思调用异常与循环冷却。仍需用消息关联记录确认每条消息的处理结果，不能继续笼统地把页面看不到回复说成所有模型调用都失败。

### 待统一优化时评审的建议

- 使用中文状态，并把持久交流决定与当前处理情况分别展示；区分已记录、等待调度、调用中、等待资源、额度不足、调用失败、暂缓、拒绝、选择沉默及已回复。
- “调用中”“休眠中”“认知未启用”等提示必须有当前后台证据；无法归因时显示等待原因未确定，不能从 `offered` 猜测已读、拒绝或沉默。
- 明确区分“你发送的消息”和“Noyra 的回复”，利用关联 ID 将回复与对应消息一起展示；使用本地时间，并保留原始时间查看入口。
- 消息无回复时展示可验证的原因、错误码、更新时间和可用的重试时间；全局状态与逐条消息证据分别展示，不能把其他任务的错误归到这条消息。
- 页面可见时自动刷新待处理消息，离开页面或退出登录后停止；限制并发、错误时退避，并提供手动更新及刷新失败提示，保留已经加载的内容。
- 提交成功后明确提示已记录；查询回复不能重复提交消息。异常提交通过相同幂等键和只读回查确认结果，防止误重发。
- 保留主体的实际交流决定，不强制回复、不生成假回复或假已读回执，也不为了界面反馈静默开启认知或放宽预算。
- 私密正文和处理解释仅向现有授权用户展示，执行原有鉴权与 CSRF 边界；日志和通用诊断不泄露消息或凭据。
- 验证异步回复关联、休眠与停用、资源缺失、额度耗尽、调用失败、真实沉默、延后再处理、历史未决消息、多窗口刷新及提交后刷新失败。
- 涉及调度、状态持久化或数据库变更的方案须单独审计，不因改善显示而改变现有优先级、重试、计费和自主决策规则。

### 最新截图的具体易用性问题

- 最新截图将左侧大面积留给发送表单，右侧历史限定在狭窄、固定高度的滚动列表；消息输入与阅读不在同一视觉流程，输入框下大量空白而正文反复折行。
- 两侧记录没有发信者标识或方向区分，所有卡片外观相同。生产 `InteractionStore.send()` 使用 `direction=outgoing/status=sent`；截图两条 `sent` 的“你好。”对应主体出站状态，不能当成管理员刚发出的消息。具体回复哪条邀请应按 `related_interaction_id` 核对，不能按相邻位置或相同正文猜测。
- 原始 UTC 时间串含毫秒和时区，字号偏小、颜色偏浅；未提供按日分隔、当地时间和回复引用，用户难以顺着阅读。
- 列表按创建时间倒序、初始只取最近 50 条，没有加载更早历史、搜索或回复定位；截图夹杂较早日期的记录，不能仅凭记录存在推断它们阻塞当前交流。
- `offered/accepted/sent` 等技术状态没有解释，`accepted` 不能当作已读或已回复；状态混合了入站决定与出站记录，并未显示处理进度或可验证的等待原因。
- 顶部“搜索配置暂时无法读取（HTTP 503）”来自全后台并行加载的局部失败汇总，不证明私密交流接口失败。正文阅读区承担了其他模块的错误提示，缺少直接重试对应模块的入口。
- 当前只有发送、更新两个主要操作，不能查看回复关联、原因、任务详情、最新消息提示或更早记录；整个列表刷新重建，不保护正在阅读的滚动位置。

### 完整页面方案

1. 页面主体改为连续对话区，输入框放在对话底部；上方是紧凑状态栏，下方是稳定的编辑区，详细诊断通过按需打开的侧栏／手机抽屉显示。移除大面积空白和重复标题，页面区块保持简洁，不在对话外再叠多层卡片。
2. 管理端消息靠右、Noyra 消息靠左，使用明确发信者标签并辅以颜色差异；不能只凭颜色或状态判断方向。当前入口固定 `web/web-user`，属于管理端共享邮箱，没有逐管理员作者字段；不得将全部历史入站消息伪称为当前账号本人所发，也不引入没有后端隔离的假多会话列表。
3. 消息按时间从旧到新展示，默认进入最新位置，按今天／昨天／具体日期分隔；主要显示当地时分，完整日期和 UTC 可查看。回复展示原消息的有界引用并可跳转，主动出站消息不伪造回复关系；跨分页的原消息由鉴权关联查询补齐。
4. 当前生命周期、认知启用、经济池、循环冷却和页面连接状态显示在顶部，但与逐条消息状态分开。休眠时说明消息可记录、认知处理可能等待，计划唤醒与下次重试不保证完成时间；不能把健康 HTTP 200 当成模型调用正常或主体已读。
5. 每条入站消息分开显示“接收情况”“当前处理”“交流决定”“关联回复”，主视图只保留最重要的一项中文状态，详情列时间线、关联错误码、重试时间和来源。调用中需有效执行／租约证据；没有证据时只显示已记录、等待原因未确定，不展示假打字动画。
6. 中文状态包括已记录、等待处理、调用中、等待资源、暂缓、接受交流、拒绝交流、选择沉默、有回复和处理异常。已接受不等于有回复，拒绝或沉默需真实决定；供应商调用结果未知不等于消息提交失败，也不保证未计费。出站账本记录与外部渠道投递分别解释，不能把 `sent` 一律当作收件端送达回执。
7. 详情以可验证证据解释“为何等待”：休眠／暂停、认知未启用、经济池不可用、预算不足、供应商冷却、请求结果未知、输出未通过验证等。全局上下文不回填成这条消息的失败原因；另设“查看关联调用”“前往认知资源”“查看活动日志”入口，默认不展开心理状态、完整提案或反思内容。
8. 输入框自动增高至有界高度，支持中文输入、粘贴长文本、换行、字符计数、清晰的超限提示和空白校验。默认 Enter 换行、Ctrl/Cmd+Enter 发送，中文输入法组合期间不触发发送；手机保留明确发送按钮并检查软键盘、滚动和底部安全区域，不依赖拖动文本框尺寸。
9. 输入草稿在页面导航和只读刷新时保留，退出登录清除。默认只保留当前页面内存，不把私密正文自动写到 localStorage；如需刷新后恢复草稿，须独立评审存储、撤销及隐私设置。发送中只冻结本次提交快照，保留后续输入，成功后不能清空用户新写的内容。
10. 提交后显示客户端提交中，HTTP 确认后换成服务器已记录并使用正式消息 ID；记录失败保留草稿，记录结果未知先查询同一幂等键。一次用户发送意图对应固定幂等键，网络重试复用，独立的新消息才生成新键；提交成功与历史刷新失败分别反馈，不因总览／搜索接口失败建议再次发送。
11. 页面可见时按约 5 秒起步有界增量刷新，在空闲及错误时退避，切走或退出时停止并取消在途请求，限制单次并发；返回时恢复读取，不触发模型测试或处理重试。旧请求不可覆盖新状态，鉴权失效停止读取并回到登录。

- 自治循环快照为连续失败 5 次、`circuit_status=open`、`last_error_type=ReflectionCognitionPending`。这说明反思尚无可用结果并进入冷却，不是服务进程退出；快照的下一次重试时间为北京时间 12:51:04，计划唤醒为 17:40:34，均不是保证执行或完成的时间。
- UTC 04:24:35（北京时间 12:24:35）的主机采样：2 个 CPU，负载 `0.05/0.05/0.01`，后续采样 CPU 空闲约 95% 至 100%，I/O 等待 0% 至 1%，内存总量 1.9 GiB、可用 1.5 GiB，服务约 187 MiB，未发生明显换页；`NRestarts=0`，所查询内核日志没有 OOM 记录。`vmstat` 第一行是开机以来平均值，后续行才是采样间隔值。
- 主机采样发生在休眠及熔断之后，不能据此完全排除失败时的短暂负载或虚拟机调度干扰；现有证据不支持把升级服务器作为首要解决办法。内部预算压力也不代表供应商账户余额、限流或响应速度。
- 当前可以确认的链条是调用错误／调用状态问题抬高失败压力，触发新休眠；休眠反思的模型调用也结果未知，进一步触发循环冷却。下一步应优先核实供应商端对应请求的耗时和状态、实际资源连接及模型响应契约，而非盲目更换密钥、延长超时或重发结果未知的请求。

### 需要只读确认的诊断

- 查看同一事务快照下的当前生命周期、最近休眠状态、触发类型、启动／完成时间、预休眠疲劳值和预计唤醒时间。
- 将已知固定触发文本转换为原因码，只输出阶段、时间、数字指标和错误码；不输出自由文本的私人休眠理由、反思内容、私密交流、API Key、令牌或完整环境。
- 查看资源压力更新时间、近期模型调用状态／错误码，以及自治循环熔断、下次重试和最后成功时间，分清新调用失败与旧压力残留。
- 代码在活动轮次中先判断是否应睡眠，随后才在主动工作钩子刷新池压力；资源配置保存不直接唤醒或刷新全部历史压力。因此需专项审计新资源已可用但旧压力仍触发再次休眠的情形，当前仅是代码层面的待验证风险。
- 如持续停在 `reflective_sleep`，检查反思调用失败、调用上限与退避；不能把“模型未生成可验证反思”显示成已经完成整合。
- 评审按资源设置请求时限、区分超时与协议／输出错误、保留有界耗时指标的方案；先验证慢模型与结构化输出的实际响应，再确定时限及总任务预算，不把延长超时当作必然修复。
- 专项审计失败压力触发休眠后反思仍依赖故障资源、结果未知隔离与调用上限／冷却的配合；保留重复发送及重复计费防护，确保页面能解释为何等待及下次可重试时间。
- 不通过强制唤醒、重置疲劳或绕过预算来代替诊断；不在收集问题期间更改服务器行为。

### 日志入口的确认缺口

- 生产已有鉴权只读 `/api/runtime-logs`，按游标合并运行事件、模型调用、动作、路由、元认知、审计等摘要；同时已有生命周期、管理员动作和模型调用查看接口。
- 当前生产 `admin.html` 没有独立日志导航，`admin.js` 没有调用运行日志接口的页面流程；“运行防护”仅显示诊断汇总。因此用户在管理台看不到活动时间线，是已确认的前端功能缺口，不表示系统没有保留记录。
- 公开“行为”只反映可公开动作历史，供应商健康只反映聚合统计；两者不能替代私有运行日志或准确说明再次休眠原因。

### 待统一实施的日志与生命周期方案

- 新增“活动日志”导航，设“运行事件”“生命周期”“模型与搜索”“行为执行”“管理审计”标签；默认显示必要摘要和近期异常，中文化类别、状态与原因码。
- 提供时间范围、类别、成功／失败／等待状态筛选、暂停自动刷新、手动刷新与分页；保留列表上下文，不能在后台把全部历史拉到浏览器。
- 每条显示发生／开始／完成时间、来源、结果、可验证原因和关联记录入口；使用本地时间并保留原始 UTC，不用一份含混时间字段替代多个时间含义。
- 生命周期展示当前状态、进入时间、已持续多久、最近一次活动时长、休眠触发原因类别、计划唤醒时间和下一步条件，并列出完整转换时间线。
- 普通循环控制与实际业务结果分开：空闲心跳不表示认知成功，成功执行一次调度不表示模型调用成功；正在反思、等待资源、调用失败与休眠完成分别展示。
- 关联模型请求、动作、交流和路由记录时沿用现有私有读取权限；默认不展开消息正文、模型输入输出、心理状态或反思内容，不凭日志摘要推测主体意愿。
- 在确认有效资源与仍有效预算的前提下审计再次休眠的判断顺序；同原因的非紧急反复休眠可评审退避或调度改善，但不设置绕过硬预算、完整性或安全暂停的强制活跃窗口。
- 针对短时间重复休眠或阶段超时显示原因和提示；告警阈值应结合真实触发与配置，不把正常的阶段推进都标成异常。
- 复用现有摘要日志及游标分页；生命周期详情、原因码、时间／类别筛选缺失时扩展受控接口，不能未经验证在前端假装已支持，也不逐秒重复写入心跳日志。
- 管理台运行日志与服务器 systemd 文本日志分开；若后续接入服务器日志，必须单独设计最小权限和脱敏边界，不给浏览器任意路径读取或任意 shell 执行能力。
- 日志导出属于单独鉴权操作，默认只含选中范围的脱敏摘要；不因新增页面开放匿名访问或跨主体数据，不提供删除核心审计记录的按钮。
- 验证休眠原因关联、阶段在途／失败、旧压力处理、跨日预算、反复休眠、分页无重复遗漏、多窗口并发与日志脱敏；涉及调度变更单独审计后再部署。

本次只追加诊断结论和方案，没有新增页面、修改调度、强制唤醒或读取服务器实际日志。

## 其他模块

### 通讯渠道、账号关联与跨渠道聊天

状态：2026-10-09 用户反馈接入复杂、不理解入站账号绑定、QQ 与管理台聊天不同步，并已采纳本节易用性、验证绑定及统一聊天方案，待统一实施；不把新的统一聊天、验证绑定或消息转发能力描述为现有功能。

#### 已核对的问题与原因

- 当前通讯页面把添加机器人、凭证、默认收件人和账号准入放在同一长表单／列表里；术语直接使用平台账号 ID、发送者 ID、`creator/participant`，缺少清晰的接入步骤、回调地址和实际收发状态。
- “添加渠道”只是配置一个收发通道；“入站账号绑定”决定哪个外部平台身份可以将文字送进 Noyra 的交流队列。这是准入及身份关联问题，不是模型配置，也不是开启服务器管理权限。
- QQ 的平台账号通常对应配置的机器人 App ID；发送者是已验签事件提供的用户 OpenID／member OpenID，未必等于数字 QQ 号。当前要求用户手填这些字段，普通用户难以知道从哪里获取。
- 渠道显示 `active` 只能证明已启用配置，不能证明回调、平台授权、账号准入、模型处理和外部投递全部成功。页面目前缺少逐步验证、最近入站／出站时间及错误原因。
- 当前 `/api/mailbox` 明确只读取 `channel=web`；网页发送接口固定为 `web/web-user`。QQ 消息写入同一主体数据库，但属于 `qq` 渠道，因此不会自动出现于当前网页邮箱。这不是仅靠自动刷新就能解决的问题。
- 外部入站另有平台会话／线程和回复路由；回复需保留原始机器人、收件场景和当前消息 ID。现有外部 `interaction_threads` 中的消息级回复定位字段不等同于用户希望的长期聊天窗口，不能直接拿它当微信式会话列表。
- 当前关系归属主要使用 `counterparty`，网页是固定身份，QQ 私聊可能是用户 OpenID，群聊可能是群 ID。没有可靠的“这几个平台身份属于同一个人”映射；也不能把群 ID 当成某个群成员，或按昵称／数字 QQ 号自动合并关系和私密记忆。
- 同一个 Noyra 主体可能检索已有长期记忆，但这不等于完整原始聊天历史已跨渠道关联，也不证明她已确认网站与 QQ 是同一人。跨渠道历史和记忆范围需与前述多窗口方案一起设计。
- 当前 QQ 适配针对官方开放平台 HTTPS API，不是 NapCat／OneBot。页面应在选择平台时明确接入类型和能力，避免用户填入不兼容的个人 QQ 机器人地址。

#### 目标体验与页面分工

用户只需完成“接入机器人 → 在 QQ 发一次验证消息 → 后台确认这是我 → 开始聊天”。日常聊天统一进入“私密交流”，通讯页面只负责接入、联系人、连接状态和投递问题。

1. **接入渠道**：选择 QQ 官方机器人、Telegram、飞书应用机器人、微信公众号、邮件或通用 Webhook；各平台使用独立向导和能力说明。明确单向通知与双向聊天，不用一个通用表单让用户猜字段。
2. **联系人与我的账号**：将“入站账号绑定”改成“允许谁与 Noyra 聊天”，主要入口为“关联我的 QQ”和“邀请其他联系人”；普通视图只显示名称、平台、验证状态和允许聊天开关。原始 ID 收到高级详情，保留人工输入作为故障处理方式。
3. **连接与投递状态**：显示凭证配置、回调验证、平台事件权限、最近收到消息、账号验证、最近发送、未知投递和故障原因；每一项有准确时间和局部修复入口，不能合并成一个虚假的“已连接”。
4. **日常聊天**：QQ 私聊、网页多窗口和 Noyra 的真实回复进入统一的聊天列表／详情；消息保留小型来源标记，主要身份为“我”和“Noyra”。联系人、群聊与频道单独显示，不能混进“我的私密聊天”。

#### 接入向导

- QQ 基础设置默认填入官方 API 地址，通常只要求机器人名称、App ID 和 App Secret；访问令牌采用已有短期获取机制，不要求普通用户反复手填。旧版 HMAC 密钥、默认目标类型／收件人等仅在需要兼容或主动通知时展开。
- 在页面提供平台创建应用入口和各字段的问号帮助；说明字段来源、用途、是否必填和秘密性质。App Secret 只写入受保护秘密存储，保存后仅显示已配置，不回显，也不进入 localStorage、日志或备份清单正文。
- 根据已验证的公网 HTTPS 基址生成完整回调地址并提供复制按钮；基址来自受控服务器配置，不信任任意请求 Host。检测 TLS、反向代理路径和平台回调的不同状态；未有可用域名／证书时允许保留接入进度，显示具体阻断项，不能宣称填入服务器 IP 就能完成 QQ 官方回调。
- 先校验配置格式，再验证凭证和平台回调；验证过程不调用模型。发送试验文字是单独动作，先显示目标及会消耗平台请求额度，禁止自动向任意默认收件人发送消息。
- 向导只显示当前需要操作的步骤；成功后默认回到紧凑渠道列表。列表支持启用、停用、查看详情、替换凭证和撤销，撤销沿用秘密清理机制；未验证完成的配置显示“待验证”，不能用“已启用”替代可用性。
- 接入检查失败只影响当前渠道，保留其他已接渠道、输入和进度；解释平台拒绝凭证、回调未收到、签名校验失败、账号未关联、平台发送权限不足和消息结果未知的差别。

#### 免手填 ID 的验证绑定

1. 管理员登录后台后点击“关联我的 QQ”，选择机器人和本次关联的交流身份，后台生成一次性短码并显示“请在机器人私聊发送：绑定 <一次性码>”。该码只用于账号验证，绝不是管理操作令牌或 API Key。
2. 机器人收到平台已验签、处于有效时间窗的私聊事件后，服务端从事件提取机器人账号、发送者及私聊目标，校验短码；自动填写平台字段。用户无须查 OpenID，也不能由消息正文自报 QQ 号、App ID 或角色。
3. 后台显示“已收到验证，等待确认”，展示机器人、平台身份的脱敏标识、昵称（仅辅助展示）、时间及私聊场景。管理员确认“这是我的 QQ”后，才建立“允许聊天”及“同一交流身份”关联；昵称相同不能代替控制权证明。
4. 关联完成后只显示“我的 QQ · 已验证 · 允许聊天”，并提供进入聊天、暂停接收、解除关联和重新验证。邀请其他联系人采用独立邀请，由后台明确允许，不自动升级为管理员或创建者。

安全要求：短码使用密码学随机值，建议 10 位 Base32、5 分钟有效；挑战绑定主体、机器人、目标交流身份和创建会话，服务端只存校验摘要，单次消费并限制失败次数（建议每挑战至多 5 次）、全局／来源速率和在途挑战数量。替换挑战须失效旧码；过期、已消费、被撤销、账号已关联其他身份或机器人不匹配时明确失败，不能静默覆盖既有身份。

- 验证消息在平台验签后由专用受限处理分支消费，不进入认知队列、长期记忆、普通聊天原文或正文日志；不把它解释成一般 QQ 管理命令。未绑定的普通消息仍不能进入认知；只新增完成有效挑战所需的最小准入。
- 默认只在一对一私聊验证“我的账号”。群里发短码不能把整个群绑定为我，也不能把其他群成员的消息当成我；群内开放聊天另外配置允许的场景和成员范围。
- 短码截图或转发可能被他人使用，所以后台最终确认和平台身份范围检查必须存在。平台不提供私聊权限时说明前置条件并保留受控人工方案，不降低验签或直接按昵称绑定。
- 单个管理令牌目前不能证明网页历史由哪个自然人撰写；本次“这是我”是经过验证后建立新的交流身份。旧 `web-user` 历史仍按共享管理邮箱处理，明确选择历史归属并保留证据，不自动把所有管理台历史授给新关联的 QQ 用户。

#### 三层同步与推荐默认值

| 同步层 | 推荐行为 | 明确边界 |
| --- | --- | --- |
| 后台可见 | 已准入的 QQ 入站、真实回复和投递状态可在管理台统一查看，带 QQ 来源标记 | 查看不触发模型、重发或跨渠道投递 |
| 同一身份与记忆 | 经验证的“我的 QQ”与网站交流身份关联；本人授权的私聊窗口共享原始历史检索和长期记忆 | 群聊、其他联系人与未确认历史不自动混入私密上下文 |
| 外部转发 | QQ 来源的回复默认发回原 QQ 会话，同时在后台显示；网页来源的回复默认留在网页 | 全量转发网页消息／历史到 QQ 另有明确开关，不能因查看同步自动泄露私密原文 |

- “同步”首先意味着读取同一条服务端消息，不复制为两条交流邀请；同一处理轮次的决定和回复必须幂等，不能因为增加渠道再次调用模型。已有暂缓后继续处理的机制保持真实轮次，不把它误称为重复消息；额外渠道送达属于独立投递记录。
- 完成本人验证后，新 QQ 私聊默认进入“我的 QQ”窗口；可以将该外部私聊关联到一个已选择的网页聊天窗口，也可以保留独立窗口。所有本人窗口共享授权历史和记忆；外部会话默认只映射到一个当前有效逻辑窗口，防止消息重复进入多个主题。
- 支持在后台选择“此 QQ 私聊使用哪个聊天窗口”，显示当前关联和生效时间；切换只影响后续消息，不移动、改写或删除旧记录。无需 QQ 用户发送命令选择网页窗口，网页新建窗口也不假装在 QQ 自动创建独立平台会话。

1. **接入体验与只读状态**：整理平台独立向导、字段解释、默认地址、回调复制、能力说明和分步状态；明确凭证／回调／收发的事实边界。核对脱敏、CSRF、TLS、配置未保存、错误保留输入和手机操作，不做真实模型调用或自动发送。

3. **身份与会话基础**：对接多窗口模型、本人身份关联和外部会话路由，演练历史迁移及来源追踪。验证群成员隔离、共享管理邮箱历史不能自动认领、跨平台名称碰撞、取消关联和回滚恢复。

5. **跨渠道记忆与可选投递**：实现授权历史检索、群／私聊上下文隔离和私聊新回复可选推送；用模拟平台测试无重复模型调用、无转发回环、QQ 限流／被动回复超时、未知投递、解绑后停止以及删除后不复活。真实平台收发只在选定测试账号和明确范围内验收。

#### 当前页面的问题

- 单页同时放入余额观测、网络／资产／地址登记、观测健康、RPC 预算、余额采集队列、自动付款策略、任务赏金、付款订单、内部账本、链上签名执行和审计历史；模块顺序和标题层级不清，实际“钱包与转账”页面远超余额采集范围。
- 首次打开会并行请求多个模块；网络图谱又同时请求诊断、网络、资产、地址和余额。图谱使用 `Promise.all`，其中一个接口失败会阻止整个图谱更新；页面没有清楚标注各区最后成功时间、部分失败和数据覆盖范围。
- 多个列表固定最多请求 100 条，界面只报告已加载条数，没有总数、游标、是否还有下一页或当前排序范围。用户无法判断列表完整性；刷新较多数据也增加等待和阅读负担。
- 网络卡片将网络、资产、完整地址、完整 RPC URL 和最近余额堆叠展示。RPC URL 若包含 userinfo、查询参数或片段中的凭据，当前前端会直接渲染，存在泄露风险；页面应默认只展示脱敏后的协议／主机／路径摘要，绝不显示 URL 用户信息、查询、片段或密钥。
- 余额、赏金额、订单金额和账本净额主要以最小单位整数显示；虽然资产记录已有 `decimals`，列表没有把最小单位转换成“人类可读金额 + 资产符号”，也缺少精确原值的详情入口，容易误读数量级。观测时间没有明确说明时区和快照新鲜度。
- 观测健康中的“新鲜／临界／过期”“从未观测／未来”“异常组合”“最大年龄”等字段没有解释判定口径；健康汇总与某地址余额快照是两种不同信息，页面容易让用户把健康状态误读成余额状态。
- “更新”既用于读取已有数据库快照，也用于重新读取队列、策略、预算等；它没有统一说明是否访问链上 RPC。队列“处理到期读取”会消耗 RPC 预算，而“更新网络与余额”只读取现存数据，两者的副作用差异不够醒目。
- RPC 预算卡只列窗口秒数、请求上限、已用／预留请求和下次可用时间，没有窗口起止／重置时间、预留的含义、单次操作预计成本及“无预算时会怎样”的说明。
- 自动付款策略同时显示付款模式、自动付款总开关、金额上限、白名单开关和紧急暂停；多个独立门槛的组合不直观。白名单关闭代表任何通过格式校验的地址都可能被接受，需显著提示实际影响。当前表单也未用按资产精度格式化的金额帮助管理员校验上限。
- 订单、账本和链上执行结果分散在不同卡片；账本只展示账户和净额，缺少网络、资产、单位、统计范围以及余额与内部预留的区分。
- 链上执行按钮语义有实质风险：当前“退款”按钮对 `unknown` 和 `failed` 执行记录都会出现，但后端仅允许订单状态为 `failed` 时释放内部预留；未知交易不能退款，点击会冲突。该操作实际是退回内部账本预留，不会撤回或退回链上资金，现有“退款”名称会造成错误预期。
- 当前未知交易同时提供“查回执”“明确重试”和“退款”。结果未知时应先核对链上回执；重试可能触发新的链上付款，必须基于最新状态、强确认和审计理由；不得把未知结果折算成失败。批量“恢复未完成”会把有限数量的签名中在途执行记录转入结果未知，属于状态恢复操作，不应与普通刷新并列。
- 队列条目展开运行 ID、租约、快照 ID、错误码和尝试详情等多种技术字段；所有记录平铺并混用操作控件。钱包专属 CSS 还使用 10–12px 小字、长标识符和嵌套滚动列表，窄屏继续显示长表单和动作，阅读密度高。

#### 目标信息架构

钱包页面顶部保留紧凑摘要：最近余额观测时间、从未观测／过期目标数、队列待处理／结果未知数量、当前 RPC 预算状态、付款是否关闭／暂停，以及需要人工处理的转账数。摘要只显示计数和下一步入口，不暴露密钥或完整地址。

正文拆成可切换的独立模块，按需加载所选模块的数据：

1. **余额观察**：按网络／资产汇总可用余额、地址数、最近观测时间和新鲜度；可展开查看地址级快照。明确这是最后已保存观测，不代表实时链上余额。把“刷新页面数据（不发 RPC）”与“发起链上读取（消耗 RPC）”做成不同名称和按钮。
2. **余额采集**：单独管理排队、运行、等待重试、结果未知、成功、失败和取消记录；顶部显示各状态总量和当前过滤条件，支持有界游标分页、尝试详情及队列入队、取消、明确重试。每个动作旁说明是否仅排队、是否会调用 RPC、幂等键和重试风险。
3. **网络与资产**：按网络分组展示网络状态、资产符号／小数位、已登记地址数；详情中展示经过脱敏的 RPC 来源。凭据只允许通过受控设置流程查看“已配置／未配置”，任何 UI、错误、审计和导出均不得回显 URL 凭据。
4. **RPC 预算**：按网络显示当前窗口的开始／重置时间、窗口上限、已结算请求、预留请求、剩余额度和下次可用时间；解释请求预留、失败结算、未知结果和不同操作会否计入预算。数据来自服务端预算接口，不由前端自行推算。
5. **任务赏金与账本**：将赏金发布／状态和订单／账本分区展示；列表以人类可读金额、网络、资产符号、状态和时间为主，精确最小单位、ID 和审计细节放在展开详情。明确内部额度预留、已结算和已释放的差别。
6. **付款与链上执行**：将自动付款策略、紧急暂停、订单状态机和链上转账记录集中管理；策略顶部显示实际有效门槛和阻断原因。按“待人工确认、准备签名、已广播、结果未知、已确认、失败”分组，未知执行默认只突出回执查询和人工对账入口。
7. **审计记录**：独立提供按时间、事件、网络、订单／执行 ID 筛选和游标分页；人类可读操作摘要先行，技术字段按需展开，显示覆盖范围和最后更新时间。

页面默认只加载摘要和当前选中模块，不再一次拉取所有模块与全部详情。局部接口失败须保留其他模块和已加载内容；每个列表呈现加载中、空数据、筛选无结果、部分结果、请求失败、总条数／已加载条数／是否还有更多以及最后成功读取时间。切换模块取消过时读取，旧响应不能覆盖新状态。

#### 金额、状态与操作规则

- 人类可读金额必须按资产 `decimals` 从最小单位精确换算，使用十进制定点／字符串算法，不用浮点数；并列显示资产符号。展开详情可查看未舍入精确值、最小单位原值及资产精度。禁止对无法识别精度的金额猜测单位。
- 余额观测状态分成“无快照”“有效期内”“接近过期”“已过期”“未来时间异常”“读取失败／结果未知”；零余额是有效观测值，不等同于没有快照或 RPC 故障。给出服务端判定时间和阈值。
- 使用一致的中文状态词和原因解释；链上执行、付款订单和采集运行是不同状态机，不能用一个含义不明的“失败”标签概括。显示事件发生、提交、广播、确认和快照采集的不同时间。
- 把只读刷新、入队、消耗 RPC 的执行、取消、重试、签名广播、恢复和释放内部预留分为不同视觉层级。任何会访问外部 RPC 的动作说明预计预算影响；实际签名或广播注明不可轻易撤销。
- 未知链上结果只能先查询回执并根据链上证据刷新状态；仍未知时保留资金预留并提供人工核对指引。明确重试前要求二次确认当前订单、网络、资产、金额和收款地址，解释可能重复付款风险并记录理由；同一订单的并发重复执行必须由服务端幂等与状态冲突保护。
- 将当前“退款”改称“释放失败订单的内部预留”（或等价清晰名称），仅在订单确认为 `failed` 且后端允许时显示。明确此操作不发链上交易、不追回已广播资金；`unknown` 状态禁止展示释放入口。
- “恢复未完成执行”显示将扫描的范围、上限和可能把签名中记录置为结果未知的影响；确认后提交，完成后回查结果并引导逐项查询回执。它不是刷新，也不代表链上执行已恢复。
- 自动付款保存前生成可读策略摘要：模式、总开关、紧急暂停、单笔／每日上限、白名单启用状态和本次变更影响；关闭白名单时明确说明收款地址的校验边界。保存采用版本检查并展示实际生效策略。

#### 安全、数据与兼容边界

- 管理端接口继续要求现有管理员鉴权和 CSRF 防护，并在服务端强制主体隔离、字段范围和状态转移；前端隐藏按钮不能作为安全控制。操作理由、操作者、幂等键、结果和状态冲突沿用既有钱包审计机制。
- 前端只持有短期的管理员会话；私钥、签名凭据、助记词及 RPC 用户信息不得发送到浏览器。RPC 地址在任何 UI、HTML 属性、日志、异常、分析事件和导出中均脱敏，不以“管理员页面已鉴权”为展示秘密的理由。
- 不改变付款策略默认值、自动付款启停状态、签名隔离、网络白名单、金额硬限制、余额采集限制或链上确认规则来解决易用性问题；新增说明与页面拆分本身不得产生交易或链上请求。
- 优先复用现有接口与受控快照。若需总数、分页游标、预算窗口口径、脱敏 RPC 来源、资产精度关联或操作预览等缺失字段，先定义并审计 API 契约，再实现；只有确认无法兼容时才新增正式数据库迁移，迁移需在脱敏副本中演练、验证钱包完整性及可恢复备份。
- 列表导出若纳入后续范围，必须单独鉴权、设置硬行数上限并默认脱敏地址和敏感 URL，不导出签名材料或无界审计正文。

#### 分阶段实施与审计门槛

1. **安全与接口基线**：逐项核对生产版本与本地差异、鉴权／CSRF、RPC URL 存储和展示、金额单位、分页上限、审计事件和付款／执行状态转移。先只形成契约和测试，不触发真实 RPC、签名或交易。审计通过后再进行界面阶段。
2. **页面拆分与局部加载**：增加模块导航、摘要、懒加载、独立错误／空态和窄屏导航；保持现有接口和行为不变。检查页面切换、慢响应、401、单模块 503、刷新竞争与已加载内容保留；确认无副作用后再进入观察数据阶段。
3. **余额观察与网络展示**：实现按资产分组、金额精度格式化、快照新鲜度、健康术语解释和 RPC URL 脱敏；所有操作只读取已有快照。通过零余额、缺失快照、过期／未来时间、特殊精度、长地址和带查询凭据的 URL 测试后再进入队列阶段。
4. **采集队列与 RPC 预算**：实现有界分页、状态计数、预计预算影响、入队／取消／结果未知回查／明确重试的分离说明。验证幂等重复入队、预算耗尽、失败与未知、并发领取、租约过期和取消竞态；真实网络读取只在单独授权的验收范围内测试，不由界面回归测试触发。
5. **赏金、账本与付款策略**：分别整理业务状态和可读金额，解释内部预留及付款门槛；不启用或放宽自动付款。审计版本冲突、禁用策略、暂停开关、白名单关闭、订单过期、余额不足和账本双重记账后再进入链上执行阶段。
6. **链上执行与恢复**：单独打磨签名隔离、二次确认、回执轮询、结果未知、重试、失败预留释放和恢复未完成流程；未知结果不得出现退款／释放入口。使用模拟签名器和可控链测试重复点击、响应丢失、已广播但未确认、重复回执、链重组、恢复后对账和审计记录，不在页面验证中向真实网络广播资金。
7. **审计、分页与响应式收尾**：补齐审计筛选和有界游标，验证结果排序稳定、跨页无重漏、刷新局部失败、多用户会话权限、URL／地址脱敏、键盘操作、手机布局与缩放。全部模块完成安全审计和回归后，再评估发布。

每阶段单独给出接口、权限、金额、预算、幂等、审计和界面检查结论；发现阻断问题时停在该阶段修复并复审，不能带着未解决的链上资金风险进入下一阶段。本节记录审计和方案，不授权启用付款、触发真实 RPC／链上交易、迁移数据或部署。

待用户继续检查其他管理后台模块后，继续追加反馈、诊断结论和采纳方案，再确定统一优化的最终范围。

## 管理台总览升级建议

状态：2026-10-09 用户要求评估总览页面的易用性和信息完整性；本节只记录方案，未修改页面、接口或运行行为。

### 当前总览的主要问题

- 当前页面将配置向导、版本升级、生命周期、认知诊断、存储、七日用量、供应商健康和数据清理全部放在同一个长页面，重要异常容易被低优先级信息淹没。
- 顶部只显示生命周期代码、公开日记数、待处理交流和等待任务；没有同时说明状态持续时间、触发原因、下一次重试／唤醒时间、最近成功调用和当前阻断项。
- 经济池与深度池只显示一个状态文字，无法快速判断模型、可用资源、密钥健康、最近成功率和延迟；`unknown`、`404`、冷却中等状态需要进入其他页面才能理解。
- 用量固定为最近 7 天，不能在总览快速切换当天、3 天、7 天、1 个月、3 个月和全部；成功率、未知结果、延迟、估算费用和搜索用量缺少同一时间窗口对照。
- 供应商健康、数据保留和“立即清理一批”属于运维模块，与日常状态混在总览中；清理按钮在首屏出现，容易被误认为普通刷新操作。
- 各区域独立请求虽能局部失败，但首屏缺少统一的“数据更新时间、失败区域、重试入口和数据覆盖范围”，用户难以判断“暂无数据”和“加载失败”的区别。

### 建议的总览结构

1. 顶部固定“运行摘要栏”：当前生命周期的中文名称、进入时间、已持续时间、最近一次活动时长、在线／暂停、完整性、服务进程和数据更新时间。生命周期代码保留为次要技术字段，不作为唯一标题。
2. 摘要栏下显示“需要处理”区域，只列真正需要操作的事项，按阻断、风险、提醒分组：认知不可用、反思连续失败、未知模型调用、待处理私密消息、待审核帖子、存储空间或完整性异常、升级不可用。正常项目收进“运行正常”摘要，避免大量绿色卡片占据首屏。
3. 设置向导改为可折叠的“配置进度”，仅在仍有必要配置或用户主动展开时占据空间；显示模型、搜索、通讯、钱包的就绪状态和直接入口，不能把可选项与阻断项混为同一完成率。
4. 认知运行卡分成经济池和深度池两列，分别显示启用资源数、可用密钥数、当前模型、最近成功／失败／未知调用、最近延迟、冷却状态、预算压力和下一次可重试时间。池卡提供“查看资源”和“查看活动日志”入口。
5. 私密交流卡显示待处理、处理中、已回复、失败、结果未知的数量，以及最早等待时间；点击进入私密交流并保留过滤条件，避免只显示一个待处理总数。
6. 模型与搜索用量卡使用统一时间段选择器：当天、最近 3 天、7 天、1 个月、3 个月、全部。切换只刷新该卡，显示实际 UTC 起止、展示时区、最早可用数据、调用／尝试／重试、成功／失败／未知、Token、已知／估算费用、搜索方法和采样时间。
7. 存储与安全卡显示加密卷和挂载状态、可用空间、数据库快速检查、完整性状态、最近完成时间、活动告警、备份验证状态和服务重启次数；异常时显示具体下一步入口，不把 `alert` 模式误写成系统故障。
8. 最近活动卡显示脱敏的最近 10 条重要事件，优先显示状态切换、模型失败、未知结果、反思等待、消息回复和管理员操作；默认只显示摘要和时间，详情进入活动日志分页，不能把提示词、回复正文、令牌或 API Key 放进总览。
9. 版本维护、供应商健康和数据清理从总览移到“运维”折叠区或独立导航；总览只显示版本状态、健康异常数和清理待执行数，并保留明确的查看入口。清理操作不能在首屏与普通刷新并列。

### 易读性与交互规则

- 状态统一使用中文名称、颜色、图标和文字原因；颜色不能作为唯一信息。`unknown` 显示“结果未知”，不折算为失败或成功。
- 所有时间显示本地时间并保留 UTC 提示；区分发生、开始、完成、下次重试和计划唤醒，不能用一个时间字段代替全部含义。
- 每个区域显示“数据更新于”“覆盖范围”“是否实时／缓存”三项元信息；请求失败保留上次成功数据，同时标注过期时间并提供局部重试。
- 数值统一使用可读单位，长整数显示完整精确值的悬浮／详情文本；费用区分已知、估算、未知，不把零费用解释为免费。
- 卡片标题和关键数字保持紧凑，详细解释通过问号帮助按钮、展开详情和对应页面承载；避免在首屏堆叠大段说明。
- 所有可执行操作标注影响范围和是否消耗模型额度；刷新、查看、测试、清理、暂停和唤醒必须视觉区分，危险操作不放在状态卡的默认按钮位置。
- 支持桌面、窄窗口、手机和浏览器缩放；移动端优先显示摘要和阻断事项，详情改为可展开列表，不要求横向滚动查看关键状态。
- 总览加载采用区域级骨架和独立错误状态，不能因一个接口失败清空整个页面，也不能把接口返回的对象直接渲染为 `[object Object]`。

### 后端与安全边界

- 总览使用一个有界的只读聚合接口或并行的受控接口，服务端完成统计和权限检查；不向浏览器拉取全部历史模型调用、日志或密钥详情。
- 聚合接口返回资源池、状态、计数、时间窗、覆盖范围和脱敏错误类别，不返回 API Key、令牌、完整 URL 查询参数、提示词、模型回复或私密消息正文。
- 所有卡片按区域独立超时和缓存；健康聚合缓存与模型调用账本的历史范围分开说明，不能以健康数据缺失伪装为零调用。
- 对“待处理”“未知结果”“阻断”定义稳定的服务端字段和版本，前端不根据字符串猜测严重程度；状态降级时保留原因码和关联记录入口。
- 生命周期详情和活动日志沿用现有鉴权、CSRF、主体隔离和游标分页；总览不开放暂停、唤醒、重试或清理等隐式副作用。

### 实施顺序与审计门槛

1. 先统一状态词、时间口径、错误分级、区域加载和首屏摘要，不改变运行逻辑。
2. 再实现认知池、交流、存储安全和最近活动的只读聚合，验证权限、脱敏、缓存、超时和历史边界。
3. 接入用量时间窗和供应商健康摘要，验证查询计划、统计不重复、未知结果与估算费用口径。
4. 最后整理配置向导、运维折叠区和响应式布局，验证所有入口、失败恢复、未保存状态和移动端阅读。

每个阶段完成后进行接口契约、浏览器流程、权限脱敏、并发读取、缓存过期和回归审计；没有阻断性问题再进入下一阶段。当前只记录方案，不实施页面改造或部署。
