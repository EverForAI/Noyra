# 2026-10-22 可运维性与后台解释能力优化

## 范围及约束

实施用户选定的三项：安装升级永久修复、低成本运行观测、后台可解释状态。仅修改开发工作区，不连接生产服务器、不自动部署、不启用付款、不改变主体行为或安全准入，不修改数据库 schema。保留原有未跟踪审计日志。

## 顺序与根因

1. 安装器：部署辅助脚本改用新暂存/已发布环境的隔离解释器；公开程序构建阶段限定 umask 0022，数据/密钥权限保持严格；在停止旧服务前完成预检，停止旧服务前及迁移前两次检查真实服务用户可导入。补齐持久化、脱敏的阶段结果报告；保留原先停止状态，显式 --start 才请求启动；旧代码回滚先验证 schema 兼容性。不得自动覆盖已迁移数据。
2. 观测：新增受 operator 认证的轻量摘要，限定 SQLite 查询时间和样本条数，文件仅 stat，不遍历数据目录、不访问外部供应商、不执行完整性全扫。资源采样失败明确 unknown，模型费用明确是有限样本非账单/预算。摘要不得参与安全准入或自动操作。
3. 后台：首屏改用轻量摘要，按证据区分休眠、暂停、循环冷却、近期未成功、认知未启用、数据未读取；显示最近成功和下次重试、资源/费用口径、建议入口。保留详细诊断入口；摘要局部失败不伪装正常；退出及迟到响应沿用会话版本保护。

## 验证

新增 Python 单元/HTTP鉴权/敏感信息测试、真实 Linux 非特权导入与 umask 检查、安装失败阶段及 shell 回滚夹具、前端状态/转义/部分失败/会话失效测试。执行 Ruff、Mypy、前端测试及相关回归；有条件运行 Linux 全量。报告应分别说明已运行结果和仍需真实 Ubuntu/systemd 门禁的部分，不将本地测试冒充八项门禁。

## 实施结果

- 以上三项已在工作区实现；没有新增运行时第三方依赖、数据库迁移或后台采样线程。
- 安装阶段报告补充 systemd 状态未知分支：查询失败或正在切换状态不伪装为“已停止”。
- 对迁移后、代码指针切换前失败的边界增加兼容检查；不兼容时保留新运行环境并阻止旧代码重启。
- CI 原有 Ubuntu 3.12 的 root 验证步骤加入安装器可运维性测试；本地实际执行 Linux root/nobody 夹具。
- 修正既有诊断从 HTTP 层不存在的 cognition 字段读取启用状态的问题；改由实际服务提供只读循环存在性视图，未把 gateway 配置本身当作认知已运行。
- 后台首屏为四个本地接口；完整诊断仅在详细运行防护/展开配置检查时读取，不产生供应商探测或付款。
- 实际验证、初次测试目录权限问题、全量测试未完成的限制，以及变更风险见
  [验证与风险记录](../audit/2026-10-22-operability-verification.md)。
- 本轮仅修改开发工作区，未提交、推送、合并或部署。生产服务器不受本轮开发操作影响。
